基于规范的 ERP 系统（如 SAP、Oracle 等）的业务逻辑，**产量回馈（Production Report / Confirmation）**与**倒扣料（Backflush）**是生产执行（PP）与库存管理（WM）深度集成的核心环节。

非倒扣料（手动领料）已在 WM 模组完成，现在的重点是：**当车间汇报产出时，系统不仅要成品入库，还要自动按 BOM 比例扣减那些标记为“倒扣料”的物料库存**。

以下是为您评估并设计的系统流程与开发方案：

### 一、 业务流程设计 (Business Process Flow)

按照标准 ERP 规范，系统流程应分为以下几个步骤：

1. **触发回馈 (Trigger)**
   - 前端用户选择状态为 `RELEASED` (已下达) 或 `IN_PROGRESS` (生产中) 的工单，创建“产量回馈单”。
2. **数据录入与自动计算 (Input & Calculate)**
   - **成品产出信息**：用户录入 `good_quantity` (良品)、`rework_quantity` (返工)、`scrap_quantity` (报废)，并指定成品入库的目标仓库 (`warehouse_id`) 和批次 (`batch_no`)。
   - **倒扣料自动计算**：系统自动筛选该工单下 `isBackflush = true` 的组件。
   - **消耗量公式**：`理论消耗量 = (本次良品数量 + 本次报废数量) * (组件 requiredQuantity / 工单 plannedQuantity)`。（*注：通常报废品也消耗了原材料，因此作为基数。*）
   - 将计算结果填充到 `production_report_components`（用料明细）中。系统应允许用户微调实际消耗量、批次或线边仓（Shop Floor Warehouse）。
3. **保存与过账 (Save & Post)**
   - **保存 (Draft)**：仅持久化 PP 模组的单据数据，不影响库存。
   - **过账 (Post)**：执行核心的库存流转与工单状态更新（必须在同一事务中保证数据一致性）。

---

### 二、 核心过账流转设计 (Core Posting Data Flow)

当用户点击“过账”时，系统需要在后端执行以下三大核心动作：

#### 1. PP 模组：更新生产进度
- **更新工单 (`ProductionOrder`)**：
  - `completedQuantity` 累加 `good_quantity`。
  - `scrappedQuantity` 累加 `scrap_quantity`。
  - 如果 `completedQuantity >= plannedQuantity`，自动将工单状态 `orderStatus` 更新为 `FINISHED` (已完工)。
- **更新工单组件 (`ProductionOrderComponent`)**：
  - 遍历本次的倒扣料明细，将消耗量累加到对应组件的 `issuedQuantity` (已发数量) 中。
- **更新回馈单状态**：将 `production_reports` 的状态更新为 `POSTED`。

#### 2. WM 模组：成品入库 (Finished Goods Receipt)
- PP 模组组装数据，调用 WM 模组的入库服务（如 `GoodsReceiptService`）。
- **动作**：生成一张成品入库单并自动过账，增加成品库存。
- **关联依据**：
  - `SourceDocType` = `PRODUCTION_REPORT`
  - `SourceDocId` = `production_reports.id`
  - `Material` = 工单的 `productMaterialId`，数量 = `good_quantity`。

#### 3. WM 模组：倒扣料发料/扣账 (Backflush Material Issue)
- PP 模组组装数据，调用 WM 模组的发料服务（如 `StockIssueService`）。
- **动作**：生成一张生产发料单并自动过账，扣减倒扣料库存。
- **关联依据**：
  - `SourceDocType` = `PRODUCTION_REPORT`
  - 遍历 `production_report_components`，将物料、仓库、批次、消耗量传入。
- **异常阻断**：如果线边仓的倒扣料库存不足，WM 的底层（如 `StockTransactionLedgerService`）会抛出库存不足异常，**整个过账事务必须回滚**，并提示用户先进行库存调拨或盘点。

### 三、 具体开发落地方案 (Development Implementation Plan)

为了实现上述设计，建议在代码层面进行以下调整和开发：

#### 1. 完善通用枚举 (Common Enums)
在 `lychee-erp-common` 模块中，为 WM 模组的单据来源增加产量回馈类型的支持：
- `GoodsReceiptSourceDocType` 增加 `PRODUCTION_REPORT` (用于成品入库)。
- `StockIssueSourceDocType` 增加 `PRODUCTION_REPORT` (用于倒扣料发料)。
- 新增 `ProductionReportStatus` 枚举：`DRAFT` (草稿), `POSTED` (已过账), `CANCELLED` (已取消)。

#### 2. PP 模组实体与仓储 (Entity & Repository)
- 根据您提供的 SQL 脚本，创建 `ProductionReport` 和 `ProductionReportComponent` 的 JPA Entity 类。
- 创建对应的 Repository 接口。

#### 3. PP 模组服务层 (Service Layer)
创建 `ProductionReportService`，核心提供以下接口：
- `calculateBackflushComponents(...)`: 供前端调用的 API。输入良品/报废数量，返回系统计算好的倒扣料明细列表。
- `create(...)` / `update(...)`: 保存草稿。
- `post(Long reportId)`: **核心过账方法**。需加上 `@Transactional` 注解。

#### 4. 跨模块服务调用 (Cross-Module Integration)
由于 PP 需要驱动 WM 产生库存异动，需要确保 PP 能调用 WM 的服务：
- 如果项目是单体架构（Monolith），可以直接在 PP 的 Service 中注入 `GoodsReceiptService` 和 `StockIssueService`。
- 如果是微服务架构，需要在 `lychee-erp-common` 中定义 `RemoteGoodsReceiptService` 和 `RemoteStockIssueService`（包含 `createAndPost(...)` 的复合接口），通过 Feign Client 进行调用，并考虑分布式事务（如 Seata 或消息事件最终一致性）。

#### 5. 防呆与校验机制 (Validation & Safety)
- **超量回馈校验**：可配置系统参数，是否允许 `completedQuantity > plannedQuantity`（即超产）。如果不允许，在录入时需报错。
- **批次管控**：如果成品物料启用了批次管理，回馈单上必须强制要求输入 `batch_no`。
- **撤销过账 (Cancel/Reverse)**：如果用户发现回馈错误需要冲销，系统需要支持 Cancel 操作。Cancel 需反向执行：扣减成品库存、增加倒扣料库存、扣减工单的完成量。

这个架构设计严格遵循了 ERP 的标准 MRP II 闭环逻辑，既保证了工单成本核算的准确性，也确保了实物库存与账面库存的强一致性。

了解您的系统架构和当前所处的开发阶段。既然系统仍在设计阶段，核心逻辑完全可以重构，那么我们抛开现有代码的束缚，**完全以规范 ERP（如 SAP、Oracle、Dynamics 等）的标准设计哲学来解答：**

即使您可以把 `StockTransactionLedgerService` 重构为一个通用的底层方法，在标准 ERP 架构中，**产量回馈（Production Report）依然不应该直接写入库存台账（StockTransaction），而是必须生成收货单/发料单（或者统称为“物料凭证 / Material Document”）。**

以下是标准 ERP 采用这种设计的核心原因和处理规范：

### 1. 标准 ERP 的“单据凭证化”原则 (Voucher/Document Principle)
在标准 ERP 中（以 SAP 为例，产量回馈事务码如 CO11N/CO15）：
*   **PP 模组** 生成的是 **产量确认凭证**（Production Confirmation）。
*   **MM/WM 模组** 只要发生库存异动，**必须且必定**生成 **物料凭证**（Material Document，即对应您系统中的 `GoodsReceipt` / `StockIssue`）。
*   物料凭证过账后，才会去更新 **库存台账/余额表**（对应您的 `StockTransaction`）。

**为什么不能跳过物料凭证（GoodsReceipt/StockIssue）直接写台账？**
因为 `StockTransaction` 仅仅是“流水/账本”，而 `GoodsReceipt/StockIssue` 是“单据/凭证”。在财务审计和内控规范中，**任何账本的变动都必须有一张属于该业务领域的单据作为依据**。产量回馈是生产行为，它说明了“做了多少”；而收发料单是仓管行为，它说明了“库存怎么变的”，两者领域不同，不可相互替代。

### 2. 异常处理与重处理机制 (Error Handling & Postprocessing)
倒扣料（Backflush）在实际业务中非常容易失败，比如**线边仓库存不足**，或者**批次锁单**。
*   **如果直接写 `StockTransaction`：** 遇到库存不足，您只能让整个产量回馈（Production Report）直接回滚报错。这在车间是不可接受的，工人报工不能因为系统里缺几个螺丝的账就无法提交产量。
*   **规范 ERP 的做法：** 产量回馈成功保存。系统尝试在后台生成 `StockIssue`（发料单）进行扣账：
    *   如果扣账成功，发料单状态为“已过账”。
    *   如果库存不足，系统会生成一张 **“待处理/失败状态的发料单”**（在 SAP 中称为 COGI 记录）。车间报工依然成功，而仓管员事后通过查阅这张失败的发料单，补齐库存后重新触发过账。
必须有 `StockIssue` 这个单据实体，才能承载“待处理”、“部分发料”等仓储业务状态。

### 3. 库存成本与财务过账的解耦 (Costing & FI Decoupling)
在标准 ERP 中，库存变动不仅仅是数量的加减，还伴随着**成本核算**（如移动平均价计算）和**财务凭证生成**（借/贷 会计科目）。
*   `GoodsReceipt` 和 `StockIssue` 往往封装了“业务类型”（入库、出库、调拨、盘点等），并且关联了具体的业务属性。
*   成本服务（FI/CO 模组）通常是监听“物料凭证”的生成，而不是监听底层流水。让 `GoodsReceipt/StockIssue` 统一作为所有库存变动的入口，可以确保成本计算逻辑集中在一处（WM 模组），而不需要在 PP 的报工逻辑中去处理物料单价、财务科目的计算。

### 💡 针对您系统的架构建议

既然您的系统是**多模组单体架构（Modular Monolith）**，且可以通过 `common` 模组的 Remote Interface 互相调用，按照规范 ERP 的设计，建议的开发路径如下：

1. **统一 WM 模组的凭证层（可选重构）：**
   目前您分为了 `GoodsReceipt` 和 `StockIssue`。这没有问题（许多轻量级 ERP 也是如此区分）。如果您想更彻底遵循 SAP 等大型 ERP 的设计，可以将其重构合并为统一的 `InventoryDocument`（物料凭证，用正负数或 Transaction Type 区分收发）。
   *如果不重构，保留现有的 `GoodsReceipt` 和 `StockIssue` 完全可行。*

2. **跨模组调用契约（Remote Interface）：**
   在 `common` 模组中，WM 提供如下接口供 PP 调用：
   ```java
   public interface RemoteProductionInventoryService {
       // 成品入库 (生成 GoodsReceipt 并过账)
       String postFinishedGoods(ProductionReceiptDTO dto);
       
       // 倒扣料发料 (生成 StockIssue 并过账，若库存不足可选择阻断或挂起)
       String postBackflushMaterials(ProductionBackflushDTO dto);
   }
   ```

3. **PP 模组的过账逻辑：**
   在 `ProductionReport` 过账时：
   * 记录良品和报废数量。
   * 调用 `RemoteProductionInventoryService.postFinishedGoods`。
   * 调用 `RemoteProductionInventoryService.postBackflushMaterials`。
   * 将返回的单号（`receiptNo`, `issueNo`）回写到 `ProductionReport` 的关联字段中，完成业务闭环。

**总结：** 规范的 ERP 绝对不会让 PP 模组直接去写 WM 模组的底层台账表。引入**收发料单据（GoodsReceipt / StockIssue）**作为 PP 和底层账本之间的“缓冲和凭证层”，是保证系统在未来支持异步处理、异常挂起、财务核算和严格审计的必不可篡改审计的审计追踪审计的必不可少走偏废的审计追溯性审计的必要设计的最优良内控的唯一正确架构基石。
