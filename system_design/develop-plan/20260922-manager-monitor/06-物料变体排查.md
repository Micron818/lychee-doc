# 06. 物料变体排查

> 接 [05](./05-物料变体检核.md)。三张变体卡片已经上线，`detailPath` 仍为 null。  
> 本批只加排查抽屉。口径、人口、停用行、索引折衷都不再改。无 Liquibase，不改物料列表搜索，不改保存流程。

卡片上的 `count` 是撞车的**组合数**。抽屉里的每一行是一颗**物料**。一组两行时，卡片是 1，表是 2 行。混色时，卡片是款数，表是这些款上全部完整变体物料。

打开健康区仍然只跑原来的计数查询。明细在使用者点开某张需关注的卡片时才查。

```java
default String inspectionKind() {
    return null;
}
```

三张变体指标覆盖为 `HealthInspectionKinds.MATERIAL_VARIANT`。`evaluate` 把 `inspectionKind()` 放进 `HealthCard`，卡片和接口判断用的是同一个方法。`UNKNOWN` 卡片不读这个方法，`inspectionKind` 为 null。

常量放在 common：`HealthInspectionKinds.MATERIAL_VARIANT = "material-variant"`。

## 2. 放置与 HTTP

```text
lychee-erp-common
  com.lychee.erp.common.monitor
    HealthIndicator.inspectionKind()    默认 null
    HealthInspectionKinds
    HealthInspection
    MaterialVariantInspectionResponse
    MaterialVariantInspectionRow

lychee-erp-report
  MonitorController
    GET /health/{code}/inspection
    返回 ApiResponse<Object>
  MonitorService
    按 code 找到 HealthInspection 并转发
    不引用变体行类型，不转型

lychee-erp-basis
  MaterialRepository
    findDuplicateColoredVariants
    findDuplicateNocolorVariants
    findMixedColorModeVariants

lychee-erp-mm
  com.lychee.erp.mm.monitor
    三个指标类同时实现 HealthIndicator 与 HealthInspection
      inspectionKind() 返回 HealthInspectionKinds.MATERIAL_VARIANT
    组装器注入 basis 已有的
      ProductModelRepository、ColorRepository、ProductSizeRepository
      只调用 findAllById，不新增查询方法
```

这四个契约类型都在 `lychee-erp-common`。放进 mm 之后，report 要么编译不过，要么就要依赖 mm。

```java
public interface HealthInspection {

    String code();

    /** 运行时类型由 inspectionKind 决定。本批是 MaterialVariantInspectionResponse。 */
    Object inspect(HealthContext context);
}
```

```java
@GetMapping("/health/{code}/inspection")
@PreAuthorize("hasAuthority('/report/monitors:read')")
public ApiResponse<Object> inspection(@PathVariable String code)
```

`GET /api/v1/report/monitors/health/{code}/inspection`

控制器不写成 `ApiResponse<MaterialVariantInspectionResponse>`。Jackson 按 `inspect` 实际返回的对象序列化。以后生产、库存或财务的排查返回自己的响应类型时，report 的方法签名不变。路径仍是这一个；卡片上的 `inspectionKind` 决定前端用哪一种抽屉。不为变体单独改成 `/material-variant-inspection`。

report 的查找顺序：

1. 没有这个 `code` 的 `HealthIndicator`，或当前用户看不见它：404。
2. 没有这个 `code` 的 `HealthInspection`，或指标的 `inspectionKind()` 为空：404。
3. 否则调用 `inspect`，把返回值放进 `ApiResponse.success`。查询异常照现网业务异常返回，不要改写成 `UNKNOWN` 卡片。report 不检查返回值是不是变体行。

变体行类型只描述 `material-variant` 的 JSON。列不同的指标不要复用它。

```java
public record MaterialVariantInspectionResponse(
    String code,
    List<MaterialVariantInspectionRow> rows
) {}

public record MaterialVariantInspectionRow(
    long materialId,
    String materialCode,
    String materialName,
    Long productModelId,
    String productModelCode,
    String productModelName,
    Long colorId,
    String colorCode,
    String colorName,
    Long productSizeId,
    String productSizeCode,
    String productSizeName,
    @JsonProperty("isFashionVariant") boolean isFashionVariant,
    ActiveStatus activeStatus
) {}
```

`code` 等于路径上的 code。`rows` 没有违规物料时是空数组，HTTP 200。这与卡片上的组合数不是同一个数。

三张现有指标类的 `inspect` 返回 `MaterialVariantInspectionResponse`。`inspectionKind()` 的默认实现在 `HealthIndicator` 上，返回 null。这三张覆盖为：

```java
@Override
public String inspectionKind() {
    return HealthInspectionKinds.MATERIAL_VARIANT;
}
```

`evaluate` 写入卡片时调用 `inspectionKind()`，不要在 `new HealthCard(...)` 里再写一遍 `"material-variant"`。

本批前端在 `inspectionKind === material-variant` 时，把 `data` 收成这个响应。换 kind 时按 kind 分支解析，不要把变体行当成所有排查的公共类型。

## 3. 查询

人口与 [05 §2](./05-物料变体检核.md) 相同：不加 `is_fashion_variant`，不加 `activeStatus`。JPQL 只查 `Material`，租户仍靠 `@TenantId`。

用相关 `EXISTS`，不用元组 `(productModelId, colorId, productSizeId) IN (SELECT … GROUP BY … HAVING …)`。Hibernate 对带 `GROUP BY` / `HAVING` 的元组构造器容易在翻译期失败。`EXISTS` 只表达「同一格上还有另一行」，和 05 的分组计数是同一批物料。

不分色不能写成 `m2.colorId = m.colorId`。两边都是 null 时，SQL 里相等不成立。无色侧用 `IS NULL`。

方法在 `MaterialRepository`。不要先查出组键再按组逐次查物料。

### 3.1 有色重复 `findDuplicateColoredVariants`

```java
@Query("""
        SELECT m FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.colorId IS NOT NULL
           AND m.productSizeId IS NOT NULL
           AND EXISTS (
               SELECT 1 FROM Material m2
                WHERE m2.productModelId = m.productModelId
                  AND m2.colorId = m.colorId
                  AND m2.productSizeId = m.productSizeId
                  AND m2.id <> m.id
           )
         ORDER BY m.productModelId, m.colorId, m.productSizeId, m.code
        """)
List<Material> findDuplicateColoredVariants();
```

### 3.2 不分色重复 `findDuplicateNocolorVariants`

```java
@Query("""
        SELECT m FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.colorId IS NULL
           AND m.productSizeId IS NOT NULL
           AND EXISTS (
               SELECT 1 FROM Material m2
                WHERE m2.productModelId = m.productModelId
                  AND m2.colorId IS NULL
                  AND m2.productSizeId = m.productSizeId
                  AND m2.id <> m.id
           )
         ORDER BY m.productModelId, m.productSizeId, m.code
        """)
List<Material> findDuplicateNocolorVariants();
```

### 3.3 同款混用有色与不分色 `findMixedColorModeVariants`

外层是该款上的每一颗完整变体。两个 `EXISTS` 分别要求这一款至少有一行有色、一行无色，与 05 §2.3 的款集合相同。

```java
@Query("""
        SELECT m FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.productSizeId IS NOT NULL
           AND EXISTS (
               SELECT 1 FROM Material colored
                WHERE colored.productModelId = m.productModelId
                  AND colored.productSizeId IS NOT NULL
                  AND colored.colorId IS NOT NULL
           )
           AND EXISTS (
               SELECT 1 FROM Material plain
                WHERE plain.productModelId = m.productModelId
                  AND plain.productSizeId IS NOT NULL
                  AND plain.colorId IS NULL
           )
         ORDER BY m.productModelId, m.colorId NULLS FIRST, m.productSizeId, m.code
        """)
List<Material> findMixedColorModeVariants();
```

名称由 mm 的组装器填充。它注入 basis 里已经存在的 `ProductModelRepository`、`ColorRepository`、`ProductSizeRepository`。这三个接口都继承 `JpaRepository`，直接调用 `findAllById(ids)`，按本页出现的 id 各查一次。不为编码和名称再写 `@Query`。主数据已不存在时，编码和名称为 null，行仍返回，`materialId` 仍在。列表顺序用上面的 `ORDER BY`，组装时不要再排一次。

`inspect` 上 `@Transactional(readOnly = true)`。三张类共用这一个组装器。

这三条 JPQL 并进现有的 `MaterialVariantHealthQueriesTest`。反射读取的方法名就是 `findDuplicateColoredVariants`、`findDuplicateNocolorVariants`、`findMixedColorModeVariants`。仍用 `AuditableEntity` + `Material` 的脱机 `HqlTranslator`。查询不连接其他实体，所以元数据不用再登记款、色、码。

## 4. 抽屉

`src/pages/report/monitors` 在健康卡片上：

| 卡片 | 点击 |
|------|------|
| `detailPath` 有值 | 照旧进入该路由 |
| `inspectionKind` 为 `material-variant`，且需关注、`count > 0` | 打开抽屉 |
| 其余 | 不可点 |

抽屉用 Ant Design `Drawer`，宽 `90%`，只读。标题用卡片的 `titleKey`。标题下说明组合数与物料行数不是同一个数，文案 key `pages.report.monitors.inspection.groupHint`。卡片上的 `count` 是组合数，表的行数是物料数。

`destroyOnClose`。打开后再请求。数据返回后再挂 `ProTable`，`scroll={{ x: 'max-content' }}`。不要在抽屉还没打开时把表挂进页面。`rowKey` 用 `materialId`。无搜索。

后端一次把行全部返回。表格用客户端分页，避免一次画出成百上千行：

```tsx
pagination={{
  defaultPageSize: 50,
  showSizeChanger: true,
}}
```

| 列 | 取值 |
|----|------|
| 物料 | `formatCodeName(materialCode, materialName)`。标题用 `pages.report.monitors.inspection.material` |
| 款 | `formatCodeName(productModelCode, productModelName)`。标题用已有的 `pages.mm.materials.productModelId` |
| 色 | `colorId == null` 时用 `pages.report.monitors.inspection.nocolor`，否则 `formatCodeName(colorCode, colorName)`。标题用已有的 `pages.mm.materials.colorId` |
| 码 | `formatCodeName(productSizeCode, productSizeName)`。标题用已有的 `pages.mm.materials.productSizeId` |
| 注记 | `isFashionVariant`。标题用已有的 `pages.mm.materials.isFashionVariant` |
| 启用状态 | `activeStatus`，`enumToValueEnum(enums.ActiveStatus)`。标题用已有的 `pages.table.activeStatus` |

`pages.table.code` 的中文是「代码」，不能当作「编码 + 名称」这一列的标题。`menu.mm.materials` 是「物料资料」，`pages.report.monitors.progress.productMaterial` 是「产品」，都不用。

空表用 `pages.report.monitors.inspection.empty`。请求失败用现有的错误通知，抽屉可以留在打开状态。关掉抽屉不重新请求健康区。

## 5. 提交与测试

一次提交完成本批（契约字段、三条明细查询、一个 GET、抽屉）。健康卡片的计数查询保持不动。

- 三张指标单测：`inspectionKind` 为 `material-variant`，`detailPath` 仍为 null。`inspect` 用 mock：有色行带色；不分色行 `colorId` 为 null；停用行仍出现；返回顺序与仓库给出的顺序一致。
- report 单测：看不见的 code、不能排查的 code，都不调用 `inspect`，并抛 `NotFoundException`。能排查时原样返回该 bean 的对象，服务里不把它转成 `MaterialVariantInspectionResponse`。
- `MaterialVariantHealthQueriesTest` 用 §3 的三个方法名读取 `@Query`。属性名写错时失败。
- 现有 `new HealthCard(...)` 全部补上末位 `inspectionKind`。`UNKNOWN` 与非本批指标传 null。

## 6. 不要做的事

- 不要把明细行放进 `GET /health`。
- 不要按物料行数改写卡片上的 `count`。
- 不要给这三张卡片填 `detailPath`，不要改物料列表去读 URL 查询。
- 不要在抽屉里编辑、删除或生成变体。
- 不要给查询加 `is_fashion_variant` 或 `activeStatus = ACTIVE`。
- 不要本批加复合索引，不要用原生 SQL 手写 `tenant_id`。
- 不要让 report 依赖 mm 或 basis 的 Repository。
- 不要把 `HealthInspectionKinds`、`HealthInspection`、`MaterialVariantInspectionResponse`、`MaterialVariantInspectionRow` 放进 mm。
- 不要把控制器写成 `ApiResponse<MaterialVariantInspectionResponse>`，也不要为变体另开一条路径。
- 不要用元组 `IN (SELECT … GROUP BY … HAVING …)` 写这三条明细。
- 不要给 inspection 加分页参数。前端不要 `pagination={false}`。
- 不要用 `pages.table.code` 做物料列标题。
- 不要在 `evaluate` 里手写 `inspectionKind` 字面量。卡片上的值来自 `inspectionKind()`。
- 不要为款、色、码名称在 `ProductModelRepository`、`ColorRepository`、`ProductSizeRepository` 上新增查询。
- 其他指标不要复用 `MaterialVariantInspectionRow`。列不同时另写响应类型，仍走同一个 GET。

## 7. 验收

- `OK`、`UNKNOWN`、`count` 为 0 的变体卡片不可点，不发 inspection 请求。
- 需关注且 `count > 0` 的三张卡片可点。打开抽屉后只请求对应 code。表在数据返回后出现，列宽不是 0。
- 物料列表头是「物料」。有色抽屉的每一行都有颜色。不分色抽屉的颜色列都是「不分色」。混色抽屉里同一款既有有色行也有无色行。
- 停用物料出现在表中，启用状态显示为停用。注记为 false 的手工资料同样出现。
- 卡片数字与表行数可以不同。标题下的说明能看出一个是组合数、一个是物料数。
- 行数超过 50 时，表格只画出当前页，并可以改每页条数。接口仍一次返回全部行，请求里没有页码参数。
- 没有 `/mm/materials:read` 且不是 `ROLE_ADMIN` 的用户看不到这三张卡片。直接调用该 code 的 inspection 得到 404，监测页本身不因此 403。
- 关掉抽屉后，健康区不会自己再请求。点健康区刷新才重新计数。
- 换租户看不到对方的物料行。
- `lychee-erp-report/build.gradle` 仍然没有业务模块依赖。控制器方法的返回类型是 `ApiResponse<Object>`。
