# 05. 物料变体检核

> 隶属本专题 P2。收集、权限、失败卡片仍按 [03](./03-契约设计.md)、[04](./04-实施清单.md)。  
> 本文只锁定三张卡片的口径。无 Liquibase，不改唯一索引，不改保存流程，不回填 `is_fashion_variant`。

来源是 `0907-001-mm-variant-generation.sql` 里注释掉的三段预检。当时准备给完整变体建唯一索引，后来 `0908-002` 把索引收成只覆盖 `is_fashion_variant = true`。混色模式从一开始就没有索引，只在服务层拦截注记为 true 的行。

注记在保存时抄分类生效策略：`is_fashion_variant = (strategy == FASHION_VARIANT)`。MANUAL 不进入变体维度校验，同款同色同码可以存多行。实务上已有本应作为时装变体的资料走了 MANUAL，注记为 false。部分唯一索引和服务层色模式锁都看不见这些行。监测按注释 SQL 的人口计数，查询里不加 `is_fashion_variant` 条件。

同一租户里，SEQUENTIAL 以及「OEM 挂同一版型、不占格」的 MANUAL 行，只要填了款和码，也会进入这三张卡片。注释 SQL 不区分编码策略，本批同样不按分类树过滤。

## 2. 三张卡片

完整变体：`product_model_id` 与 `product_size_id` 都非空。有色、无色两张的行互不相交。混色按款汇总，一行物料只可能贡献其中一侧。

| code | 一组是什么 | 计入条件 |
|------|------------|----------|
| `mm.material.variant.duplicate.color` | 款 + 色 + 码 | 该组行数 > 1，且 `color_id` 非空 |
| `mm.material.variant.duplicate.nocolor` | 款 + 码 | 该组行数 > 1，且 `color_id` 为空 |
| `mm.material.variant.mixed-color-mode` | 款 | 该款完整变体里，有色行与无色行都至少 1 条 |

注记为 true 的行若独自撞车，部分唯一索引会拒绝写入。前两张卡片里出现的组，因此至少含一行注记为 false 的资料（常见是 MANUAL）。一张 true 与一张 false 落在同一格，同样算一组。查询仍不要写成 `is_fashion_variant = false`：索引失效或历史双 true 时，这些组也要出现在卡片上。

混色同样不加注记条件。`assertColorModeForSave` / `assertColorModeForReplace` 只统计 `is_fashion_variant = true`，挡不住手工录入的混色款。

### 2.1 有色重复

```java
@Query("""
        SELECT m.productModelId, m.colorId, m.productSizeId
          FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.colorId IS NOT NULL
           AND m.productSizeId IS NOT NULL
         GROUP BY m.productModelId, m.colorId, m.productSizeId
        HAVING COUNT(m.id) > 1
        """)
List<Object[]> findDuplicateColoredVariantGroups();
```

`count` = 返回行数。

### 2.2 不分色重复

```java
@Query("""
        SELECT m.productModelId, m.productSizeId
          FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.colorId IS NULL
           AND m.productSizeId IS NOT NULL
         GROUP BY m.productModelId, m.productSizeId
        HAVING COUNT(m.id) > 1
        """)
List<Object[]> findDuplicateNocolorVariantGroups();
```

`count` = 返回行数。

### 2.3 同款混用有色与不分色

JPQL 没有 `COUNT(*) FILTER`。用两侧行数都大于 0：

```java
@Query("""
        SELECT m.productModelId
          FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.productSizeId IS NOT NULL
         GROUP BY m.productModelId
        HAVING SUM(CASE WHEN m.colorId IS NOT NULL THEN 1 ELSE 0 END) > 0
           AND SUM(CASE WHEN m.colorId IS NULL THEN 1 ELSE 0 END) > 0
        """)
List<Long> findProductModelIdsWithMixedColorMode();
```

`count` = 返回的款号个数。

三条都只选出违规键，不加载 `Material`。`evaluate` 用列表长度作为 `count`。组数变大时，只把对应方法改成对同一分组做 `COUNT`，卡片字段不变。

## 3. 放置与组装

```text
lychee-erp-basis
  MaterialRepository
```

`HealthCard` 组装：

| 字段 | 值 |
|------|-----|
| `code` | 该 Bean 的 `code()` |
| `status` | 组数 `> 0` 为 `ATTENTION`，否则 `OK` |
| `count` | 组数，类型 `Long`。0 也返回 0，不用 null |
| `titleKey` | `titleKey()` |
| `detailPath` | `null` |

`requiredAuthority()` 返回 `/mm/materials:read`。不为这三张卡片新增菜单动作。

## 4. 提交顺序与文案

一次提交一张，顺序：

1. `mm.material.variant.duplicate.color`
2. `mm.material.variant.duplicate.nocolor`
3. `mm.material.variant.mixed-color-mode`

响应按 `code` 字典序排列，与这个顺序一致。

每一张同时写入后端 `messages.properties` / `messages_zh_CN.properties` / `messages_vi.properties`，以及前端 `src/locales/{en-US,vi-VN,zh-CN}/pages.ts`（与监测健康 key 相邻）。key 就是 `titleKey()`，前端 `formatMessage` 用的是接口返回的这个 key。

| key | zh-CN | en-US | vi |
|-----|-------|-------|-----|
| `monitor.health.mm.material.variant.duplicate.color` | 款色码重复 | Duplicate model, color and size | Trùng mẫu, màu và cỡ |
| `monitor.health.mm.material.variant.duplicate.nocolor` | 款码重复（不分色） | Duplicate model and size without color | Trùng mẫu và cỡ (không phân màu) |
| `monitor.health.mm.material.variant.mixed-color-mode` | 同款混用有色与不分色 | Model uses both colored and uncolored variants | Cùng một mẫu vừa có màu vừa không phân màu |

每张配一个指标单测：组数 0 得到 `OK` 且 `count = 0`；组数大于 0 得到 `ATTENTION` 且 `count` 等于组数；`detailPath` 为 null；`titleKey` 等于 `monitor.health.` + `code`。查询方法用 mock，不在单测里起数据库。

## 5. 不要做的事

- 不要给查询加 `is_fashion_variant = true` 或 `= false`。
- 不要按 `code_strategy` 递归分类树，把 SEQUENTIAL / OEM 行排除在外。
- 不要在 report 里写这三段 SQL，也不要让 report 依赖 mm 或 basis 的 Repository。
- 不要用原生 SQL 手写 `tenant_id`。
- 不要改 `uk_materials_tenant_fashion_variant_*`，不要把注释里的全量唯一索引打开。
- 不要在保存、生成变体、替换款色时改为拦截 MANUAL 重复或混色。本批只读。
- 不要回填 `is_fashion_variant`，不要给物料表单加注记开关。
- 不要为下钻改物料列表的搜索或 URL 初始化。`detailPath` 保持 null。
- 不要建指标结果表或定时快照。

## 6. 验收

- 有 `/mm/materials:read` 或 `ROLE_ADMIN`、且能打开监测页的用户，能看到已注册的这几张。没有该权限且不是 `ROLE_ADMIN` 时，这几张不出现，页上其他卡片还在。
- 当前租户没有撞车组时，对应卡片 `OK`，`count` 为 0。
- 同款同色同码至少两行（不论注记）时，有色卡片为 `ATTENTION`，`count` 为这种组合的个数。缺款、缺色或缺码的行不进入这一张。
- 同款同码、`color_id` 为空且至少两行时，不分色卡片同样计数。这些行不进入有色卡片。
- 同一款上既有有色完整变体、又有无色完整变体时，混色卡片的 `count` 加 1。只有一侧时不加。
- 换租户看不到对方的组。
- `evaluate` 抛错时，这一张为 `UNKNOWN`，标题仍是本节 key 的译文，另外两张和进度区不受影响。
- `lychee-erp-report/build.gradle` 仍然没有业务模块依赖。
