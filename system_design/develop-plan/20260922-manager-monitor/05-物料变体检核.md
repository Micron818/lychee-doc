# 05. 物料变体检核

> 隶属本专题 P2。收集、权限、失败卡片仍按 [03](./03-契约设计.md)、[04](./04-实施清单.md)。  
> 本文锁定三张卡片的口径，以及监测页改为按区块载入。无 Liquibase，不改唯一索引，不改保存流程，不回填 `is_fashion_variant`。

来源是 `0907-001-mm-variant-generation.sql` 里注释掉的三段预检。当时准备给完整变体建唯一索引，后来 `0908-002` 把索引收成只覆盖 `is_fashion_variant = true`。混色模式从一开始就没有索引，只在服务层拦截注记为 true 的行。

注记在保存时抄分类生效策略：`is_fashion_variant = (strategy == FASHION_VARIANT)`。MANUAL 不进入变体维度校验，同款同色同码可以存多行。实务上已有本应作为时装变体的资料走了 MANUAL，注记为 false。部分唯一索引和服务层色模式锁都看不见这些行。监测按注释 SQL 的人口计数，查询里不加 `is_fashion_variant` 条件。

同一租户里，SEQUENTIAL 以及「OEM 挂同一版型、不占格」的 MANUAL 行，只要填了款和码，也会进入这三张卡片。注释 SQL 不区分编码策略，本批同样不按分类树过滤。

## 2. 三张卡片

完整变体：`product_model_id` 与 `product_size_id` 都非空。有色、无色两张的行互不相交。混色按款汇总，一行物料只可能贡献其中一侧。

| code | 一组是什么 | 计入条件 |
|------|------------|----------|
| `mm.material.variant.duplicate.color` | 款 + 色 + 码 | 该组行数 > 1，且 `color_id` 非空 |
| `mm.material.variant.duplicate.nocolor` | 款 + 码 | 该组行数 > 1，且 `color_id` 为空 |
| `mm.material.variant.mixed-color-mode` | 款 | 该款完整变体里，有色行与无色行都至少 1 条 |

三张查询都不加 `activeStatus` 条件。`ACTIVE` 与 `INACTIVE` 都计入。

注记为 true 的行若独自撞车，部分唯一索引会拒绝写入。前两张卡片里出现的组，因此至少含一行注记为 false 的资料（常见是 MANUAL）。一张 true 与一张 false 落在同一格，同样算一组。查询仍不要写成 `is_fashion_variant = false`：索引失效或历史双 true 时，这些组也要出现在卡片上。

混色同样不加注记条件。`assertColorModeForSave` / `assertColorModeForReplace` 只统计 `is_fashion_variant = true`，挡不住手工录入的混色款。

### 2.1 有色重复

```java
@Query("""
        SELECT m.productModelId, m.colorId, m.productSizeId
          FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.colorId IS NOT NULL
           AND m.productSizeId IS NOT NULL
         GROUP BY m.productModelId, m.colorId, m.productSizeId
        HAVING COUNT(m.id) > 1
        """)
List<Object[]> findDuplicateColoredVariantGroups();
```

`count` = 返回行数。

### 2.2 不分色重复

```java
@Query("""
        SELECT m.productModelId, m.productSizeId
          FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.colorId IS NULL
           AND m.productSizeId IS NOT NULL
         GROUP BY m.productModelId, m.productSizeId
        HAVING COUNT(m.id) > 1
        """)
List<Object[]> findDuplicateNocolorVariantGroups();
```

`count` = 返回行数。

### 2.3 同款混用有色与不分色

JPQL 没有 `COUNT(*) FILTER`。用两侧行数都大于 0：

```java
@Query("""
        SELECT m.productModelId
          FROM Material m
         WHERE m.productModelId IS NOT NULL
           AND m.productSizeId IS NOT NULL
         GROUP BY m.productModelId
        HAVING SUM(CASE WHEN m.colorId IS NOT NULL THEN 1 ELSE 0 END) > 0
           AND SUM(CASE WHEN m.colorId IS NULL THEN 1 ELSE 0 END) > 0
        """)
List<Long> findProductModelIdsWithMixedColorMode();
```

`count` = 返回的款号个数。

三条都只选出违规键，不加载 `Material`。`evaluate` 用列表长度作为 `count`。组数变大时，只把对应方法改成对同一分组做 `COUNT`，卡片字段不变。

### 2.4 索引用不上，扫描留到展开时

`0908-002` 里和变体有关的索引是：

| 索引 | 为何用不上 |
|------|------------|
| `uk_materials_tenant_fashion_variant_color` | 部分索引，谓词含 `is_fashion_variant = true` |
| `uk_materials_tenant_fashion_variant_nocolor` | 同上 |
| `idx_materials_fashion_variant` | 列序为 `(tenant_id, is_fashion_variant, product_model_id)`，本查询没有该等值条件 |

三条 JPQL 不加 `is_fashion_variant`，PostgreSQL 不能用这三只索引做 `GROUP BY`。展开「系统健康」时，它们在当前租户的 `materials` 上扫描并做哈希聚合。`MonitorServiceImpl` 对每个 `HealthIndicator` 串行 `evaluate`，耗时相加。

测试阶段接受这个成本，本批不加 Liquibase。物料行到了万级、展开健康区变慢时，再补**非部分**索引 `(tenant_id, product_model_id, product_size_id, color_id)`。索引上不能带 `is_fashion_variant = true`，否则 MANUAL 行仍在索引外。不要打开 `0907-001` 里注释掉的两只全量唯一索引：现有重复行会让迁移失败，也和本批只读冲突。

打开监测页本身不再跑这三条。见 §7。

key 就是 `titleKey()`。前端 `formatMessage` 用的是接口返回的这个 key。第 0 步若增加刷新文案，key 见 §7，同一次写入上述前端三语文件。

| key | zh-CN | en-US | vi |
|-----|-------|-------|-----|

| `pages.report.monitors.health.refresh` | 刷新 | Refresh | Làm mới |

每张卡片在 `lychee-erp-mm` 有一个指标单测：仓库方法用 mock。组数 0 得到 `OK` 且 `count = 0`；组数大于 0 得到 `ATTENTION` 且 `count` 等于组数；`detailPath` 为 null；`titleKey` 等于 `monitor.health.` + `code`。这个单测不解析 JPQL。

三条 `@Query` 另在 `lychee-erp-basis` 用 `MaterialVariantHealthQueriesTest` 做语法校验，不执行 SQL、不连接数据库：

1. 用反射读取 `MaterialRepository` 上这三个方法的 `@Query` 字符串，测试里不另抄一份。
2. `MetadataSources` 同时登记 `AuditableEntity.class` 与 `Material.class`。`AuditableEntity` 是 `@MappedSuperclass`，只登记 `Material` 时超类字段不会进元数据。方言用 `PostgreSQLDialect`。显式设置 `hibernate.boot.allow_jdbc_metadata_access=false`，测试不申请 JDBC 连接。
3. 把每段 JPQL 交给 `HqlTranslator.translate`。属性名或语法错误时测试失败。

指标单测全部绿灯，不能代替这一步。

## 6. 验收

- 打开 `/report/monitors` 且 URL 没有 `sections` 时，不出现 `/api/v1/report/monitors/health`，也不出现 `/production-progress`。
- `?sections=health` 只请求健康接口。`?sections=progress` 只请求进度接口，且 `reportDate` 为当天、不带工厂。两个 id 都在时，两个请求都发。
- 收起后再展开，不自动重查。健康区点刷新才再次 `GET`，且已展开的面板不会被这次点击收起。进度区仍用查询按钮。
- 进度表在面板第一次展开、并且已经可见时才挂载。展开后列宽按内容撑开，不是 0。
- 有 `/mm/materials:read` 或 `ROLE_ADMIN`、且能打开监测页的用户，展开健康区能看到已注册的这几张。没有该权限且不是 `ROLE_ADMIN` 时，这几张不出现，页上其他卡片还在。
- 当前租户没有撞车组时，对应卡片 `OK`，`count` 为 0。
- 同款同色同码至少两行（不论注记、不论停用）时，有色卡片为 `ATTENTION`，`count` 为这种组合的个数。缺款、缺色或缺码的行不进入这一张。
- 同款同码、`color_id` 为空且至少两行时，不分色卡片同样计数。这些行不进入有色卡片。
- 同一款上既有有色完整变体、又有无色完整变体时，混色卡片的 `count` 加 1。只有一侧时不加。停用行参与这一判断。
- 换租户看不到对方的组。
- `evaluate` 抛错时，这一张为 `UNKNOWN`，标题仍是本节 key 的译文，另外两张和进度区不受影响。
- `MaterialVariantHealthQueriesTest` 在 JPQL 属性名写错时失败。
- `lychee-erp-report/build.gradle` 仍然没有业务模块依赖。

## 7. 监测页按区块载入

`src/pages/report/monitors/index.tsx` 今天在挂载时做两件互不相关的事：`useRequest(getMonitorHealth)` 立刻 `GET`，`useEffect` 用当天日期 `POST` 进度。以后再加区块，就会在同一次打开上再叠请求。三条变体聚合又用不上现有索引，不能留在这次打开里。

选定的粒度是**区块**，不是单张卡片。使用者要看的是「系统健康」或「今日生产进度」，展开后才付出那一块的查询。健康区内部仍一次返回全部可见卡片：卡片还少，逐张点选会先看到一排未计算的壳。某一区块里的重查询多到展开一次已经过慢时，再给 `GET /health` 加可选、可重复的 `codes`，缺省仍是全部可见指标。那一步改 [03](./03-契约设计.md)，不在本批。

### 7.1 区块

| id | 面板标题（已有 key） | 展开后 |
|----|----------------------|--------|
| `health` | `pages.report.monitors.health.title` | `GET /api/v1/report/monitors/health` |
| `progress` | `pages.report.monitors.progress.title` | `POST /production-progress`，`reportDate` 为今天，不带 `factoryId` |

以后的区块追加一行：自己的 id、自己的接口，不在页面挂载时调用。

### 7.2 交互

- 两个面板用 Ant Design `Collapse`，默认全部收起。窄屏仍上下排列。不设 `forceRender`。
- `destroyInactivePanel={false}`。antd 5.29 若该属性已改为 `destroyOnHidden`，设为 `false`。首次在面板可见时挂载内容，之后收起仍保留实例，不要销毁后再在隐藏节点里重挂。
- 展开状态写在 URL 查询参数 `sections`，值为逗号分隔的 id，例如 `?sections=health,progress`。用 `history.replace`，避免每点一次面板就多一条历史。
- 首次进入且没有 `sections`：零请求。
- 刷新页面时只请求 `sections` 里列出的区块。
- 某一区块已经有成功结果时，收起再展开不自动重查。
- 健康面板标题栏 `extra` 提供刷新（`pages.report.monitors.health.refresh`）。`onClick` 里先 `e.stopPropagation()`，再处理展开和请求。冒泡会让 `Collapse` 把当前面板再切换一次：已展开时点刷新会收起，收起时会展开又被按钮逻辑再展开。面板收起时，这次点击自己把该区块展开并请求；已展开时只再 `GET` 一次，保持展开。
- 进度区的 `ProTable` 使用 `scroll={{ x: 'max-content' }}`。收起面板是 `display: none`，表在里面做第一次测量时列宽会变成 0。进度表在该面板第一次展开、内容已经可见之后再挂载；有进度响应后再渲染表格。收起期间不要预挂这张表。`destroyInactivePanel` / `destroyOnHidden` 保持 `false`，避免下次展开又在隐藏容器里重挂。
- 进度区去掉挂载时的 `useEffect`。首次展开用今天查一次。日期、工厂和查询按钮保持现在的行为；清空工厂后的请求仍不带 `factoryId`。
- 健康与进度的失败互不影响，仍是两次独立请求。

## 8. 排查

`detailPath` 为 null 时卡片不可点击。数量大于 0 时，用下面语句列出物料编码，交给主数据专员改。把 `:tenant_id` 换成要查的租户。这是数据库会话里的脚本，不是应用查询，所以这里要写租户条件。应用内的 JPQL 仍靠 `@TenantId`。

有色重复：

```sql
SELECT m.id, m.code, m.name,
       m.product_model_id, m.color_id, m.product_size_id,
       m.is_fashion_variant, m.active_status
  FROM lychee_erp.materials m
  JOIN (
        SELECT product_model_id, color_id, product_size_id
          FROM lychee_erp.materials
         WHERE tenant_id = :tenant_id
           AND product_model_id IS NOT NULL
           AND color_id IS NOT NULL
           AND product_size_id IS NOT NULL
         GROUP BY 1, 2, 3
        HAVING COUNT(*) > 1
       ) d
    ON m.tenant_id = :tenant_id
   AND m.product_model_id = d.product_model_id
   AND m.color_id = d.color_id
   AND m.product_size_id = d.product_size_id
 ORDER BY m.product_model_id, m.color_id, m.product_size_id, m.code;
```

不分色重复：

```sql
SELECT m.id, m.code, m.name,
       m.product_model_id, m.product_size_id,
       m.is_fashion_variant, m.active_status
  FROM lychee_erp.materials m
  JOIN (
        SELECT product_model_id, product_size_id
          FROM lychee_erp.materials
         WHERE tenant_id = :tenant_id
           AND product_model_id IS NOT NULL
           AND color_id IS NULL
           AND product_size_id IS NOT NULL
         GROUP BY 1, 2
        HAVING COUNT(*) > 1
       ) d
    ON m.tenant_id = :tenant_id
   AND m.product_model_id = d.product_model_id
   AND m.color_id IS NULL
   AND m.product_size_id = d.product_size_id
 ORDER BY m.product_model_id, m.product_size_id, m.code;
```

同款混用有色与不分色：

```sql
SELECT m.id, m.code, m.name,
       m.product_model_id, m.color_id, m.product_size_id,
       m.is_fashion_variant, m.active_status
  FROM lychee_erp.materials m
 WHERE m.tenant_id = :tenant_id
   AND m.product_size_id IS NOT NULL
   AND m.product_model_id IN (
        SELECT product_model_id
          FROM lychee_erp.materials
         WHERE tenant_id = :tenant_id
           AND product_model_id IS NOT NULL
           AND product_size_id IS NOT NULL
         GROUP BY 1
        HAVING COUNT(*) FILTER (WHERE color_id IS NOT NULL) > 0
           AND COUNT(*) FILTER (WHERE color_id IS NULL) > 0
       )
 ORDER BY m.product_model_id, m.color_id NULLS FIRST, m.product_size_id, m.code;
```

下一批再做产品化排查：`count > 0` 的卡片打开抽屉，列出与上面相同的列（物料编码、款、色、码、注记、启用状态）。仍不改物料列表的搜索。本批不做这个抽屉。
