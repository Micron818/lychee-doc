# 01. 预告订单现状与问题（As-Is）

> 依据当前代码与文档：`lychee-erp-sd` / `lychee-erp-pp` / `lychee-erp-common` / `lychee-frontend` / `lychee-doc`。  
> 旧单表与现网 CRUD **不是** To-Be 依据，见 [03-schema设计.md](./03-schema设计.md) §8。本文件只说明「现在有什么、差在哪」。

---

## 1. 业务缺口

正式订单链已闭环：

```text
SO(CONFIRMED) → FO(汇总) → MRP → PLO → MO → 产量 → GR → DN(交货，仅 SALES_ORDER)
```

客户预告（Booking / 滚动计划）没有对等入口。业务只能：

- 等正式 SO 再转 FO（长周期物料来不及），或
- 手开 `FactoryOrderSourceType.MANUAL` 的 FO（无客户预告单、无消耗、正式单再转一次会双投产）

`MrpSourceType.FORECAST`、单据前缀 `SFO`、菜单文案「客户需求预测」在文档里出现过，**都没有接到这条执行链**。

---

## 2. 现网正式单各管什么（预告必须对齐的部分）

| 单据 | 模块 | 现网能力 | 对预告的含义 |
|------|------|----------|--------------|
| `sales_orders` / items | SD | 表头–明细、确认/反确认/关闭、`allocated_quantity`、`delivered_quantity` | 预告应对齐单据骨架，但没有价税与交货 |
| FO `add-items-from-so` | PP | 仅 `sourceType=SALES_ORDER`；回写 SO allocated；pegging `SO→FO` | 预告转 FO 应对标这条，而不是另做 MRP 种子 |
| `pending-production` | SD | FO 汇入待转 SO 行 | 预告需要同等「待转 FO」查询 |
| MRP 引擎 | PP | 种子只读 `CONFIRMED`/`IN_PROGRESS` 的 FO | 未转 FO 的预告今天不算需求，To-Be 也保持如此 |
| DN | SD | `DeliverySourceDocType.SALES_ORDER` | 预告不能成为交货来源 |

SO 确认（`SalesOrderServiceImpl.confirmSalesOrderBulk`）只改状态，**不读任何预测/预告表**。反确认只拦 `allocated_quantity > 0`。

## 3. 已占位、不能用的废稿

### 3.1 单表 `sales_forecasts`

三处互相不一致，都是扁平行、无单据号：

| 来源 | 形态 |
|------|------|
| `schema_tables/SD/sales_forecasts.sql`、`0620-002` | `consumed_quantity`、`status` 字符串、`customer_id` 必填；唯一键 `(tenant, material, bucket_date)` **不含客户** |
| `v0` initial | 无 `consumed_quantity`，状态列名 `order_status` |
| Entity `SalesForecast` | 行级 `version`、`status_option_id`；唯一键还带 `version`；**无** `consumed_quantity` |

代码路径：

| 区域 | 路径 |
|------|------|
| CRUD | `sd/.../SalesForecastController.java`：`/page`、`POST`、`PUT /{id}`、`bulk-delete` |
| 服务 | `SalesForecastServiceImpl`：查重、填物料/客户/单位名。无确认、无行项目、无数量账 |
| 仓库 | `existsByMaterialIdAndBucketDateAndVersion`（与 changelog 唯一键也不一致） |

**没有**：`GET /{id}`、确认、关闭、明细 API、转 FO、被 SO 消耗。  
**前端没有** `pages/sd/sales-forecasts`。菜单种子无预告项（`SD01` 客户、`SD02` SO、`SD03` DN）。

### 3.2 枚举与文档占位

| 占位 | 实际 |
|------|------|
| `MrpSourceType.FORECAST` | `MrpCalculationEngine.seedFactoryOrderDemands` 只写 `FACTORY_ORDER` |
| `order_type_code.md` 前缀 `SFO` | `DocumentTypeEnum` 无 `SALES_FORECAST`，无单号规则种子 |
| `All_menu_design.md` 把 Forecast 放 CRM，「不直接进 MRP」 | 与「客户预告订单」不是同一对象；现网也没有 CRM 模块 |
| MRP 演进 Phase 5「启用 FORECAST 播种」 | 未做。To-Be **不**走这条，避免与 FO 双计 |

### 3.3 Pegging / FO 来源

- `PeggingOrderType` 无 `SALES_FORECAST`
- `FactoryOrderSourceType` 只有 `SALES_ORDER` / `MANUAL`
- `addItemsFromSalesOrders` 硬校验 `sourceType == SALES_ORDER`
- 删 FO 行回滚 allocated 只处理 `demandType == SALES_ORDER`
- `FactoryOrderPrintServiceImpl` 仅 `SALES_ORDER` 来源可打客户矩阵
- `OrderPeggingServiceImpl` 把 `SALES_ORDER` 当需求根做了特例；预告作为需求根不存在
- `uk_order_peggings` 现为 `(tenant_id, material_id, demand_id, supply_id)`，**不含** `demand_type` / `supply_type`。预告行 id 与 SO/FO 行 id 会撞号：同一数值对上的 `FORECAST→FO` 与 `SO→FO`（或 `FORECAST→SO` 与 `FORECAST→FO`）会唯一键冲突。To-Be 必须扩唯一键，见 [03](./03-schema设计.md) §5.1

## 4. 若继续用单表 / 直连 MRP 会错什么

| 方案 | 问题 |
|------|------|
| 在旧单表上 `ALTER` | 无单据号/确认/行号；唯一键缺客户，两客户同料同周会撞；代码与 changelog 已分叉 |
| 预告行直接当独立需求进 MRP | 转 FO 后再算一次 → 双需求；绕过现网 MPS（FO）与进度/打印 |
| 预告复制一整套 SO→DN | 无合同依据；正式单再转 FO 双投产 |
| SO 行加 `forecast_item_id` | 一张 SO 行可能吃多桶、一行预告被多张 SO 吃，1:1 FK 写死 |
| 用 `status_option_id` | 转单/消耗/关单无法靠枚举守卫 |
| 关单要求「未转开量必须为 0」 | 与「客户未下满、剩余作废」矛盾；滚动换版会被在制 FO 卡死，或关掉后 SO 只扫新 ACTIVE → 旧 FO 成孤儿、双投产 |
| ACTIVE 唯一键 / 消耗键不含 `company_id` | 现网 SO 有 `company_id`；两家销售公司对同一客户会互抢一张预告 |

结论：`DROP CASCADE` 后按 [03](./03-schema设计.md) 建表头–明细；计划需求经 FO 进入执行链；正式 SO 消耗并接管，交货只认 SO。
