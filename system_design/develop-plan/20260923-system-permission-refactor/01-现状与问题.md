**结论：** 现在的权限架构有 2 个严重漏洞和 4 个高风险问题，其中两个可以被直接利用：任何登录用户都能给自己分配 ADMIN 角色；JWT 也能被伪造来冒充任意用户。所以我不建议在现有结构上补 `data_permissions` 和代理，而是分四步走：

1. **上线前先修补（P0）。**
2. **重构 ADM 权限域。** 参照 SAP、D365、金蝶的共同做法，改成"系统定义的权限目录 × 带组织范围的角色指派 × 少量行规则"。
3. **工作代理分两阶段。** 先做"权限代理"（运行时派生授权，不复制数据）；等有了审批流，再做"任务代理"。
4. **两份草稿表直接废弃。**

## 一、现有架构漏洞评估

| 等级 | 问题 | 位置 | 后果 |
|---|---|---|---|
| 严重 | 授权管理 API 没有权限校验 | `UserRoleController`、`RolePermissionController` | 任意登录用户可自授 ADMIN，或给任意角色加权限 |
| 严重 | JWT issuer 没有白名单 | `MultiTenantJwtDecoder` | 可伪造 token 冒充任意用户；有 SSRF；解码器缓存无上限 |

## 二、两份草稿为什么不能作为依据

- **粒度放错了地方。** 两张表都挂在 `role_permission_id`（角色 × 菜单 × 动作）上。资料范围本质上是"这个人在哪些组织工作"：挂在角色权限上，同一个角色就没法在不同工厂复用，只能按工厂复制角色。一次休假代理也得逐条委派几十上百个 role_permission。
- **外键指向会被删掉重建的行。** `updateRolePermission` 每次保存都先 `deleteAllInBatch` 再重建 `role_permissions`，ID 会变。外键又是 `ON DELETE NO ACTION`，一旦有了范围或代理数据，编辑角色权限就会因为外键报错。
- **`conditions jsonb` 没有结构。** 无法校验，无法建索引，转成 SQL 有注入风险，也回答不了"谁能看到这张单"。
- **`scope_option_id` 语义不受控。** 它取自租户可编辑的 `option_values`，会重复"目录被篡改"的问题。
- **唯一键表达力不够。** `(tenant_id, role_permission_id)` 只允许一个范围，写不出"工厂 A 全部 + 工厂 B 仅本人"这种规则。
- **代理表的规则缺失。** 不检查委托人是否真的持有这项权限（等于能被拿来"洗"权限），没有范围，没有禁止转授，没有撤销人和撤销时间，也不做 SoD 检查。
- **代码里没人用。** `DataPermission`、`RolePermissionDelegation`、`RoleHierarchy` 三个实体没有任何引用。`role_hierarchy` 建议一起删掉：角色继承会让 SoD 分析变难，要复用的话用"复制角色模板"就够了。

## 三、规范 ERP 怎么做

| 系统 | 功能权限 | 资料权限 | 代理 |
|---|---|---|---|
| SAP S/4HANA | 角色 = 事务 + 权限对象，审批有独立权限对象 | 权限对象里带组织字段（公司代码、工厂、采购组织、库位）；主角色按组织值派生出子角色 | 工作流替代人（有效期、任务范围）；紧急权限 Firefighter |
| Oracle EBS / Fusion | Job Role → Duty → Privilege | 按业务单元、账簿、库存组织划分的数据角色；MOAC | Vacation Rule 按单据类型转交待办；Proxy 代理并留痕 |
| Dynamics 365 F&O | Role → Duty → Privilege | 指派角色时"分配组织"到法人；XDS 行级策略 | 工作流委派（按工作流类型 + 日期）；SoD 规则 |
| Odoo | Groups + 模型 ACL | Record Rules（每个模型的域条件、多公司规则） | — |
| 金蝶 / 用友 / 鼎新 | 功能权限，审核和反审核独立 | 用户 × 组织 × 角色；本人/本部门/下级/指定组织；字段权限 | 工作流委托、代理人（期间、单据范围），签核时显示"代理" |

这些系统的共同点，就是这里说的"规范"：

1. 权限目录由系统定义，租户只能组合角色，不能改目录本身。
2. 动作要细分。提交、审核、反审核、过账、冲销、作废、导出、打印都要单独授权。
3. 资料权限以组织维度为主，范围放在"用户 × 角色 × 组织"这层指派上，再补少量行规则（本人、本部门）。
4. 默认拒绝。没有范围就看不到资料，"全部"必须显式授予。
5. 代理有期间、有范围、不能转授，全程留下"谁代谁"的记录，而且不能拿代理绕开职责分离。
6. 安全配置的变更全部审计，并支持定期权限复核。

## 四、资料权限：方案比较与推荐

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 角色级范围 | 每个角色一个范围：全部/本部门/本人 | 最简单 | 不同工厂要复制角色；不支持公司、工厂、仓库多维 |
| B 角色权限级 JSON 条件（草稿的方向） | 每个角色 × 菜单 × 动作挂一段条件 | 看起来灵活 | 配置量爆炸；没法校验和复核；有注入风险 |
| **C 范围挂在指派上（推荐）** | 角色只管"能做什么"，指派决定"在哪些组织做"，资源在代码里声明自己的组织字段 | 角色可复用；结构化、可审计；和代理自然衔接 | 需要重构指派模型和查询注入点 |

**推荐方案 C，把三个层面分开：**

- **平台层：** 租户、权限目录、菜单模板，只接受平台专用身份。
- **租户安全管理层：** 角色、指派、范围、代理、SoD。
- **业务执行层：** 注解加资料范围。

某个用户对某资源做某动作时，能覆盖的范围等于：他所有"含这项权限"的指派，各自"组织范围 ∩ 行规则"后的并集。


**组织维度按层级往下推。** 公司推到工厂，工厂推到仓库；公司也推到部门。没配下级维度时继承上级的范围。一条范围都没配，就等于没有资料权限（fail-closed）。

`HOME` 取 `users.company_id/factory_id/department_id`。这样用户换了工厂，范围会自动跟着变。

各单据需要的维度字段现在基本都已经有了，不用加列：

| 单据类别 | 组织维度（现有字段） | 行规则字段 |
|---|---|---|
| FI：凭证、AP/AR、付款、固定资产 | `company_id` | `created_by` |
| PO、收货、调拨、生产、出货 | `factory_id` | `created_by` |
| 请购、领料 | `factory_id` + `department_id` | `requester_id`、`created_by` |
| 库存余额、库存交易、盘点 | `warehouse_id` | — |
| 销售订单、销售预测 | `company_id` | `sales_person_id` |

运行时的范围求值大致是这样：

```java
DataScope resolve(Principal u, Resource r, Action a) {
    List<Grant> grants = u.activeGrants().stream()     // 直接指派 + 有效代理派生；已排除停用/过期
            .filter(g -> g.permissions().contains(r.code(a)))
            .toList();
    if (grants.isEmpty()) return DataScope.DENY;
    List<Predicate> anyOf = new ArrayList<>();
    for (Grant g : grants) {
        OrgSet org   = expand(g.scopes(), r.dimensions());   // 层级下推，HOME 动态解析
        RowRule rule = g.role().rowRule(r, a.access());      // 缺省 ALL
        Long owner   = g.isDelegated() ? g.delegatorId() : u.userId();
        if (org.isAll() && rule == RowRule.ALL) return DataScope.UNRESTRICTED;
        anyOf.add(and(org.predicate(r), rule.predicate(r, owner)));
    }
    return DataScope.anyOf(anyOf);
}
```

**需要注入校验的地方：**

1. **功能权限。** 继续用 `@PreAuthorize`，但启动时要校验权限码都存在于 `sys_permissions`。另加一条架构测试：所有 handler 都必须声明授权，从而做到默认拒绝。
2. **查询出口。** 分页、详情、子表、导出、打印、下拉、报表、单据链，都要带资料范围。
   - 建议在查询端点上标 `@DataScope(resource)`，由切面只对该实体启用 Hibernate Filter，不影响其他实体的内部查询。
   - Hibernate 6.5 起，`@FilterDef(applyToLoadByKey = true)` 可以让 `findById` 也被过滤，这点要用集成测试确认。
   - 为数不多的原生 SQL 需要手工拼谓词。
3. **动作入口。**
   - 修改、审核、过账等动作，在服务里显式调用 `dataScope.check(resource, action, entity)`。
   - 新建时，请求里的 `factoryId/warehouseId/companyId` 必须落在写入（WRITE）范围内。
   - 批量操作查到的条数比请求 ID 少，就直接拒绝。
   - 内部跨模块联动不做过滤：授权只在"用户操作的那张单"上完成，这和 SAP 一致。
4. **子表。** `putIfAbsent(parentId)` 改成服务端强制覆盖；`DynamicSpecifications` 加可过滤字段白名单。
5. **下拉选项。** 公司、工厂、仓库、部门的选项缓存现在 key 只有 tenantId，保持按租户缓存，返回前再按用户范围过滤。
6. **异步任务。** `ExportJobEventListener` 已经把 `Authentication` 传进了执行线程，所以范围必须从 `Authentication` 推导，不能依赖 request 作用域的 bean。
7. **职责分离。** 审核和过账统一校验：实际操作人和"被代理的委托人"都不能是制单人。是否强制按单据类型做成租户参数，FI 默认强制。

## 五、工作代理：方案比较与推荐

| 方案 | 做法 | 评价 |
|---|---|---|
| A 账号代理 | 代理人直接以委托人身份登录操作 | 审计混乱，拿到全部权限，不采用 |
| **B 权限代理（第一期推荐）** | 在期间内，把委托人的部分角色连同组织范围派生给代理人 | 不需要审批流就能落地，和资料权限模型一致 |
| C 任务代理（第二期） | 审批待办按单据类型转给代理人，代理人用自己的权限处理 | 最规范（SAP、Oracle、D365 都是这样），但依赖审批流，现在系统还没有 |

**权限代理必须守住的规则：**

- **只能代理自己直接持有的角色。** 只能代理委托人直接持有、且标记为可代理的角色，范围沿用委托人的指派。这是运行时计算的：委托人一旦失去角色或被停用，代理立刻同步失效。
- **不能转授。** 派生出来的授权不再参与代理计算。
- **期间必填、有上限**（例如不超过 90 天）。到期由运行时判断；权限缓存的过期时间不能晚于最近一次代理生效或结束的时刻。
- **有些权限不能代理：** 安全管理类（角色、指派、代理、SoD 配置）和平台权限。
- **建立代理时做 SoD 检查。** 用"代理人自己的权限 ∪ 代理来的权限"去检查，有冲突就阻断，或者要求审批并记录理由。
- **"本人"指委托人。** 在代理授权下，行规则里的"本人"指委托人，因为代理人处理的是委托人的工作。
- **留痕。** 通过代理完成的动作要记录 `actor_id`、`on_behalf_of_id`、`delegation_id`。如果代理人自己本来就有这项权限，就不算代理操作。
- **建立与撤销。** 由委托人本人或安全管理员建立，可配置成需要主管核准；通知双方，可以提前撤销。

```sql
CREATE TABLE lychee_erp.work_delegations (
    id bigserial PRIMARY KEY, tenant_id bigint NOT NULL,
    delegator_id bigint NOT NULL, delegatee_id bigint NOT NULL,
    valid_from timestamptz NOT NULL, valid_to timestamptz NOT NULL,
    role_mode varchar(20) NOT NULL,           -- ALL_DELEGABLE / SELECTED
    status    varchar(20) NOT NULL,           -- PENDING / ACTIVE / REVOKED（过期按时间判断）
    reason text,
    created_by bigint NOT NULL, approved_by bigint, approved_at timestamptz,
    revoked_by bigint, revoked_at timestamptz,
    CHECK (delegator_id <> delegatee_id), CHECK (valid_to > valid_from)
);

CREATE TABLE lychee_erp.work_delegation_roles (
    delegation_id bigint NOT NULL REFERENCES lychee_erp.work_delegations(id),
    role_id bigint NOT NULL,
    PRIMARY KEY (delegation_id, role_id)
);
```

## 六、实施路线

**P0 上线前修补（大多是单点改动）：**

- **JWT 与认证：**
  - 按"已配置的 Keycloak 地址 + 启用中的租户代码"做 issuer 白名单；
  - 校验 `aud/azp`；
  - 给解码器缓存设上限，并删掉打印 payload 的 debug 日志；
  - 删除实际不生效的 `realm_access.roles` 映射，避免将来 Keycloak 角色变成第二个授权来源。
- **补权限注解：** 给上面提到的 4 个控制器补上注解，并加一条"默认拒绝"的架构测试。
- **只取有效数据：** 生成权限快照时只取启用状态的用户、租户、角色、权限、菜单，以及 `is_active` 且未过期的指派。
- **审计与自授：** 审计字段改由服务端写入；禁止修改自己的角色指派。
- **租户管理：** 改为只允许平台身份操作。
- **冻结权限目录：** 菜单 `path` 和 `PERMISSION_ACTION` 选项值不能由租户修改。
- **拆分动作：** 审核、反审核、过账、冲销、作废拆成独立动作，并和前端 `WorkflowActions` 对齐；FI 凭证和付款先上"制单 ≠ 审核"。同时更新 `.cursor/rules/backend-development.mdc` 第 79 行只列了 CRUD 的约定。

**P1 资料权限（中到大）：**

- 权限目录代码化，菜单改为系统级并引用权限码；
- 建好指派、范围、行规则三张表；
- 实现 `DataScopeService`，以及查询和动作两类注入点；
- 前端改成"资源 × 动作"矩阵，指派页加组织范围选择；
- 为每类资源建一套"受限用户"的集成测试矩阵。

**P2（中）：** 权限代理、SoD 规则、安全配置审计日志、带 `on_behalf_of` 的单据动作日志。

**P3（大）：**

- 审批流与任务代理；
- 字段权限：单价、成本用 `view_cost` 控制，接口响应和导出都要脱敏；
- PostgreSQL RLS，作为租户隔离的纵深防御；
- 定期权限复核报表。

## 七、需要你们拍板的几点

下面几点是业务取舍，我给了默认建议，有不同意见再调整：

- **组织范围挂在哪里：** 默认挂在"角色指派"上。简化版是"用户级范围"，配置更少，但同一个人不能在不同工厂担任不同角色。
- **主数据是否隔离：** 物料、供应商、客户，第一期默认在租户内共享，客户可以选用"本人业务员"规则。
- **能否自己制单自己审核：** 小团队是否允许同一个人制单并审核？默认 FI 强制禁止，其他单据按租户参数。
- **代理是否需要核准：** 默认委托人自己建立就生效，包含高风险权限时需要主管核准。
