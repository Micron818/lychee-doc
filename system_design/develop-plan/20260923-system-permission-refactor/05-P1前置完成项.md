## 1. 来源组织一致性（2026-10-06）

一张单不能吃进另一厂或另一公司的来源。多公司、多厂用户本来就能分别开单；缺的是防止**同一张单**混入别的组织。这是业务校验，不是资料权限。校验放在回写数量、分配量和落行之前，不匹配抛 `ValidationException`。

| 规则 | 入口 |
|---|---|
| 来源工厂 = 单据头工厂 | 收货 ← 采购订单、收货 ← 委外订单；领料 ← 生产订单（含单行）；调拨 ← 委外组件；领料 ← 出货的单行（与批量相同） |
| 来源公司 = 工厂所属公司 | 出货 ← 销售订单（同时要求客户一致）；工厂订单 ← 销售订单、工厂订单 ← 销售预测 |
| 请求的计划订单必须全部命中 | 委外订单拉计划订单。外厂或无效 ID 不再被静默丢掉 |
| 指定仓库属于单据工厂 | 收货（含手工行；非库存物料仍可空仓）、调拨的调出仓与调入仓、生产领料。委外调入仓只取本厂该供应商的仓 |

文案已补英文、简体中文、越南文。单元测试覆盖上表各类入口：组织不一致则拒绝且不回写；组织一致则通过该校验。

未做：资料范围、写守卫、Hibernate 过滤器。来源组织对齐之后，资料权限只需判断目标单头。

## 2. 采购与委外的未结案检查不再走原生 SQL（2026-10-12）

改公司国家码时，`CompanyServiceImpl` 经 `RemoteScmOpenDocumentService` 确认该公司没有未结案的采购订单和委外订单。原先 `PurchaseOrderRepository`、`OutsourceOrderRepository` 的 `existsOpenByCompanyId` 是 `nativeQuery = true`，并写死 `lychee_erp.` 表名。这两处已删除。

检查改为两步，都走 Spring Data 派生查询：

1. `FactoryRepository.findByCompanyId` 取出该公司的工厂。没有工厂则视为没有未结案单。
2. `existsByFactoryIdInAndStatusNot(factoryIds, CLOSED)` 判断这些工厂下是否还有未结案采购订单或委外订单。

实现在 `RemoteScmOpenDocumentServiceImpl`。单元测试覆盖公司为空、没有工厂、存在未结案单、全部已结案。

[04-P1资料权限设计-收敛稿.md](./04-P1资料权限设计-收敛稿.md) 第二节把这两处列为「保持原生 SQL、不受控」的例外，[03-P1资料权限设计.md](./03-P1资料权限设计.md) 的 `existsOpenByCompanyId` 同此。那两处正文不改，以本节为准：方法已不存在，不再是原生 SQL 例外。

语义不变：这是改国家码前的完整性检查，必须看见该公司全部工厂、全部未结案单。过滤器落地后，`hasOpenPurchaseOrders` 与 `hasOpenOutsourceOrders` 不能被当前用户的工厂范围收窄；否则只持有部分工厂的人可以在其他工厂仍有未结案单时改掉国家码。

`OrderPeggingRepository` 的递归追溯、`SysDocSequenceRepository` 的序号递增、税类与税码的跨表存在检查、`MaterialBomReferenceRepository` 仍使用原生 SQL，不在本次范围内。
