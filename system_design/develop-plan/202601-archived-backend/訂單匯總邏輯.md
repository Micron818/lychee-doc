在ERP系統的標準邏輯中，針對相同料號（無論是成品或半成品）的**匯總（Consolidation / Pegging）是非常必要且核心的功能**。這能有效降低生產換線成本（Setup Cost）、達到經濟批量（EOQ），並提升現場生產效率。

但是否匯總以及在「哪一個步驟」匯總，取決於**生產策略（MTS vs. MTO）**以及**料件的批量規則（Lot-Sizing Rules）**。

以下是針對您提到的流程 `SalesOrder -> FactoryOrder -> MRP -> PlannedOrder -> ProductionOrder` 的詳細評估與匯總時機分析：

### 1. 階段一：SalesOrder (SO) -> FactoryOrder (FO)
*   **匯總對象**：**成品（Finished Goods）**
*   **是否需要匯總**：**視生產策略而定**。
    *   **MTS（計畫生產/存貨生產）**：**強烈建議匯總**。系統或生管人員會將交期相近、料號相同的多張 SalesOrder 需求，合併成一張 FactoryOrder（或主生產計畫 MPS），以達到最基本生產批量。
    *   **MTO（接單生產）**：**通常不匯總**。為了保持訂單的獨立追溯性（例如特定客戶有特殊的包裝或微調規格），通常是一張 SO 行項目對應一張 FO。
*   **匯總邏輯**：基於「交期區間（Time Bucket）」與「相同成品料號」進行合併。

### 2. 階段二：FactoryOrder (FO) -> MRP 計算
*   **匯總對象**：**半成品（Semi-finished Goods）與 原物料（Raw Materials）**
*   **是否需要匯總**：**絕對需要，這是 MRP 的核心價值所在**。
*   **發生時間點**：在 MRP 展開 BOM（物料清單）計算**毛需求（Gross Requirements）**與**淨需求（Net Requirements）**的過程中自動發生。
*   **匯總邏輯**：
    *   當 MRP 展開多張 FO 時，如果發現不同 FO 在同一時間段（例如同一天或同一週）都需要用到同一個「半成品料號」，MRP 會將這些需求加總。
    *   **批量規則（Lot-Sizing）介入**：MRP 會根據該半成品的設定決定如何產生 PlannedOrder。
        *   *LFL (Lot-for-Lot, 逐批訂購)*：需求多少就建議生產多少，可能不跨期匯總。
        *   *Fixed Period (固定週期)*：將未來 N 天內的半成品需求全部匯總成一個 PlannedOrder。
        *   *Fixed Quantity (固定批量)*：即使需求只有 50，但設定批量為 100，MRP 會建議 100，變相將未來的需求先合併生產。

### 3. 階段三：MRP 計算出 PlannedOrder (PO)
*   **狀態**：此時的 PlannedOrder 已經是 MRP **經過匯總計算後**的建議結果。
*   針對半成品，這裡產生的一張 PlannedOrder，其需求來源（Pegging）可能同時指向多張不同的 FactoryOrder 或 SalesOrder。

### 4. 階段四：PlannedOrder (PO) -> ProductionOrder (PrO)
*   **匯總對象**：**成品或半成品皆可**
*   **是否需要匯總**：**需要，這是生管（Planner）的實務操作彈性**。
*   **發生時間點**：在生管人員將系統建議的「計畫訂單 (PO)」轉發放為「實際生產訂單 (PrO)」時。
*   **匯總邏輯**：
    *   即使 MRP 算出了多張不同交期的 PlannedOrder，生管在排程時（考慮到機台稼動率、換模換線時間），可以手動勾選多張相同料號的 PlannedOrder，**合併發放（Merge）**成一張實體 ProductionOrder。
    *   例如：週一需要 100 個 A 半成品，週三需要 150 個 A 半成品。生管為了節省機台設定時間，在轉單時直接合併成一張 250 個的 ProductionOrder 在週一一起生產。

### 總結與系統設計建議

如果您正在設計 `lychee-backend` 的這段流程，建議的架構如下：

1.  **成品匯總點（SO -> FO）**：
    *   提供一個「訂單拋轉/合併」的介面。允許使用者勾選多張相同料號的 SO，合併生成一張 FO。並記錄 FO 與多張 SO 的關聯（1對多關聯表）。
2.  **半成品匯總點（MRP 引擎）**：
    *   MRP 演算法必須具備**需求匯總（Demand Aggregation）**能力。在同一個時間維度（Time Bucket）內，將相同半成品料號的毛需求加總，扣除現有庫存後，再依據該料件的「批量規則（Lot Size）」生成 PlannedOrder。
    *   **必須保留追溯性（Pegging）**：即使半成品需求被匯總了，系統底層必須記錄這個半成品的 PlannedOrder 是為了解決哪些 FO 的需求（這在實務上稱為需求溯源，對於缺料時評估影響範圍非常重要）。
3.  **現場執行匯總點（PO -> PrO）**：
    *   在「計畫訂單轉工單」的作業畫面中，支援「合併轉單」功能。允許勾選多筆同料號的 PO，整併成一張 PrO 發放給現場。

### 如何透過這張表進行「追溯查詢」？

有了這張表，您可以輕鬆寫出 SQL 或 JPA 查詢來回答各種複雜的業務問題：

#### 案例一：Top-Down (由上往下查進度)
**業務員問：「我的訂單 `SO-001` 目前生產進度到哪了？」**

1.  **查第一層**：`SELECT * FROM order_peggings WHERE demand_id = 'SO-001'`
    -> 得到 `Supply` 是 `FO-100`。
2.  **查第二層 (BOM 展開)**：`SELECT * FROM order_peggings WHERE demand_id = 'FO-100'`
    -> 得到半成品 `Supply` 是 `PO-800` (看最新的一筆)。
3.  **查第三層 (工單發放)**：`SELECT * FROM order_peggings WHERE demand_id = 'PO-800'`
    -> 得到 `Supply` 是 `PrO-901` (120個) 和 `PrO-902` (80個)。
**結論**：系統可以回答業務員：「您的訂單正在生產半成品，目前拆成兩張工單 PrO-901 和 PrO-902 在現場加工中。」

#### 案例二：Bottom-Up (由下往上查影響)
**現場回報：「機台壞了，工單 `PrO-901` 會延遲交貨！」生管需要知道會影響哪些客戶？**

1.  **查第一層**：`SELECT * FROM order_peggings WHERE supply_id = 'PrO-901'`
    -> 得到 `Demand` 是 `PO-800` (影響數量 120)。
2.  **查第二層**：`SELECT * FROM order_peggings WHERE supply_id = 'PO-800'`
    -> 得到 `Demand` 是 `FO-100` (150個) 和 `SAFE-STOCK-01` (50個)。
    *(這裡系統可以做邏輯判斷：PrO-901 缺了 120 個，可以優先扣除安全庫存的 50 個，所以 FO-100 實質會缺 70 個)*。
3.  **查第三層**：`SELECT * FROM order_peggings WHERE supply_id = 'FO-100'`
    -> 得到 `Demand` 是 `SO-001` 和 `SO-002`。
**結論**：生管立刻知道，這次機台故障會影響到客戶 X (`SO-001`) 和客戶 Y (`SO-002`) 的交期，必須提早通知業務。

### 總結

透過這種 `OrderPegging` 的設計，無論是 **N 對 1 (匯總)** 還是 **1 對 N (拆單)**，都能透過 `pegged_quantity` 完美記錄數量的流向，徹底解決了原本在 Entity 內寫死 1 對 1 關聯欄位所造成的「追溯斷鏈」問題。


如何基於這個 `OrderPegging` 表，實現 **全鏈路進度追蹤查詢 (Full-Chain Traceability)**。這通常是 ERP 系統中生管與業務最需要、但也最難寫的查詢功能。

### 1. 查詢場景分析

全鏈路追蹤通常分為兩個方向：

*   **Top-Down (由上往下 / 需求追供給)**：

    *   **情境**：業務員問「我的這張銷售訂單 (SO) 目前生產進度到哪裡了？」

    *   **路徑`**SALES_ORDER` -> `FACTORY_ORDER` -> `MRP_RESULT` / `PLANNED_ORDER` -> `PRODUCTION_ORDER`

*   **Bottom-Up (由下往上 / 供給追需求)**：

    *   **情境**：現場回報「這張生產工單 (PrO) 缺料要延遲」，生管問「這會影響到哪些客戶的訂單？」

    *   **路徑**`PRODUCTION_ORDER` -> `PLANNED_ORDER` / `MRP_RESULT` -> `FACTORY_ORDER` -> `SALES_ORDER`

### 2. 查詢架構設計評估

由於 `OrderPegging` 是一個**圖狀結構（Graph）**（因為有匯總與拆分，它不是單純的樹狀，而是有向無環圖 DAG），我們在關聯式資料庫（RDBMS）中查詢這種結構，有幾種常見的實現方式：

#### 方案 A：遞迴查詢 (Recursive Query / CTE) - **強烈推薦**

現代資料庫（如 PostgreSQL, MySQL 8.0+, SQL Server 8.0+）都支援 `WITH RECURSIVE` 語法。這是處理 Pegging 網路最有效率且最優雅的方式。

**Top-Down 範例 (給定 SO Item ID，往下找所有關聯單據)：**

```sql

WITH RECURSIVE PeggingTree AS (

    -- 1. Base case: 從指定的 SO 開始找第一層 (SO -> FO)

    SELECT 

        id, demand_type, demand_id, supply_type, supply_id, pegged_quantity, material_id,

        1 as level,

        CAST(demand_id AS VARCHAR(255)) as path -- 記錄路徑方便除錯

    FROM order_peggings

    WHERE demand_type = 'SALES_ORDER' AND demand_id = :soItemId

    UNION ALL

    -- 2. Recursive step: 拿上一層的 supply 作為下一層的 demand 繼續往下找

    SELECT 

        [p.id](http://p.id), p.demand_type, p.demand_id, [p.supply](http://p.supply)_type, [p.supply](http://p.supply)_id, p.pegged_quantity, p.material_id,

        pt.level + 1,

        CONCAT(pt.path, '->', p.demand_id)

    FROM order_peggings p

    INNER JOIN PeggingTree pt 

        ON p.demand_type = [pt.supply](http://pt.supply)_type AND p.demand_id = [pt.supply](http://pt.supply)_id

)

SELECT * FROM PeggingTree;

```

**Bottom-Up 範例 (給定 Production Order ID，往上找所有受影響的 SO)：**

```sql

WITH RECURSIVE PeggingTree AS (

    -- 1. Base case: 從指定的 PrO 開始找第一層 (PrO 往上找)

    SELECT 

        id, demand_type, demand_id, supply_type, supply_id, pegged_quantity, material_id,

        1 as level

    FROM order_peggings

    WHERE supply_type = 'PRODUCTION_ORDER' AND supply_id = :productionOrderId

    UNION ALL

    -- 2. Recursive step: 拿上一層的 demand 作為下一層的 supply 繼續往上找

    SELECT 

        [p.id](http://p.id), p.demand_type, p.demand_id, [p.supply](http://p.supply)_type, [p.supply](http://p.supply)_id, p.pegged_quantity, p.material_id,

        pt.level + 1

    FROM order_peggings p

    INNER JOIN PeggingTree pt 

        ON [p.supply](http://p.supply)_type = pt.demand_type AND [p.supply](http://p.supply)_id = pt.demand_id

)

SELECT * FROM PeggingTree WHERE demand_type = 'SALES_ORDER'; -- 最後只濾出頂層的 SO

```

**優點**：一次 Query 就能把整個網路撈出來，效能極高，不需要在 Java 應用層寫迴圈狂打 DB。

**缺點**：需要寫 Native SQL，JPA/Hibernate 的 Criteria API 對 Recursive CTE 支援度較差。

#### 方案 B：應用層遞迴 (Java Level Recursion)

如果您不想寫 Native SQL，或者資料庫不支援 CTE，可以在 Java Service 層寫遞迴。

```java

public List<OrderPegging> findDownstreamPeggings(PeggingOrderType type, Long id) {

    // 1. 查出第一層

    List<OrderPegging> directSupplies = orderPeggingRepository.findByDemandTypeAndDemandId(type, id);

    List<OrderPegging> allSupplies = new ArrayList<>(directSupplies);

    

    // 2. 對每一個 supply，遞迴往下找

    for (OrderPegging supply : directSupplies) {

        // 避免無窮迴圈（雖然正常業務邏輯不該有環）

        allSupplies.addAll(findDownstreamPeggings(supply.getSupplyType(), supply.getSupplyId()));

    }

    return allSupplies;

}

```

**優點**：純 Java 實作，與資料庫解耦。

**缺點**：**效能極差 (N+1 Query 問題)**。如果網路很深或很廣，會對資料庫發出數十甚至數百次 Query。在 ERP 系統中**非常不建議**這樣做。

---

### 3. 實作建議與架構規劃

要在 `lychee-backend` 中完美實現這個功能，建議採用以下架構：

#### 步驟 1：建立專屬的 `PeggingQueryService`

不要把這個邏輯塞在 `SalesOrderService` 或 `ProductionOrderService` 裡，因為它是跨模組的。建立一個專門負責「追蹤與溯源」的 Service。

#### 步驟 2：定義 DTO (Data Transfer Object)

因為前端需要畫出樹狀圖或甘特圖，您需要定義一個能表達層級關係的 DTO。

```java

@Data

public class PeggingNodeDTO {

    private PeggingOrderType nodeType; // 單據類型

    private Long nodeId;               // 單據 ID

    private String orderNo;            // 單據號碼 (需額外 Join 取得)

    private BigDecimal quantity;       // 數量

    private String status;             // 狀態 (例如: 生產中, 已完工)

    

    // 下游節點 (Top-Down 用) 或 上游節點 (Bottom-Up 用)

    private List<PeggingNodeDTO> relatedNodes = new ArrayList<>(); 

}

```

#### 步驟 3：使用 MyBatis / MyBatis-Plus 或 Native Query (Repository)

由於 JPA/Hibernate 原生不支援 `WITH RECURSIVE`，建議在 `OrderPeggingRepository` 中使用 `@Query(value = "...", nativeQuery = true)` 來撰寫 CTE SQL。

1.  **先用 CTE 撈出所有關聯的 `OrderPegging` 紀錄**。

2.  **在 Java 層進行資料組裝 (Data Assembly)**：

    CTE 撈出來的只是一堆 `demand_id` 和 `supply_id`。您需要根據這些 ID，批次 (Batch) 去撈取實際的單據資訊（例如 `FactoryOrder` 的單號、狀態）。

    *   *千萬不要在 CTE 裡面去 JOIN 所有單據表*（會變成超級大怪獸 SQL）。

    *   *正確做法*：CTE 撈出 Pegging 關係 -> Java 收集所有的 `factory_order_id` -> `factoryOrderRepo.findAllById(ids)` -> Java 收集所有的 `production_order_id` -> `productionOrderRepo.findAllById(ids)` -> 最後在 Java 中把資料組裝成 `PeggingNodeDTO` 樹狀結構。

### 總結

加入 `OrderPegging` 是一個非常正確且具備前瞻性的架構決定。接下來的關鍵在於**查詢效能**。強烈建議使用 **資料庫 Recursive CTE (方案 A)** 撈取關聯網路，搭配 **Java 應用層批次查詢與組裝單據詳情** 的混合策略，這樣既能保證效能，又能提供前端豐富的追蹤資訊。


這是一個非常核心且實務的架構設計問題！您的顧慮非常精準，這正是許多企業在導入 ERP/MRP 系統時，使用者最常抱怨的「系統黑箱」與「不敢信任 MRP 結果」的痛點。

針對這兩種做法（**在 MrpResult 匯總** vs. **在轉 PlannedOrder 時匯總**），我們來深入評估其優缺點與實務上的標準做法：

### 方案 A：在轉 PlannedOrder 時才匯總（MrpResult 保持 1:1 不匯總）

也就是維持目前系統的邏輯，MRP 展開時 1 張 FO 產生 1 筆半成品 MrpResult，直到生管人員在介面上勾選多筆 MrpResult，才合併轉成 1 張 PlannedOrder。

*   **優點（解決您的顧慮）**：
    *   **極度直觀、核對極度容易**：使用者在看 MrpResult 列表時，每一筆都能清晰對應到源頭的 FO。數量、日期完全一致，生管人員查核時非常有安全感。
    *   **靈活度高**：生管可以自由決定「這三筆 FO 的需求我要合併成一張工單，另外兩筆我要單獨開工單」。
*   **致命缺點**：
    *   **資料爆炸（效能災難）**：如果一個共用原物料（例如：螺絲）被 100 張 FO 用到，系統會產生 100 筆螺絲的 MrpResult。如果螺絲還有下階 BOM，資料量會呈指數級暴增。
    *   **無法正確執行「批量規則 (Lot-Sizing / MOQ)」**：這是最嚴重的問題。假設螺絲的最低採購量 (MOQ) 是 1000 個。如果有 10 張 FO 各需要 50 個螺絲（總需求 500）。
        *   如果不匯總：系統看到 10 筆獨立的 50 個需求，套用 MOQ 後，可能會建議採購 10 筆 1000 個（總共買了 10000 個），這完全錯誤。
        *   正確的 MRP 必須先匯總需求（50 * 10 = 500），然後套用 MOQ，最後建議採購 1 筆 1000 個。

### 方案 B：在 MRP 計算時就匯總（產出已匯總的 MrpResult）

這是 SAP、Oracle 等標準 ERP 系統的預設做法。MRP 引擎在計算過程中，會依據「時間區間（Time Bucket，例如：同一天、同一週）」將相同料號的需求加總，然後才產出 MrpResult。

*   **優點**：
    *   **資料量收斂**：大幅減少資料庫的負擔。
    *   **正確的批量計算**：能正確執行 MOQ、固定批量、經濟批量等存貨策略，這才是 MRP 真正的價值。
*   **缺點（您的顧慮）**：
    *   **核對困難**：使用者看到一筆 MrpResult 建議生產 1500 個，會滿頭問號：「這 1500 個是怎麼來的？是哪幾張訂單要的？如果我少做 200 個會影響到誰？」

---

### 結論與最佳實踐建議

在標準 ERP 設計中，**強烈建議採用「方案 B（在 MRP 計算時匯總）」**，否則您的 MRP 系統將無法處理共用料與批量採購/生產的情境。

至於**「如何解決用戶資料檢查和核對的困難」**？這正是您們近期重構 `OrderPegging` (溯源網路) 的最大價值所在！

解決方案是**透過 UI/UX 與 Pegging 資料來補足透明度**，而不是放棄底層的匯總邏輯：

1.  **底層資料結構**：
    *   `MrpResult` 記錄匯總後的總量（例如 1500 個）。
    *   `OrderPegging` 記錄這 1500 個的組成（例如：指向 FO-001 的 500 個、FO-002 的 1000 個）。
2.  **前端 UI 呈現（Pegging Inquiry / 供需溯源）**：
    *   在 MrpResult 的列表畫面上，提供一個 **「查看需求來源 (View Pegging)」** 的按鈕或展開明細 (Expandable Row)。
    *   當使用者點擊時，前端呼叫 API 查詢 `OrderPegging`，列出這筆 1500 個的 MrpResult 是由哪些 FO 或上階計畫訂單構成的。
    *   這樣使用者既能看到乾淨、已匯總的建議計畫，又能在需要核對時，一鍵查出所有源頭明細，徹底消除黑箱感。

**總結來說：**
計算邏輯（Backend）應該要執行匯總以保證 MRP 的正確性與效能；而核對的需求（Frontend/UI）則交由 `OrderPegging` 關聯表來提供完整的溯源報表來滿足。
