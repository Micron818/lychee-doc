# 02 — 目标架构

## 1. 结论

新报表的 PDF 由独立服务 `lychee-pdf` 生成：

| 层 | 选择 |
|----|------|
| 版式 | HTML5 + CSS（`@media print`、`@page`） |
| 渲染 HTML | TypeScript。输出不含脚本的完整文档 |
| 出 PDF | Playwright 驱动的 headless Chromium，`page.pdf()` |
| 取数 | 仍在业务模块的 Java Service / `*PdfRenderer` |
| 调用方式 | 后端内网 HTTP。PDF 服务不对外发布端口 |
| 存量 PDF | 继续 `PdfRenderSupport`，按 [04-实施清单](./04-实施清单.md) 的顺序逐张迁 |

Playwright 的安装、镜像和 API 以 Node 为准，所以 PDF 服务用 TypeScript，不把 Chromium 嵌进 Spring。Umi 页面不承担版式：Ant Design 样式、登录态和异步请求不能进 PDF。

许可：Playwright 为 Apache 2.0，Chromium 为 BSD。

仓库、镜像、compose 服务名、配置前缀和日志里的这个进程都叫 PDF：`lychee-pdf`、服务名 `pdf`、`lychee.pdf.*`。用户侧仍称单据打印。Java 的 `*PrintService` 继续负责查询、校验和组装视图模型，PDF 服务不替代这些类。Chrome 打印预览、`iframe.print()`、存量目录 `templates/print/` 保持原名。

## 2. 请求路径

### 2.1 同步预览（不变的对外接口）

```text
前端 PdfPreviewSession
  → GET /{id}/pdf 或 POST /report/pdf     Bearer，:read
Java Controller
  → *PdfRenderer.render
       1. Service 查询、校验、解析名称
       2. 金额 / 日期 / 标签格式化成视图模型
       3. ChromiumPdfClient.render(templateId, model, PREVIEW, out)
            → POST http://pdf:3100/render
              头带 X-Trace-Id
       4. out 收成 PDF 字节返回
  → Content-Disposition: inline
前端 blob → iframe → print()
```

预览不建 `export_jobs`，不上传 OSS。

### 2.2 归档（有导出需求时）

与 [02-导出框架](../20260818-report/02-导出框架总体设计.md) 相同：`*PdfExportHandler.export` 调用**同一个** `*PdfRenderer`。Renderer 把 `OutputStream` 指到 `ExportJobExecutor` 的临时文件，客户端按 `EXPORT` 超时把 PDF 流写进去，再 `StorageService.upload`。下载仍是导出中心的 `GET /file`。客户端不把整份 PDF 收成 `byte[]`。

一张单据若同时有预览和归档，两个入口只允许共用一个 Renderer。禁止预览走 Chromium、归档仍走 openhtmltopdf。

### 2.3 PDF 服务内部

```text
POST /render
  → 校验令牌、模板 id、正文大小、可选的 X-Trace-Id
  → 等待队列（上限 8；已满则 503）
  → 信号量（同时只渲染 1 份）
  → 模板注册表中的 render(model) → HTML 字符串
  → 常驻 Browser.newContext（JavaScript 关闭）
  → page.setContent(html, { baseURL: 本服务 })
  → page.pdf(该模板声明的纸张与边距)
  → 关闭 context，返回 application/pdf
```

浏览器进程在服务启动时拉起，崩溃后重新拉起。按请求启动浏览器会给预览多加数秒，不采用。累计成功渲染 500 次后，等队列清空再关掉 Browser 并重新拉起，避免常驻进程把内存吃到 cgroup 上限。重启期间 `/health` 与 `/render` 都返回 503。

进程退出时关闭 Browser。PDF 服务不保存模型、不写 OSS、不记租户。

## 3. 代码放在哪里

```text
lychee-pdf                         新的独立 git 仓库，单独镜像
├─ src/server.ts                     HTTP、令牌、等待队列、信号量、浏览器生命周期
├─ src/pdf.ts                        Playwright：setContent + page.pdf
├─ src/templates/<id>.tsx            一张报表一个模板模块
├─ src/templates/registry.ts         templateId → 模板，禁止按路径读文件
├─ fonts/                            Noto Sans、Noto Sans SC（与后端现用文件相同）
├─ fixtures/<id>.json                本地改版式用的视图模型
└─ Dockerfile                        钉死的 Playwright 镜像 + Chromium

lychee-erp-common
└─ com.lychee.erp.common.export
   └─ ChromiumPdfClient              调用 PDF 服务；失败变成业务异常

lychee-erp-<领域>
└─ *PdfRenderer                       新报表改为调用 ChromiumPdfClient
                                      存量继续 PdfRenderSupport

lychee-frontend                      不新增打印页。新报表只加薄的 PdfPreview 适配
lychee-infra/deploy                  compose 增加 pdf 服务与内存限额
```

依赖方向：业务模块 → `ChromiumPdfClient`（common）→ PDF 服务。`lychee-erp-report` 仍然只依赖 common，不依赖 PDF 服务，也不依赖业务模块。PDF 服务不依赖任何 Java 模块。

`lychee-pdf` 不放进 `lychee-frontend` 仓库。前端镜像是 nginx 静态资源，和 Chromium 运行时不是同一个交付物。

## 4. 视图模型

Java 在调用 PDF 服务之前完成展示数据，模板只摆放字段。这和现行「模板不做格式化」的规则相同。

| 规则 | 说明 |
|------|------|
| 字段名 | camelCase，与 Jackson 序列化一致 |
| 金额、单价、数量、日期 | Java 格式化成字符串后再放入模型。金额用 `MoneyFormatSupport`，跟单据币别，不跟 UI locale |
| 静态标签 | 放进模型的 `labels`。`MessageService.labelsByPrefix` 按 `print.<单据>.` 一次装入，Renderer 不对每个标签各写一行 `getMessage`。模板不查 i18n 文件 |
| 枚举 | `MessageService` 按本次请求 locale 写成字段上的字符串，不进 `labels` |
| 空数据、混合币别、混合公司 | 在 Java 抛 `ValidationException`，不调用 PDF 服务 |
| 租户 | 模型里不出现 `tenantId`。查询仍走 JPA `@TenantId` |
| 实体 | 不把 Entity 序列化给 PDF 服务 |
| 图片 | 样品图经 OSS 缩成 JPEG 再嵌 data URI。公司 Logo 仍走原图 `toDataUri`，保留透明通道。PDF 服务不持有 OSS 密钥，也不访问 CDN |

图片走 data URI，是为了让 PDF 服务成为纯函数：同一份 JSON 在本地 Chrome 预览和在服务器出 PDF 的结果一致，样例文件可以离线打开。请求正文上限见 [03](./03-契约.md)。

公司 Logo 继续用现网 `StorageImageHelper.toDataUri`。除领料单外，现网单据都嵌了 `companyLogoDataUri`，常见是透明底 PNG。OSS `format,jpg` 会把透明区域填成黑色，所以 Logo 不走图片处理。Logo 体积小，第 2 张起的抬头不用改读取方式。

样品图（物料图、款式图）才走 OSS：`GetObject` 带 `x-oss-process=image/resize,m_lfit,w_{edge},h_{edge}/format,jpg/quality,q_80`。`edge` 由 Java 按该图在版式上的槽位决定（显示尺寸的 2 倍，并设上限）。返回字节做成 `data:image/jpeg;base64,...`。Java 不解码 WebP，也不用 ImageIO。OSS 处理失败时该图留空，不用原图顶上。`StorageService.open` 与 `toDataUri` 保持原样，处理参数走单独方法。

`MaterialImageHelper.resolvePrimaryImageDataUris` 仍给尚未迁移的 openhtmltopdf 用。新引擎另增一个方法，只改已经切到 Chromium 的调用点（委外单、工厂订单、销售订单报表）。

公司抬头、越南文名称等「与界面语言无关、按主数据 source locale」的字段，维持现行订购单的做法：Java 填好 `companyName` / `companyNameVi`，模板按有无值决定印不印。

## 5. 模板

一张模板导出一个模块：

```ts
export type PrintTemplate = {
  id: string; // 如 "wm/stock-issue"
  render(model: unknown): string;
  pdf: {
    width: string;  // 如 "210mm"；Letter 多联用 "216mm"
    height: string; // 如 "297mm" 或 "279mm"
    margin: { top: string; right: string; bottom: string; left: string };
    footer: boolean;
    measure: boolean; // 跨页要重复键列时为 true
  };
};
```

`render` 使用会转义文本的渲染方式（React `renderToStaticMarkup` 或同等实现），产出完整 HTML5 文档，CSS 内联在 `<style>`。用户备注、地址、名称禁止用未转义 HTML 插入。

样式约定：

- 字体：`font-family: 'Noto Sans', 'Noto Sans SC'`。`@font-face` 指向本服务的 `/fonts/...`，由 `setContent` 的 `baseURL` 解析。不依赖镜像里的系统字体，避免 Windows 开发机和 Linux 容器换行不一致。
- 纸张与边距以模板声明的 `pdf` 为准，交给 `page.pdf()`。CSS `@page` 的 size 与之一致。页码只放在 Playwright 的 `footerTemplate`（`pageNumber` / `totalPages`），模板 CSS 里不再写 `counter(page)`。`footer: true` 时，`margin.bottom` 留出页脚高度。`headerTemplate` / `footerTemplate` 不继承文档的 `<style>` 和 `@font-face`，只放 ASCII 的页码。禁止把中文、越南文或公司名写进页脚，容器不装系统 CJK 字体。多单合并仍是一次 `render`、一份 PDF，页码是整份连号，与现行 `counter(page) / counter(pages)` 相同。不按单从 1 重新计数，也不把多份 PDF 拼成一份。
- 表头每页重复用 `thead { display: table-header-group }`。一组不得拆开的行使用 `break-inside: avoid`。
- 文档内不放 `<script>`。最终出 PDF 的 context 关闭 JavaScript。`measure: true` 的测量轮次见 §6。
- 除本服务的字体和文档本身外，拦截其他网络请求。签名 URL、外链图片不会在打印时再抓一次。

本地改版式：`pnpm dev` 用 `fixtures/<id>.json` 打开同一 `render` 函数。Chrome 打印预览即版式验收。改列宽、字号、分页不需要启动 Spring。字段有增减时，先改 Java 模型和样例 JSON，再改模板。

## 6. 分页与合并单元格

Chromium 能正确处理同一页里的垂直居中、Flexbox 和 `white-space: nowrap`。一组明细跨到下一页时，HTML `rowspan` 仍可能只留在第一页或被截断。

Java 不知道分页落在哪一行，视图模型不带「续页重印」标记。需要跨页重复型号、色号、单号的模板把 `pdf.measure` 设为 true，由 PDF 服务在出 PDF 前测量并改 HTML。这不是把 `renderPaginatedPdf` 的 PDFBox 坐标循环搬过来。

测量只针对模板标出的格子：

- 每一行明细带 `data-pdf-row`。
- 跨页后要在新页重复的格子带 `data-pdf-repeat`（型号、色号、单号这类键）。同一页内的 rowspan 仍由模板按模型直接输出。
- 放得进一页的小组继续用 `break-inside: avoid`。高于一页的组不要套这个属性，按行拆开，新页第一行重复 `data-pdf-repeat` 的文字。

步骤：

1. 测量 context 使用打印介质。`emulateMedia({ media: 'print' })` 之后，DOM 仍是未分页的连续流，分页发生在 `page.pdf()` 内部。不能用元素 Y 坐标除以内容区高度。

   `viewport.width` 设成可打印区像素宽：`pdf.width − margin.left − margin.right`，按 `1mm = 96 / 25.4 px` 换算。默认视口 1280px 比 A4 可打印宽度宽，折行变少，测出的行高会偏小。

   服务脚本维护虚拟页游标 `cursorY`，按行高累加：

   - 内容区高度 = `pdf.height − margin.top − margin.bottom`。同一张表的第 1 页可用高度就是它，`thead` 在连续流里，高度算进 `cursorY`。
   - 当 `cursorY + rowHeight` 超过当前页可用高度时翻页。带 `break-inside: avoid` 的行整行推到下一页，页尾留白。
   - 同一张表从第 2 页起，`page.pdf()` 会再印一遍 `thead`。可用高度改为内容区高度减去 `thead` 高度，翻页后 `cursorY` 从该高度起算。连续 DOM 里 `thead` 只出现一次。
   - 多单合并时，下一张单据根元素上的 `break-before: page` 把 `cursorY` 归零，从新页顶边重新累加。连续布局不会因为这个声明腾出空白。
2. `data-pdf-repeat` 的格子若跨到后面的页，把该格文字放到每个新页的第一行，并缩短原来的 rowspan。模型 JSON 不改。
3. 改过的 HTML 再测一轮。两轮之后直接 `page.pdf()`，不再循环。
4. 最终 `page.pdf()` 使用关闭 JavaScript 的 context。测量那一轮才允许 JavaScript，而且只执行 PDF 服务自己的 `page.evaluate`。模板 HTML 仍然没有 `<script>`，用户字段已经转义。网络拦截与最终那遍相同。

本地 Chrome 打印预览看不到这一步改写。`measure: true` 的模板，分页以 `pnpm pdf` 的结果为准。

## 7. 安全

- PDF 服务只接入 `lychee-net`。compose 不把它映射到宿主机端口。本机调试由 `application-local` 指向 `127.0.0.1`，那是开发编排，不是生产入口。
- 调用方带共享令牌。令牌放在后端配置与 PDF 服务环境变量，不进日志、不进仓库。
- 最终出 PDF 的 context 关闭 JavaScript，浏览器不访问外网。模板 HTML 不含 `<script>`。`measure: true` 时，测量轮次只跑服务自己的脚本，见 §6。模板 id 只查注册表，不能当成文件路径。
- 业务权限仍在 Java 的 `@PreAuthorize` 和导出 Handler 的 `requiredAuthority()`。PDF 服务不识别用户。

## 8. 失败时的行为

| 情况 | 后端行为 |
|------|----------|
| 连接失败、超时、进程无浏览器 | 预览接口返回业务错误（三语 `pdf.render.unavailable`）。不启动 openhtmltopdf 兜底 |
| PDF 服务 503（等待队列已满，或浏览器正在重启） | 同样提示稍后重试。客户端不自动重试 |
| 未知模板 id | 视为编程错误，记日志并返回失败。不上线未注册的 id |
| 模型缺字段 | 模板按空值留白或省略可选块。必填缺失在 Java 组装阶段拒绝 |

导出作业调用同一客户端。渲染失败时作业按现行框架标记 `FAILED`，不上传半份文件。

导出线程池最大 4。PDF 服务同时只渲染 1 份，多出来的请求在 PDF 进程里排队，上限 8；队列满才返回 503。Java 不再自己排队。预览的 HTTP 时限是 30 秒，归档是 60 秒，都包含排队和渲染。单次渲染最多 25 秒，所以预览最多再等大约 5 秒，归档大约 35 秒（大约容得下一份正在进行的渲染）。队列上限是为了挡住突发的请求正文，不是保证排在后面的请求都能在超时内开始。客户端超时会断开连接。连接断开时，还在排队的请求移出队列，已经开始的渲染关掉 context。PDF 服务不接收调用方时限。排队超过 35 秒仍未开始的请求返回 503。

## 9. 两套引擎并存

新报表禁止新增 `templates/print/*.html`，禁止调用 `PdfRenderSupport`。

存量报表在迁移前禁止改成调用 PDF 服务「先试试」。一张报表的切换是一次交付：新模板、样例、预览与归档入口一起切，旧 Thymeleaf 模板在同一变更里停用。

迁移顺序从单张、无归档的单据开始。矩阵和跨页合并放在后面：

| 顺序 | 模板 | 备注 |
|------|------|------|
| 1 | `stock-issue-pdf` | 单张、无归档。纸张是 Letter 216×279mm，用来确认非 A4 |
| 2 | `payment-pdf` | 单张、无归档。同一模板切换收款/付款标题 |
| 3 | `goods-receipt-pdf` | 单张、无归档 |
| 4 | `purchase-requisition-pdf` | 单张、无归档 |
| 5 | `physical-inventory-pdf` | 单张、无归档 |
| 6 | `delivery-note-pdf` | 单张、无归档 |
| 7 | `purchase-order-pdf` | 预览 + 归档。多单合并为一份 PDF，仍是一次 `render`。页码整份连号 |
| 8 | `outsource-order-pdf` | 同订购单：预览 + 归档 + 多单合并。另含价税与样品图。Logo 仍走原图；样品图走 §4 的 OSS JPEG |
| 9 | `delivery-billing-statement-pdf` | 尺码矩阵。跨页重复键列走 §6，`measure: true` |
| 10 | `factory-order-pdf` | 矩阵、样图、预览 + 归档 + 多单合并。跨页走 §6。Logo 走原图，样品图走 §4 |
| 11 | `sales-order-report-pdf` | 跨单矩阵。现行 `renderPaginatedPdf` 改为 §6 的游标测量。Logo 走原图，样品图走 §4 |

未列入的新单据直接用新引擎，不进入上表。

Excel 报表不在迁移范围内。
