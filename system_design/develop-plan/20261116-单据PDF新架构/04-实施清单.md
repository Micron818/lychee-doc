# 04 — 实施清单

**状态：P0 代码已落地，尚未部署。** 开发时以本文件为入口。架构说明见 [02](./02-目标架构.md)，接口见 [03](./03-契约.md)。三台主机升到约 8GB、并且各机 `.env` 写上 `LYCHEE_PDF_TOKEN` 之前，不要把这份 compose 拉到现网。

## 已锁定、实施时不再改的决定

1. 新 PDF 走 `lychee-pdf`。存量在切换完成前继续 `PdfRenderSupport`。
2. 对外预览 URL、权限、iframe 预览、归档作业模型不变。
3. 一张报表的预览与归档共用一个 Renderer、一个模板 id。
4. PDF 服务无数据库、无 OSS、无用户会话；同时只渲染 1 份，等待队列上限 8，满了立即 503。
5. 文案和金额在 Java 格式化。模板只转义并摆放字符串。
6. 样品图用 OSS `x-oss-process` 缩成 JPEG 再嵌 data URI。Java 不解码 WebP。公司 Logo 继续 `toDataUri`，不转 JPEG。现网 `toDataUri` 与 `resolvePrimaryImageDataUris` 留给尚未迁移的 openhtmltopdf。
7. 不把 Chromium 放进后端容器，不在 Umi 里做打印页。
8. 页码用 Playwright 页脚，不用 CSS `counter(page)`。
9. 不移植 `renderPaginatedPdf`。
10. Excel 仍用 Fesod。
11. 仓库、镜像、compose 服务、配置和错误文案用 PDF（`lychee-pdf`、服务名 `pdf`、`pdf.render.unavailable`）。Java `*PrintService` 不改名。
12. 客户端签名是 `render(templateId, model, PdfRenderMode, OutputStream)`，JDK `HttpClient` 流式写入。`PREVIEW` 30 秒，`EXPORT` 60 秒。
13. 静态标签进 `labels`，由 `MessageService.labelsByPrefix` 一次装入。
14. 页脚模板只放 ASCII 页码。多单合并的页码是整份连号，与现行 CSS `counter(page)` 相同。不按单从 1 重新计数，不用 pdf-lib 拼多份 PDF。
15. 跨页重复键列由 PDF 服务测量（`pdf.measure`、`data-pdf-row`、`data-pdf-repeat`）。Java 模型不预打重印标记，不把 `renderPaginatedPdf` 搬进 PDF 服务。

## P0 — 链路（不含业务单据）

目标：本机能用样例 JSON 在 Chrome 里改 HTML，服务器能用同一函数打出 PDF，Java 能取回字节。不替换任何现网模板。

- [x] 新建仓库 `lychee-pdf`：HTTP 服务、令牌、`/health`、`/render`、等待队列、信号量、Browser 生命周期（含每 500 次成功渲染后的空闲重启）、字体路由、网络拦截、`X-Trace-Id` 只记入日志。
- [x] 注册一个非业务模板 `sample/hello`（一张 A4，含中文、越南文、页脚页码），并提交 `fixtures/sample/hello.json`。
- [x] `pnpm dev` 打开该样例；`pnpm pdf` 对同一 `render` 写出 PDF。
- [x] Dockerfile 钉死 Playwright / Chromium 版本；构建期安装浏览器；运行期不下载。
- [x] `lychee-erp-common`：`ChromiumPdfClient`（`PdfRenderMode` + `OutputStream`）+ `lychee.pdf.*` + 三语 `pdf.render.unavailable` + `labelsByPrefix`。本机示例配置 `lychee.pdf.base-url: http://127.0.0.1:3100`。`labelsByPrefix` 的单元测试自带 `src/test/resources/i18n/`，不依赖 `lychee-erp` 的 properties。
- [x] 单元测试：客户端把非 PDF 响应和超时转成该异常；`PREVIEW` / `EXPORT` 使用各自超时；响应流写入调用方的 `OutputStream`。不启动浏览器。
- [x] 异步导出：`ExportJobEventListener` 把 `ValidationException` 按作业 `locale` 解成文案再 `markFailed`。
- [x] `lychee-pdf` 的 `.github/workflows/build.yml` 与 `deploy.yml` 对齐前后端：推 `main` 构建并部署 `khh-test`；`workflow_dispatch` 选择 `khh-test` / `demo` / `khh-prod` 和 8 位标签，只部署。`deploy.yml` 使用同一把锁 `/home/deployer/lychee/.lychee-deploy.lock`（`flock -w 600`），避免和 backend、frontend 同时改 `khh-test` 的 `.env`。
- [x] `deploy-service.sh` 接受 `pdf`，使用 `PDF_IMAGE` / `PDF_TAG`。发布 `pdf` 时不 reload nginx。
- [x] `.env.example`、`.env.khh-test`、`.env.demo`、`.env.khh-prod` 都补上 `PDF_IMAGE`、`PDF_TAG`、`LYCHEE_PDF_TOKEN`。`render-stack-config.sh` 对这三个键 `require_key`。
- [x] `lychee-infra`：`pdf` 服务、`mem_limit: 1536m`、`shm_size: 256m`、`init: true`、json-file 日志、仅 `lychee-net`、不映射端口。后端限额保持 1GB。
- [x] SLS：同一机器组增加 `service=pdf` 的 Logtail，logstore `lychee-pdf`，索引 `traceId`。不新建 Project，不改 backend 那条采集。配置写在 [SLS.md](../../20260819-logging-sjs/SLS.md) §5.1，控制台尚未执行。
- [x] 把 `lychee-pdf` 加进 `lychee-workspace/work.code-workspace`。`workspace.mdc` 补上仓库表、验证命令，以及「Java 打印视图模型 ↔ `lychee-pdf` 模板类型与 fixtures」。
- [x] 主机：按 [07-测试栈共用正式Keycloak](../20261022-多租户运行栈/07-测试栈共用正式Keycloak.md) §6。`khh-prod` 约 8GB 后再拉起 `pdf`；`khh-test` 停掉本机 Keycloak 后在约 4GB 上拉起；`demo` 本次不拉起。不用 profile 跳过 `pdf`。
- [x] 验收：`sample/hello` 从 Java 客户端打出的 PDF 能打开，页码为 `1 / 1`，中文与越南文都在；PDF 容器重启期间，一张存量单据（例如订购单）预览仍成功。

P0 完成后不要开始迁移存量模板。

## P1 — 第一张真实新报表

目标：下一张**新**单据或新报表直接用本架构，作为版式回路的第一次业务验收。

单据定为 **销售订单月汇总表**。口径、权限、版式、是否归档见 [销售订单月汇总表](../20261116-销售订单月汇总表/设计.md)。

销售订单列表上现有的跨单矩阵，用户侧改称 **销售明细表**。那张继续走 openhtmltopdf，不在本阶段换引擎。更名只改标题和按钮文案。

- [x] Java：Service 校验与视图模型；`*PdfRenderer` 只调用 `ChromiumPdfClient`。
- [x] 预览端点保持现行形态（`read`、inline、不落 OSS）。需要归档时，ExportHandler 调用同一 Renderer（`export`）。本期月汇总不归档。
- [x] `lychee-pdf`：模板、类型、脱敏 fixture。静态标签走 `labels` 与 `labelsByPrefix`，三语 key 仍在 Java `messages*`。
- [x] 前端：只加领域 `PdfPreview` 薄适配，复用 `PdfBlobViewer`。
- [x] 验收：改 CSS 后只刷新 Chrome 打印预览即可看到结果；再经后端预览接口得到同一版式的 PDF。空数据、无权限不会打到 PDF 服务。代码与单测已覆盖后半句；Chrome 与后端联调仍待本机 PDF 服务。

## P2 — 存量逐张迁移

开工条件：P1 的那张报表已在目标环境用过，并且用 Chrome 预览改过至少一轮版式。

一次只迁一张。该张的预览、归档（若有）、新模板、fixture 同一变更完成；旧 `*-pdf.html` 停止被该 Renderer 引用。

顺序见 [02 §9](./02-目标架构.md)。尺码矩阵用 §6 的游标测量，不按 `offsetTop / 页高` 整除。公司 Logo 继续原图 data URI。样品图用 §4 的 OSS JPEG，并给 `MaterialImageHelper` 新增方法，不改现网 `resolvePrimaryImageDataUris`。不要把 `renderPaginatedPdf` 搬进 Chromium，也不要在 Java 模型里预打续页标记。迁入第 8 张（委外单）之前，OSS JPEG 读取方法可用。迁入第 9 张之前，`pdf.measure` 可用。

每张的验收：

- [ ] 抬头、合计、签核、空值省略与迁移前一致（人工对页，不要求 PDF 字节相同）。
- [ ] 三语各打一页。
- [ ] 有归档的单据：预览与导出作业的 PDF 来自同一次模板渲染。
- [ ] 该模板的 openhtmltopdf 坐标测试删除或改为 HTML 断言；其余未迁移模板的测试仍跑。

全部 11 张迁完之前，`PdfRenderSupport` 与 openhtmltopdf 依赖保留。最后一张迁完后另开一次变更删除该引擎、classpath 字体注册和已无引用的 Thymeleaf 打印模板。

## 明确不做

- 用用户浏览器的 `window.print()` 代替服务端 PDF。
- 让 Playwright 打开已登录的 Umi 页面。
- 由前端把 HTML 传给 PDF 服务。
- 在 Node 里查库或校验租户。
- 为新报表增加 Thymeleaf 打印模板。
- 在 P0 修改订购单、销售订单报表等现网版式。
- 在 Java 模型里预打续页重印标记。
- 按单渲染后再用 pdf-lib 拼成一份 PDF。
