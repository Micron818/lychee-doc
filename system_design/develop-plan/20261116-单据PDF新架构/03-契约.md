# 03 — 契约

PDF 服务是内网纯函数：`模板 id + 视图模型 → PDF 字节`。没有会话，没有数据库。

## 1. HTTP

基址：容器内 `http://pdf:3100`。本机调试 `http://127.0.0.1:3100`。

### 1.1 `GET /health`

无令牌。供编排探活。

| 状态 | 含义 |
|------|------|
| 200 | 进程在，且 Browser 已连接 |
| 503 | 进程在，浏览器未就绪或正在重启 |

响应正文：

```json
{ "status": "ok", "browser": "chromium" }
```

### 1.2 `POST /render`

请求头：

| 头 | 值 |
|----|----|
| `Authorization` | `Bearer <LYCHEE_PDF_TOKEN>` |
| `Content-Type` | `application/json` |
| `X-Trace-Id` | 可选。Java 从 MDC `traceId` 原样透传，头名是 `TraceContext.HEADER`。缺失时 PDF 服务不补造 |

```json
{
  "templateId": "wm/stock-issue",
  "model": {}
}
```

`templateId` 只含小写字母、数字和 `/`、`-`，且必须在注册表中。`model` 为 JSON 对象。不传 locale：文案已经写进 `model`。

成功：`200`，`Content-Type: application/pdf`，正文为 PDF。不包 `ApiResponse`。这是服务间字节流，不是给浏览器的业务 API。

失败正文为 JSON：`{ "error": "<code>" }`。

| HTTP | error | 何时 |
|------|-------|------|
| 401 | `unauthorized` | 令牌缺失或不匹配 |
| 400 | `invalid_request` | JSON 不合法、缺 `templateId`、`model` 不是对象 |
| 404 | `unknown_template` | id 未注册 |
| 413 | `payload_too_large` | 正文超过上限（默认 20MB） |
| 503 | `busy` | 等待队列已满，或浏览器正在重启 |
| 500 | `render_failed` | 模板抛错或 Chromium 失败。日志记 templateId 与异常，不记 model |

比较令牌使用常数时间比较。日志可以记 `X-Trace-Id`、`templateId`、耗时、PDF 字节数，不记令牌和模型。

### 1.3 并发与时限

- 同时只渲染 1 份（信号量 = 1）。
- 进程内 FIFO 等待队列，上限 8，不含正在渲染的那一份。队列已满时新请求立即 503 `busy`，不进入队列。客户端不自动重试。
- 排队中的请求若连接断开，从队列移除，不开始渲染。渲染已经开始后连接断开，关闭该 context。Java 的 HTTP 超时会断开连接，请求头不传 30 秒或 60 秒。
- 服务端排队上限 35 秒（归档 60 秒减去渲染 25 秒）。超过仍未开始渲染则返回 503 `busy`。预览的 30 秒更短，由客户端先断开。
- 单次 `page.pdf()` 时限 25 秒，只计算渲染，不含排队。超时关闭该 context 并返回 500。
- Java 客户端预览超时 30 秒，归档超时 60 秒。时限覆盖排队加渲染，超时视为不可用，不重试。渲染上限 25 秒，所以预览最多再等大约 5 秒，归档大约 35 秒。队列上限 8 挡住突发请求正文（每份最多 20MB），不是保证 8 份都在超时内开始。
- 正文默认上限 20MB，挡住过大的 data URI。样品图经 OSS 缩成 JPEG；公司 Logo 仍是原图 data URI。见 [02 §4](./02-目标架构.md)。

### 1.4 PDF 选项

每个模板的 `pdf` 字段映射到 Playwright：

```ts
await page.pdf({
  width: pdf.width,
  height: pdf.height,
  margin: pdf.margin,
  printBackground: true,
  preferCSSPageSize: false,
  displayHeaderFooter: pdf.footer,
  footerTemplate: pdf.footer
    ? '<div style="font-size:8px;width:100%;text-align:center;color:#888;"><span class="pageNumber"></span> / <span class="totalPages"></span></div>'
    : '<span></span>',
  headerTemplate: '<span></span>',
});
```

纸张以这里的 `width` / `height` 为准，所以 `preferCSSPageSize` 为 false，避免和页脚边距互相覆盖。CSS `@page { size }` 写成同一尺寸，供 Chrome 打印预览使用。

`footer: false` 的单据（若业务不要页码）仍传空的 header/footer，避免 Chromium 打上默认的 URL 和时间。

页眉页脚运行在独立上下文里，不继承文档字体。上面的页脚只使用 ASCII。不要把中文或越南文写进 `headerTemplate` / `footerTemplate`。

最终出 PDF 的 context：

```ts
await browser.newContext({
  javaScriptEnabled: false,
});
```

`pdf.measure: true` 时，在此之前多一轮测量。那一轮允许 JavaScript，只为执行服务自己的 `page.evaluate`；模板 HTML 没有 `<script>`。测完改 HTML，再进入上面的 context。两轮测量之后直接 `page.pdf()`。详见 [02 §6](./02-目标架构.md)。

两种 context 的 `page.route` 都只放行 `baseURL` 下的文档和 `/fonts/*`，其余 `abort`。

## 2. Java 客户端

`ChromiumPdfClient` 放在 `lychee-erp-common`，供各领域 `*PdfRenderer` 使用。

预览和归档共用 Renderer，但超时不同。现网归档把 PDF 写进临时文件（`ExportJobExecutor` 的 `Files.newOutputStream`），客户端不要再把响应收成 `byte[]`。`lychee-erp-common` 不引入 WebFlux，用 JDK `java.net.http.HttpClient`（与 `VcbExchangeRateClient` 相同），`BodyHandlers.ofInputStream()` 直接写入调用方的 `OutputStream`。

```java
public enum PdfRenderMode {
    PREVIEW, EXPORT
}

public void render(String templateId, Object model, PdfRenderMode mode, OutputStream out) {
    // POST {baseUrl}/render，头带 X-Trace-Id
    // PREVIEW 用 preview-timeout，EXPORT 用 export-timeout
    // 2xx 且 Content-Type 为 application/pdf → 把响应流写入 out
    // 否则抛 ValidationException("pdf.render.unavailable")
}
```

同步预览的 Controller 仍返回 `byte[]`：Renderer 传入 `ByteArrayOutputStream`。归档传入临时文件流。请求 JSON 仍在内存里序列化，所以上限是正文 20MB，不是响应再复制一份。

配置（`application.yaml` / 环境变量，令牌不入库）：

```yaml
lychee:
  pdf:
    base-url: http://pdf:3100
    token: ${LYCHEE_PDF_TOKEN:}
    preview-timeout: 30s
    export-timeout: 60s
```

生产 `base-url` 用 `http://pdf:3100`（compose 网络内的服务名）。本机 `application-local.example.yaml` 写 `lychee.pdf.base-url: http://127.0.0.1:3100`。

`base-url` 或 `token` 为空时，客户端在被调用时失败，并使用同一条文案。不要在应用启动时因为 PDF 服务未配置而拒绝启动：CRUD 与 Excel 不调用它，单据 PDF 在请求时返回 `pdf.render.unavailable`。

三语 key 为 `pdf.render.unavailable`（`messages*.properties`，三份文件同一位置）。文案指 PDF 渲染不可用，不写成打印机故障。用户能做的只有稍后重试，文案不区分 503、超时和连接失败。模板 id 错误、500 的细节只进后端日志。

| 文件 | 文案 |
|------|------|
| `messages.properties` | PDF rendering is unavailable. Please try again later. |
| `messages_zh_CN.properties` | PDF 渲染暂不可用，请稍后再试。 |
| `messages_vi.properties` | Kết xuất PDF tạm thời không khả dụng. Vui lòng thử lại sau. |

预览 Controller 的对外形状不变：`ResponseEntity<byte[]>`，`application/pdf`，`ContentDisposition.inline()`，文件名仍由 Java 按现行规则生成（PDF 服务不返回文件名）。

## 3. 视图模型约定

`model` 的 TypeScript 类型写在对应模板旁边，例如 `src/templates/wm/stock-issue.tsx` 导出 `StockIssuePrintModel`。Java 侧用一个专用于打印的 Response / record，字段与该类型对齐。

静态表头不在模板里查 properties。这些字符串进模型的 `labels`。

`MessageService.labelsByPrefix(Locale locale, String prefix)` 从 messages 家族的 properties 枚举该前缀下的全部 key，去掉前缀作为 `labels` 的字段名。`MessageSource` 本身列不出 key，不要假设它能。运行期读启动模块 classpath 上的 `i18n/messages*.properties`，取值仍走 `messageSource.getMessage`。`MessageService` 在 `lychee-erp-common`，common 的测试 classpath 没有 `lychee-erp` 那份 properties。单元测试在 `lychee-erp-common/src/test/resources/i18n/` 放测试用 properties，或允许测试传入 properties。一张单据的 Renderer 调用一次，例如前缀 `print.purchase_order.`。禁止对每个标签各写一行 `getMessage`。金额、日期、枚举文案仍是模型上的独立字符串，不进 `labels`。

约定：

- 展示用文本一律为 `string`。可选块用空字符串或 `null`，模板用有无值判断，不在模板里格式化数字。
- `labels` 为 string 到 string 的对象。模板只读 `labels.<字段>`。
- 列表字段为数组。行次、排序在 Java 完成。
- 图片字段为 data URI 或空字符串。公司 Logo 保留原图的 MIME（常见 `image/png`）。样品图为 `image/jpeg`。不传 OSS key，不传 CDN URL。
- 不传 `tenantId`、用户 id、权限串。

样例 `fixtures/wm/stock-issue.json` 与该类型一致，供 `pnpm dev` 和测试使用。真实单据抓一次模型即可更新样例；样例放在 `lychee-pdf`，不放业务数据进 git 时用脱敏后的字段。

## 4. 运行与资源

在约 8GB 主机上建议的限额（实施时写入 `docker-compose.yml`）：

| 服务 | mem_limit | 说明 |
|------|-----------|------|
| `pdf` | `1536m` | 常驻 Chromium + 一份渲染 + 最多 8 份排队正文。无宿主机端口 |
| `backend` | 维持 `1g` | 堆百分比策略不变。浏览器不在这个 cgroup 里 |
| `keycloak` | 维持 `768m` | |
| `postgres` | 仍不设上限 | 余量留给库缓存 |

`pdf` 使用钉死版本的 Playwright 官方镜像（或在该镜像上只加字体与应用代码）。Chromium 在构建镜像时安装，容器启动后不再下载浏览器。镜像内字体文件与 `@font-face` 使用的文件是同一套 Noto，不另装一套系统 CJK 字体以免两套度量并存。

`docker-compose.yml` 里 `pdf` 还要：

- `shm_size: 256m`。容器默认 `/dev/shm` 只有 64MB，多图或多页时 Chromium 会崩。
- `init: true`。Node 作为 PID 1 不会回收 Chromium 子进程。
- `logging` 使用现有 `default-logging`（json-file，`max-size: 50m`，`max-file: 3`），供 LoongCollector 读 stdout。
- 不映射宿主机端口。

日志不新建 SLS Project。现有 Logtail 只采集 `com.docker.compose.service=backend`。在同一机器组上为 `service=pdf` 增加一条 Logtail，写入该 Project 的 logstore `lychee-pdf`，`traceId` 做 text 索引。backend 那条采集配置不改。

`docker-compose.yml` 三台栈共用，不使用 profile 让某一台跳过 `pdf`。`khh-prod` 升到约 8GB 后再在该机拉起 `pdf`（本机还有 Keycloak `768m`）。`khh-test` 停掉本机 Keycloak、维持约 4GB 后再拉起，见 [07-测试栈共用正式Keycloak](../20261022-多租户运行栈/07-测试栈共用正式Keycloak.md)。`demo` 保持本机 Keycloak，4GB 上不拉起 `pdf`。`khh-test` 会随 `main` 自动部署，含 `pdf` 的 infra 合入 `main` 前，测试机要已经是远程 issuer。

探活使用 `GET /health`。`backend` 不把 `pdf` 的存活当作自己的启动条件：PDF 容器重启时，CRUD 与 Excel 仍可用，单据预览与归档返回 `pdf.render.unavailable`。

环境变量：

| 变量 | 服务 | 说明 |
|------|------|------|
| `LYCHEE_PDF_TOKEN` | `pdf` 与 `backend` | 同一值。写入该机 `deploy/.env`，不入库 |
| `LYCHEE_PDF_BASE_URL` | `backend` | 生产 `http://pdf:3100` |
| `PDF_IMAGE` / `PDF_TAG` | compose | 与 `BACKEND_IMAGE` / `BACKEND_TAG` 同样的发布方式 |

## 5. 与导出框架的边界

[02-导出框架](../20260818-report/02-导出框架总体设计.md) 的作业表、SPI、同步阈值、线程池、OSS 路径、下载鉴权都不改。

变化只发生在「Handler 写出 PDF 字节」的那一步：新报表的 Renderer 把临时文件的 `OutputStream` 交给 `ChromiumPdfClient`（`EXPORT`），再走现有上传。Excel Handler 不读取 `lychee.pdf.*`。

异步失败由 `ExportJobEventListener` 调用 `markFailed(exportJobId, e.getMessage())`。`ValidationException.getMessage()` 是 i18n key，导出中心的 `errorMessage` 会原样显示。PDF 渲染失败若只抛 `pdf.render.unavailable`，列表里就是这个 key。listener 在入库前识别 `ValidationException`，用作业上保存的 `locale` 调用 `MessageService.getMessage`，再 `markFailed`。不要依赖 catch 块里的 `LocaleContextHolder`。同步预览仍由 `GlobalExceptionHandler` 翻译。两条路径都不要把 key 给用户。
