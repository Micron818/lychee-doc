│                                                                          │
│ FO 列表                                                                  │
│ ┌────┬──────────────┬──────────┬────────┬──────────┬──────────┬──────────┐
│ │ #  │ FO No         │ 状态     │ 客户   │ 需求日期 │ 总数量   │ 来源 SO  │

│ └────┴──────────────┴──────────┴────────┴──────────┴──────────┴──────────┘
│                                                                          │
│ 分页:  << 1 2 3 >>                                                        │
└──────────────────────────────────────────────────────────────────────────┘
```

**一 FO 多 SO 的表达说明（List Page）**

* 列表页不直接显示单一 SO 编号，避免误导为一对一关系
* 「来源 SO」显示为 **SO 笔数汇总**（如：3 笔 SO）
* 支持 Hover / 点击展开查看明细 SO：

```
来源 SO：3 笔
----------------
SO-2026-001  数量 100
SO-2026-002  数量 120
SO-2026-005  数量 80
```

* FO No 仍作为主导航入口，SO 细节留在明细页完整呈现

**设计重点****

* 列表支持批次操作（确认 / MRP）
* FO No 点击进入明细页
* 列表只呈现「决策所需最少字段」

## 二、SO → FO 汇总规则说明（核心业务规则）

> 本区块用于明确：**多个 SO 如何被汇总成一张 FO，以及 FO Lines 的生成逻辑**，避免前后端、业务理解不一致。

---

### 2.1️⃣ 汇总前提条件（不满足则不可汇总）

以下条件**必须一致**，SO 才能被汇入同一张 FO：

- 客户（Customer）一致
- 工厂 / 生产据点一致
- 币别一致
- 交易类型一致（一般销售 / 专案 / 内销 / 外销等）

> 系统行为：
> - 条件不一致的 SO 行，在「从 SO 汇入」时应被禁选或提示原因

---

### 2.2️⃣ FO Lines 合并规则（是否合并行）

#### 规则 A：同产品 + 同需求日期 → **自动合并（推荐默认）**

```

SO-001  FG-001  50  2026-02-15
SO-002  FG-001  30  2026-02-15
──────────────────────────
FO Line: FG-001  数量 80  需求日 2026-02-15
来源 SO：SO-001, SO-002

```

- FO Lines 以「产品 + 需求日期」作为合并 Key
- 来源 SO 需在行级明细中可追溯

---

#### 规则 B：同产品 + 不同需求日期 → **拆为多行（默认）**

```

SO-001  FG-001  50  2026-02-15
SO-002  FG-001  30  2026-02-20
──────────────────────────
FO Line 1: FG-001  50  2026-02-15  (SO-001)
FO Line 2: FG-001  30  2026-02-20  (SO-002)

```

- 交期是 MRP 的关键输入，不建议强制合并

---

#### 规则 C：是否允许「手动合并 / 拆分」（可选）

- 提供行级操作：
  - 【合并行】（仅当产品、工厂一致）
  - 【拆分行】（数量拆分，保留来源 SO 关系）
- 建议仅开放给「计划角色」

---

### 2.3️⃣ 交期（需求日期）处理规则

#### 默认规则（强烈建议）

- FO Line 的需求日期 = SO 行需求日期
- 不因汇总而自动提前或延后

#### 可选策略（需业务确认）

- 最早交期优先：取所有 SO 中最早日期
- 最晚交期优先：取最晚日期

> ⚠ 不建议作为默认策略，容易影响交期承诺

---

### 2.4️⃣ 部分转单（Partial SO → FO）规则

```

SO-003 FG-001  80
已转 FO：50
可转数量：30

```

- 系统必须记录：
  - SO 行原始数量
  - 已转 FO 数量
  - 剩余可转数量
- FO Lines 仅能使用「剩余可转数量」

---

### 2.5️⃣ Confirm FO 前的系统检查（强制）

在 FO Confirm 前，系统需检查：

- 是否存在超转 SO 行
- 是否存在未指定来源 SO 的 FO 行
- 同一 SO 行是否被转入多张未完成 FO

不通过则禁止 Confirm，并给出明确提示。

---

## 三、页面设计总原则（供评审用）

- FO = 决策型单据，不是纯录入
- 状态驱动操作（按钮随状态变化）
- MRP 先建议、再确认
- 所有下游单据必须可追溯
