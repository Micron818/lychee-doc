# 01. 计划工单作业现状与问题（As-Is）

> 依据当前代码：`lychee-erp-pp` / `lychee-frontend`。  
> 采购对照：[`../20260825-purchase/01-现状与问题.md`](../20260825-purchase/01-现状与问题.md)。

---

## 1. 设计初衷与实际作业

现网单据链是对的：

```text
MrpResult(PRODUCTION, OPEN)
    → 人工转 PLO(PROPOSED)     // 建议变成计划单据，下次 Regenerative 仍可清掉
    → 可选 FIRMED              // 锁定：下次 MRP 不删，并计入预计入库
    → 转 MO(PLO=CONVERTED)     // 执行
```

采购已经把「确认要买」从 MRP 结果页挪到采购订单页的 MRP 待转 Tab。生产侧仍停在更早的形态：

| 角色假设 | 实际操作 |
|----------|----------|
| 计划员在 MRP 结果勾选生产建议并转 PLO | 必须先滤「建议生产」（`ALL` 不能转），勾选，POST 到**当前这条 Run** |
| 再到计划工单页处理锁定与下达 | 换菜单；行内「更多」逐笔确认 / 转 MO / 删除 |
| 采购员在采购订单页处理待买 | 同一页 Tab，最新 Run 待转池 |

摩擦不在算法，在**作业切换与一次只能点一行**。

## 2. 现行主流程

```text
CONFIRMED / IN_PROGRESS FO
        │
        ▼
   MRP Run（再生式净算，可手动或 SCHEDULED）
        │
        ▼
   MrpResult  suggested_action_type = PRODUCTION | PURCHASE
        │
        ├─ PURCHASE：结果页按钮跳转 /scm/purchase-orders?tab=mrp（可带 factoryId）
        │
        └─ PRODUCTION：结果页勾选 → POST /mrp-runs/{id}/results/convert-to-planned-orders
                │
                ▼
           PlannedOrder PROPOSED（带 mrpRunId）
                │  换到 /pp/planned-orders
                ▼
           行内更多：确认 FIRMED / 取消确认 / 转 MO / 删除 / Pegging
                │
                ▼
           ProductionOrder CREATED
```

培训剧本 [PB-04](../../../user_training/zh/03-process-playbooks/PB-04-mrp-to-production.md) 也按「结果页转计划单 → 再打开计划工单」写。

## 3. 各步骤在代码中的行为

### 3.1 MRP 结果转 PLO — `MrpConversionServiceImpl.convertToPlannedOrders`

- 仅 `suggestedActionType = PRODUCTION` 且 `convertStatus = OPEN`
- 整行转出：`convertedQuantity = requiredQuantity`，`convertStatus = CONVERTED`（生产无 PARTIAL）
- 新建 PLO：`orderType = MAKE`，`orderStatus = PROPOSED`，数量/起止日抄结果
- Pegging：`MRP_RESULT → PLANNED_ORDER`
- 若 FO 需求侧已有 FIRMED/CONVERTED PLO（`hasProtectedOrder`）：**静默 skip**，不报错、不返回跳过清单
- **不校验「该厂最新 OPERATIVE Run」**。路径上的 `{id}` 是 Run id，Service **不用它**。历史 Run 的未转生产建议仍能转出
- API 权限：`/pp/mrp-runs:update`
- 返回 `void`

前端 `ResultList`：必须把建议类型滤成 `PRODUCTION` 才出现勾选和「转计划单」。`ALL` 只提示去选类型。

### 3.2 计划工单页 — `planned-orders/index.tsx`

- 单表 `ProTable`，无 Tab
- 工具栏只有 `BatchDeleteButton`，**不按状态禁用**（CONVERTED 仅 checkbox 禁用；混选时点删除靠后端 `delete.contains.converted`）
- 确认 / 取消确认 / 转 MO / 删除 / Pegging 全在行内 `PlannedOrderMoreActionsButton`
- 后端批量接口已具备：

  | API | 行为 |
  |-----|------|
  | `POST /bulk-firm` | 仅把 **PROPOSED** 改为 FIRMED；其它状态**静默忽略** |
  | `POST /bulk-unfirm` | 仅把 **FIRMED** 改为 PROPOSED；其它静默忽略 |
  | `POST /bulk-convert-to-mo` | 一批生成 MO；已 CONVERTED 或非 MAKE **整批失败** |
  | `DELETE /bulk-delete` | 含 CONVERTED **整批失败**；PROPOSED 删除会 `applyConvertedQuantity` 回退结果 |

- 行规则见 `getPlannedOrderRowActions`：PROPOSED 与 FIRMED **都可以**转 MO。文案 `convertToMo.tooltip` 却写「将选中的确定状态计划订单转换」，与代码不一致
- 改日期/类型会 **自动 FIRMED**（`PlannedOrderServiceImpl.updatePlannedOrder`）
- 无「新增」：PLO 不能手建
- `tableAlertRender={false}`，没有销售订单那种混态提示

### 3.3 转 MO — `PlannedOrderServiceImpl.convertToProductionOrders`

- 已按 `Set<Long>` 批量实现；前端每次只传 `[record.id]`
- 按 PLO 开工日匹配有效 APPROVED BOM，展开组件
- Pegging：`PLANNED_ORDER → PRODUCTION_ORDER`
- PLO → `CONVERTED`；沿 MrpResult pegging 回写 FO `allocatedQuantity`

### 3.4 采购工作台（对照，已落地）

- `/scm/purchase-orders?tab=mrp`
- 待转池 = 该厂最新 `COMPLETED + OPERATIVE` Run 上 `PURCHASE` 且 remaining > 0
- 结果页不 POST 转单，只跳转；无 `purchase-orders:create` 则禁用
- 工作台行上改供应商/数量后分组生成 DRAFT PO

生产没有对等入口。

## 4. 摩擦点

| # | 问题 | 影响 |
|---|------|------|
| 1 | 转 PLO 与处理 PLO 分属两个菜单 | 计划员日常是「结果页点完再找计划工单」 |
| 2 | 结果页转单绑在**当前打开的 Run** | 与采购「只转最新 Run」不一致；旧建议可误转 |
| 3 | `hasProtectedOrder` 静默跳过 | 点了成功，PLO 列表却没有对应单 |
| 4 | 批量 API 已有，UI 仍逐行 | 一次 MRP 几十上百条生产建议时无法下达 |
| 5 | 工具栏删除不校验均匀状态 | 与销售订单 / BOM 的 `hasUniformStatus` 模式不一致 |
| 6 | firm/unfirm 静默忽略非法状态 | 混选时表现为「点了没全改」 |
| 7 | 转 MO 文案与规则不一致 | 培训/tooltip 以为必须先确认 |

---

## 5. 明确不是问题（本专题不改）

- 计算后自动转 PLO：否。PROPOSED 下一轮仍会被清，自动转只烧单号（见此前评估）
- 跳过 PLO 直接出 MO：否。PLO 仍是可改日期、可锁定、可回退的计划层
- 生产建议部分转：否。继续整行，无 PARTIAL
- 引擎、清理、FIRMED 才计入供给、Pegging 模型：不改
- 采购待转 / 请购待转：不改
- 手建 PLO、OUTSOURCE 转单：本期不做
