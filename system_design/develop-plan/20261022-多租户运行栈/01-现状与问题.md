# 01. 现状与问题（As-Is）

> 依据当前仓库：`lychee-infra`、`lychee-backend`、`lychee-frontend`。  
> 日志采集见 [`../20260819-logging-sjs/SLS.md`](../20260819-logging-sjs/SLS.md)。

---

## 1. 现在只有一套运行环境

`main` 推送后，前后端各自的 GitHub Actions 构建镜像，SSH 到 `secrets.HOST` 这一台机器，在 `/home/deployer/lychee/lychee-infra/deploy` 把对应的 `BACKEND_TAG` 或 `FRONTEND_TAG` 改成提交号前 8 位，再 `docker compose up` 该服务。

这台机器上是一整套 Compose：Postgres、Keycloak、backend、frontend、nginx。编排注释按约 4GiB 内存限制 Java（backend 1GiB、Keycloak 768MiB）。数据目录在项目根下的 `data/postgres`、`data/keycloak`。

因此正式与测试无法叠在这台机器上，也不能共用这一套库和 Keycloak。

## 2. 两个入口域名指向同一租户

Nginx 把两个 Host 反代到同一组容器：

| Host | 作用 |
|------|------|
| `khh.lycheetech.com` | 租户入口（租户代码 `kimhiephoa`） |
| `lycheetech.com` | 初期安排的第二入口，同样进 `kimhiephoa` |

`lycheetech.com` 以后用作产品介绍与帮助站，不再是 khh 或任何租户的入口。本专题取消这层关联。

80 端口把这两个名字一起跳到 HTTPS。443 上是两段几乎相同的 `server`：`/`、`/api/`、`/oidc/` 各写一遍。改超时、改转发头必须改两处。导出文件那次就为此写过「两个 host 各一份」（[`../20260918-export-file-delivery/02-目标流程.md`](../20260918-export-file-delivery/02-目标流程.md) §6.2）。

两个 `server` 都引用 `lycheetech.com.pem`。本机留存的证书副本（已过期，仅作参考）是单域名证书：`lycheetech.com` 那张只含根域和 `www`，`khh.lycheetech.com` 另有一张。新增 Host 不能假设一张证书覆盖全部名字；服务器上的现行证书要在切换前核对 SAN。

CORS 与这两个 Host 对齐，写在 `application-prod.yaml`：

```yaml
app.cors.allowed-origins: https://lycheetech.com, https://khh.lycheetech.com
```

Keycloak、数据库、OSS bucket `lychee-erp-assets` 是这一套环境共用的。租户数据靠行上的 `tenant_id` 和对象键前缀隔开，不靠再开一套 Compose。

## 3. 登录 realm 不看 Host

前端容器启动时把一份环境变量写进 `env-config.js`（`docker-entrypoint.sh`）：

- `API_BASE_URL`
- `KEYCLOAK_URL`
- `KEYCLOAK_REALM`（缺省 `kimhiephoa`）
- `KEYCLOAK_CLIENT_ID`

`src/services/auth/config.ts` 用这一份 realm 拼 authority：`{KEYCLOAK_URL}/realms/{KEYCLOAK_REALM}`。用户从任一 Host 打开页面，浏览器回调是该 Host 的 `/auth/callback`，但 realm 仍是容器里的那一个，不随 Host 变化。

`env-config.js` 里的 `API_BASE_URL` 没有被请求使用。`app.tsx` 的 `baseURL` 读构建期的 `process.env.API_BASE_URL`，正式构建没有定义它，请求一直走当前页面的 `/api/`。现网 `.env` 的 `API_BASE_URL=https://lycheetech.com/api` 实际不生效。

后端 `MultiTenantJwtDecoder` 从 token 的 issuer 取出 realm，并要求它是启用中的租户代码。issuer 前缀只有一份，来自 `KEYCLOAK_URL`。[05](./05-khh正式issuer切换.md) 把它从 `https://lycheetech.com/oidc` 改为 `https://khh.lycheetech.com/oidc`。

`tenants.domain` 存在表里，登录路径没有用它做 Host 匹配。

所以现网能区分的是 **两个入口域名**。真正进哪个租户，取决于登录用的 realm，而 realm 目前是整站一份。

## 4. 环境差异写进了镜像和仓库文件

| 位置 | 写死的内容 | 后果 |
|------|------------|------|
| `docker-compose.yml` | `SPRING_PROFILES_ACTIVE: prod`；单一 `KEYCLOAK_REALM` | 测试机无法换 profile；realm 不随 Host |
| `application-prod.yaml` | CORS、OSS endpoint 与 bucket、CDN 域名 `cdn.lycheetech.com` | 同一镜像在测试机仍访问正式域名和正式 bucket |
| `application-local.example.yaml` | 正式 bucket `lychee-erp-assets`、正式 CDN | 本机开发上传的文件写进正式 bucket |
| `default.conf` | 两个 Host、证书路径；`proxy_pass` 写静态容器名 | 服务器上手改会被 `git reset --hard` 覆盖；容器重建换 IP 后 Nginx 仍连旧 IP，部署脚本不 reload |
| `docker/postgres/init.sql` | 两个数据库角色的口令（与正式 `.env` 相同，已入库）；不建 schema `lychee_erp` | 新栈会沿用正式口令；空库上应用找不到 schema |
| `backup/scripts/backup_to_oss.sh` | 容器名 `lychee-postgres`，OSS 前缀 `backup-postgres/` | 两台机器备份会写进同一前缀 |
| `backup/scripts/restore_from_oss.sh` | 只从 `daily/` 取文件；不停 backend、keycloak | 没有「哪台栈的备份」概念，任何机器都能恢复正式备份 |
| 前端 `config/config.ts` | CDN 预连接 `cdn.lycheetech.com` | 构建期写死，测试、演示栈会预连正式 CDN |
| 两个 `deploy.yml` | 一组 `HOST` / `KEY`，`main` 推送即部署；先改 `.env` 标签再拉镜像 | 没有「先上测试、再升正式」；拉取失败时 `.env` 已指向拉不到的标签 |

`deploy/.env` 被 `lychee-infra/.gitignore` 忽略，`git reset --hard` 不会清掉它。镜像标签、数据库口令、Keycloak 口令可以留在各台机器上。但同一条规则 `.env.*` 也忽略了 `deploy/.env.example`：仓库里其实没有这份模板。

证书文件（`*.pem` / `*.key` / `*.crt`）已被忽略，各台机器放自己的证书即可。

## 5. 空库建不起来，新租户没有配置来源

- Liquibase 基线 `v0/20260617-initial-db.sql` 带 `contextFilter:"!local AND !prod"`。`application-prod.yaml` 设 `contexts: prod`，本机设 `local`。空库在这两个 context 下会跳过基线，第一个增量就因缺表失败。只有集成测试（context `it`）执行基线。
- `v1/` 的数据脚本有按字面值写的种子：`tenant_id = 1`、`created_by = 1`（如 `0710-001`、`0729-001`，以及 `0831-002` 末尾的兜底段）。审计列有外键到 `users`。空库没有租户 1 和用户 1，脚本中途失败。集成测试靠 `session_replication_role = replica` 关掉外键才跑完。
- `init.sql` 只建角色和库，不建 schema。连接 URL 不带 `currentSchema`，应用靠 `search_path` 的 `"$user"` 落到 schema `lychee_erp`。
- 除 `tenants` 外，其余 132 张表都带 `tenant_id`。菜单、权限、选项、角色、单据编号规则、科目表这些系统配置只存在于正式库（以及与之同步的本机库）的数据里，仓库没有。`TenantServiceImpl.createTenant` 只插一行 `tenants`，新租户登录后没有菜单和权限，也没有第一个用户。
- `system_design/database/sql/schema_tables/` 与库有出入（例如 `menus.sql` 仍有已删除的 `status_option_id`），不能拿来拼基线。

本机库与正式库已同步，可以以库为准重新生成基线，见 [06](./06-数据库基线与租户开通.md)。

## 6. 这台机器的身份

现网这一套就是 **大租户 khh**（租户代码 `kimhiephoa`）的正式栈，不是一套将来能直接塞进许多客户的公用生产环境。用户入口是 `khh.lycheetech.com`；`lycheetech.com` 是要退出的初期入口。

库、Keycloak、OSS bucket `lychee-erp-assets`、备份前缀、SLS Project `lychee-prod` 都属于这一台机器。没有第二套测试数据，也没有给销售看的演示数据。

## 7. 本专题要解决的事

1. 用同一份 Compose 和同一份镜像描述每一台栈。栈由 `.env` 里的环境（`prod` / `test` / `demo`）和放置方式（大租户独享 / 小租户共用）区分。
2. 为 khh 增加独享测试栈，用户只从 `khh-test.lycheetech.com` 进入。khh 正式只保留 `khh.lycheetech.com`，`lycheetech.com` 退出 ERP。
3. 增加演示栈：演示租户与演示资料，和 khh 的库、对象存储、登录 issuer 分开。
4. 空库能从仓库建起来；新租户有可重复的开通方式。
5. 小租户将来进共用栈（正式、测试各一台）。本波把加入和升格成大租户的规则写清，不购买共用栈机器。
6. `main` 自动部署到 khh 测试栈。演示和 khh 正式用已存在的镜像标签手动发布。
