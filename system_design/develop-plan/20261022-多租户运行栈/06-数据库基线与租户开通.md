# 06. 数据库基线与租户开通

> 让空库能从仓库建起来，让新租户拿到一套可用的系统配置。  
> khh-test 从 khh-prod 备份恢复，不依赖开通；demo 与以后的共用栈依赖本文件。  
> 表结构不变。

---

## 1. 现状

见 [01 §5](./01-现状与问题.md)。要点：

- 基线 `v0/20260617-initial-db.sql` 带 `contextFilter:"!local AND !prod"`，空库在正式和本机的 context 下会跳过基线。
- `v1/` 的数据脚本写死 `tenant_id = 1`、`created_by = 1`，审计列有外键到 `users`，空库上中途失败。集成测试靠 `session_replication_role = replica` 绕过。
- 除 `tenants` 外的表都带 `tenant_id`。系统配置只存在于库里的数据中；`createTenant` 只插 `tenants`。

本机库与正式库已同步。以库为准重新生成基线，旧的 `v0/`、`v1/` 退出 changelog。

## 3. 基线

### 3.1 结构（`01-schema.sql`）

1. 比对本机与正式 `databasechangelog` 的 `id`、`author`、`filename`、`md5sum`，一致后暂停向 `v1/` 合并。
2. 从本机库导出结构：

```bash
pg_dump --schema-only --no-owner --no-privileges --schema=lychee_erp \
  --exclude-table=lychee_erp.databasechangelog \
  --exclude-table=lychee_erp.databasechangeloglock \
  <本机库名>
```

3. 删除 `SET`、`set_config`、`CREATE SCHEMA` 语句。当前 changelog 没有函数、触发器、视图和扩展；导出里若出现，单独成 changeset 并设 `splitStatements:false`。
4. 整个文件是一个 changeset，已有库跳过：

```sql
--liquibase formatted sql
--changeset lychee:baseline-schema
--preconditions onFail:MARK_RAN
--precondition-sql-check expectedResult:0 SELECT count(*) FROM information_schema.tables WHERE table_schema = 'lychee_erp' AND table_name = 'tenants'
```

正式库、本机库、从正式恢复的 khh-test 已有 `tenants`，记为 `MARK_RAN`。空库执行。

schema 本身由数据库初始化脚本建立（[03 §9](./03-环境契约.md)）：Liquibase 的记录表就建在 `lychee_erp` 里，要先有 schema 才能启动。

### 3.2 模板租户（`02-template-tenant.sql`）

- 租户代码 `lychee-template`，状态 `INACTIVE`。没有对应的 realm，不能登录，只作为开通的来源。
- 只在空库执行：前置条件是 `tenants` 没有任何行，否则 `MARK_RAN`。已有库没有模板，也不需要。
- 内容从本机库的 `kimhiephoa` 按 §3.3 的白名单导出：保留原 id；`tenants` 那一行改为模板代码和 `INACTIVE`；引用 `users` 的列（`created_by`、`updated_by`、`granted_by` 等）置 NULL；最后把涉及的序列 `setval` 到各表最大 id。
- 生成后逐表审核，去掉 khh 自定义的内容：自建角色、自定义选项值、改过的编号前缀等。发布后冻结，以后的变化走 `v2/` 增量。

### 3.3 模板白名单（初版）

| 范围 | 表 | 取数 |
|------|----|------|
| 菜单与权限 | `menus`、`permissions` | 全部 |
| 选项 | `option_categories`、`option_values` | `is_system = true` 的分类及其值；另加前后端代码按 code 引用的分类，例如币别 `CURRENCY` |
| 角色 | `roles`、`role_permissions`、`role_hierarchy`、`data_permissions` | `is_system = true` 的角色及其授权；至少一个拥有全部权限的管理员角色 |
| 编号规则 | `sys_doc_rule` | 全部；`sys_doc_sequence` 不取 |
| 单位 | `material_units`、`standard_unit_conversions` | 全部 |
| 物料类型与评估类 | `material_types`、`valuation_classes`、`material_type_valuation_classes` | 全部 |
| 科目与判定 | `gl_accounts`、`fi_account_determination` | 科目表；`company_id IS NULL` 的默认判定 |
| 税 | `tax_classes`、`tax_codes`、`tax_code_rates`、`tax_determinations` | `company_id IS NULL` 的默认行 |
| 付款条件 | `fi_payment_terms`、`fi_payment_term_lines` | 全部 |

不进模板：公司、工厂、部门、仓库、员工、职务、客户、供应商、业务伙伴、物料分类、物料、颜色、尺码、款式、BOM、各类单据、库存与期间、汇率、成本政策、导入导出任务、操作日志、用户与用户角色。这些由开通后的管理员建立。

白名单在实施时逐表核对，结果更新到本表。§6 的验收会暴露遗漏。

### 3.4 后台任务

汇率同步与 MRP 排程经 `RemoteTenantService.findAllTenants()` 遍历全部租户，不看状态。模板没有公司和排程，不会产生数据。以后若给模板加了公司级数据，这两处要跳过非启用租户。

## 4. 开通函数

```sql
lychee_erp.provision_tenant(
  p_code              text,   -- 租户代码，等于 realm 名
  p_name              text,
  p_admin_idp_user_id text,   -- 该 realm 里第一个管理员的用户 ID，即 token 的 sub
  p_admin_username    text
) RETURNS bigint              -- 新租户 id
```

1. 校验 `p_code` 符合 realm 规则、尚不存在，且模板存在。
2. 插入租户，状态 `ACTIVE`。
3. 按依赖顺序复制白名单表里模板的行。新行的 id 由序列生成，外键按自然键重连，不依赖旧 id：`menus.path`、`option_categories.code` 与 `option_values.code`、`roles.code`、`gl_accounts.code`、`material_units.code`、`material_types.code`、`valuation_classes.code`、`tax_codes.code`、`sys_doc_rule.rule_code` 等。审计列为 NULL。
4. 插入管理员 `users`（`idp_user_id`、`username`、`ACTIVE`），绑定拥有全部权限的系统角色。
5. 全部在一个事务里，任何一步失败整体回滚。

`functions/provision-tenant.sql` 设 `runOnChange:true`、`splitStatements:false`。复制清单随白名单变化时直接改这个文件。

在该栈主机的 `deploy` 目录调用：

```bash
docker compose exec -T postgres psql -U lychee_erp -d lychee_erp -v ON_ERROR_STOP=1 \
  -c "SELECT lychee_erp.provision_tenant('demo', 'Demo', '<Keycloak 用户 ID>', 'admin');"
```

页面上的「新增租户」（`TenantServiceImpl.createTenant`）只插 `tenants`，接入开通函数之前不用于开通。接入放到共用栈那一波，届时表单要增加管理员的 Keycloak 用户 ID。

## 5. 增量规则（`v2/` 起）

1. 路径 `db/changelog/v2/<yyyy>/<MMdd>-<序号>-<描述>.sql`。已发布的 changeset 不再修改。
2. 数据脚本对每个租户生效：从 `tenants` 或已有配置行出发，用自然键找父项。写法参照 `0831-002-purchase-return-setup.sql` 的菜单、权限、授权三段；它末尾按 `tenant_id = 1` 兜底的写法不再使用。
3. 不写字面的租户 id、选项 id、用户 id。审计列写 NULL。
4. 新增一张需要默认数据的配置表时，同一次改动里把它加进开通函数的复制清单和 §3.3。
5. 函数、触发器单独成 changeset，`splitStatements:false`。

`workspace.mdc` 与 `backend-development.mdc` 按本节更新。

## 6. 测试与验收

- 删除 `db.changelog-it.yaml` 与其中的 `session_replication_role` 开关；`src/test/resources/application-test.yaml` 里的 changelog 与 context 设置随之删除，集成测试使用正式 master。
- `LiquibaseHarnessIT`：空库跑完全量，开通一个租户，断言：
  - 新租户的 `menus`、`permissions`、`option_values`、`sys_doc_rule` 行数与模板相同；
  - 管理员经 `AssignmentGrantLoader` 取到的权限覆盖全部 `permissions`。
- 其余集成测试自己插入租户、按租户过滤，不受模板影响；若有不分租户的计数断言，改为按租户。
- 本机库：先备份，再启动应用。基线两项为 `MARK_RAN`，开通函数建立；切换前后 `pg_dump --schema-only` 只多出开通函数。
- 演示栈：见 [04 §4](./04-实施清单.md) 第 9 条。

## 7. 切换顺序

1. 暂停 `v1/` 合并，比对两边 `databasechangelog`。
2. 生成并审核 `baseline/`，编写开通函数，改 master，删除 `v0/`、`v1/`，改集成测试。
3. 在本机库与空库上各验证一次。
4. 随一次正常发布进入 khh-test（若已建）和 khh-prod。正式发布前先手动备份。
5. demo 在新基线发布之后开通。
