# 02. 目标架构

> 域名与变量以 [03-环境契约.md](./03-环境契约.md) 为准。本波范围以 [04-实施清单.md](./04-实施清单.md) 为准。数据库基线与租户开通见 [06-数据库基线与租户开通.md](./06-数据库基线与租户开通.md)。

---

## 1. 栈

一台 ECS、一套 Compose、一个 Postgres、一个 Keycloak、一个 OSS bucket、一条备份前缀、一个 SLS Project，构成一个栈。租户不能跨栈共享数据库、issuer 或签名密钥。

| 栈 | 放置 | 环境 | 谁在上面 | 本波 |
|----|------|------|----------|------|
| `khh-prod` | 大租户独享 | `prod` | 仅 `kimhiephoa` | 现网，配置改为按栈注入 |
| `khh-test` | 大租户独享 | `test` | 仅 `kimhiephoa` | 新建 |
| `demo` | 共用形态 | `demo` | 租户 `demo`，以后可加多个演示租户 | 新建 |
| `shared-prod` | 小租户共用 | `prod` | 多个小租户 | 不建机器 |
| `shared-test` | 小租户共用 | `test` | 这些小租户的待发布版本 | 不建机器 |

大租户不进共用栈，也不单独做演示栈。销售演示用虚构资料，放在 `demo`。khh 的验收走 `khh-test`。

以后再出现的大租户沿用 khh 的成对方式：`{标签}-prod` 与需要时的 `{标签}-test`，各一台机器。

## 2. 两类放置

**大租户独享。** 一个栈只有一个租户代码。用户入口、数据库、Keycloak realm、OSS bucket、备份都只属于他。机器规格和停机窗口可以单独安排。khh 是第一个。

独享栈的 issuer 用该栈自己的用户 Host。`khh-prod` 只有一个用户 Host `khh.lycheetech.com`，issuer 是 `https://khh.lycheetech.com/oidc`，由 [05](./05-khh正式issuer切换.md) 先行切换。`khh-test` 的 issuer 是 `https://khh-test.lycheetech.com/oidc`。

**小租户共用。** 多个租户代码在同一套 Postgres（行上的 `tenant_id`）、同一个 Keycloak（一租户一个 realm）、同一个 backend。对象键继续用租户前缀，bucket 属于这一台栈，不按租户再拆 bucket。

共用栈的 issuer 用中性域名，并且不放进 `TENANT_HOSTS`：

| 栈 | issuer |
|----|--------|
| `shared-prod` | `https://auth.lycheetech.com/oidc` |
| `shared-test` | `https://auth-test.lycheetech.com/oidc` |
| `demo` | `https://auth-demo.lycheetech.com/oidc` |

用户从自己的 Host 打开页面，登录跳到该栈 issuer，回调回到当前 Host。issuer 这个 Host 打开首页时，前端发现它不在 `TENANT_HOSTS` 里，停留在未登记地址的提示，不发起登录。`/oidc/` 仍由 Nginx 转到 Keycloak。

演示栈从第一天就用中性 issuer。演示租户增加第二个时，不用改已经写进 token 的 issuer。

用户 Host 与 issuer 都在 `lycheetech.com` 之下，属于同一站点。前端的会话检查 iframe 从 issuer 加载，跨站时会被浏览器的第三方 Cookie 限制拦下。以后若要接客户自有域名，需要另行评估。

## 3. 域名

ERP 用到的名字都是 `lycheetech.com` 下的一层名字。每个名字单独做 A 记录，指向所属栈。不要把 `*.lycheetech.com` 解析到某一台机器。

| 用途 | 名字 | 指向 |
|------|------|------|
| khh 正式用户入口，兼 issuer | `khh.lycheetech.com` | `khh-prod` |
| khh 测试，用户入口兼 issuer | `khh-test.lycheetech.com` | `khh-test` |
| 演示用户入口 | `demo.lycheetech.com` | `demo` |
| 演示 issuer | `auth-demo.lycheetech.com` | `demo` |
| 小租户正式 | `{标签}.lycheetech.com` | `shared-prod` |
| 小租户测试 | `{标签}-test.lycheetech.com` | `shared-test` |
| 额外演示租户 | `{标签}-demo.lycheetech.com` | `demo` |
| 小租户正式 / 测试 issuer | `auth.lycheetech.com`、`auth-test.lycheetech.com` | 对应共用栈 |
| 产品介绍与帮助站 | `lycheetech.com`、`www.lycheetech.com` | 不属于任何栈；`khh-prod` 切换当天起不再指向它 |

标签是 DNS 短名。租户代码是 Keycloak realm 和 `tenants.code`。khh 的标签是 `khh`，代码是 `kimhiephoa`。演示租户的标签和代码都是 `demo`。

同一标签的正式名在全局只能指向一台栈。`khh.lycheetech.com` 已经属于大租户，不会再出现在共用栈上。`www`、`auth`、`cdn` 及其 `-test`、`-demo` 形式保留，不作租户标签。

各栈统一使用 `*.lycheetech.com` 通配证书，私钥放在每一台栈上。通配证书只覆盖一层，所以 ERP 的名字都保持在 `lycheetech.com` 下一层；根域不在其中，也不再需要。

## 4. 镜像与配置

前后端只构建一次，`pnpm run build`。测试和演示不另打前端包。

每台机器的 `deploy/.env`（不入库）至少给出：

- `STACK_ID`：`khh-prod`、`khh-test`、`demo`，以及将来的 `shared-prod`、`shared-test`
- `STACK_PLACEMENT`：`dedicated` 或 `shared`（演示栈是 `shared`）
- `LYCHEE_ENV`：`prod`、`test` 或 `demo`
- `TENANT_HOSTS`：`host=tenantCode`，逗号分隔
- `ISSUER_HOST`：issuer 域名。Keycloak 地址由它推出，不再分别写 `KEYCLOAK_URL`、`KC_HOSTNAME`、`DOMAIN_NAME`
- 该栈的 OSS、CDN，以及只能访问本栈资源的 AccessKey

各栈的 Spring profile 都是 `prod`，环境之间的差别只来自 `.env`。测试条和演示条由 `LYCHEE_ENV` 决定。排查问题时可以临时加 `sql-log` profile 打印 SQL；khh 正式不加。

随栈变化的后端配置（bucket、CDN、CORS、issuer）不给缺省值。缺了就在部署脚本或应用启动时失败，不会悄悄回落到 khh 正式的 bucket。

浏览器访问 API 走当前 Host 的 `/api/`（现网实际就是同源）。运行时的 `API_BASE_URL` 删除。

部署仍会 `git reset --hard origin/main`。随栈变化的内容只留在 `.env` 和证书目录。Nginx 配置由 `render-stack-config.sh` 用入库的模板生成：一个 443 `server` 列出本栈全部 Host，用通配证书；`/`、`/api/`、`/oidc/` 只写一份。Nginx 在运行时按容器名解析地址，重建业务容器后不再需要 reload。

## 5. 发布

```text
push main
  → 构建一次，标签 = 提交号前 8 位
  → 只自动部署到 khh-test

workflow_dispatch，选择栈与标签
  → 部署已经存在的标签，不重新构建
  → khh-prod 需要审核人
```

一次发布是一对标签（backend、frontend），在两个仓库各发一次。后端先发，Liquibase 增量随后端启动执行。

演示不跟每一次 `main`。演示保持一个已知可用的标签。共用栈以后加入时，在发布矩阵里增加对应的 GitHub Environment：`shared-test` 跟 `main`，`shared-prod` 跟 khh 正式一样手动并审核。

各栈 `.env` 记录自己的镜像标签。标签使用提交号，不再推 `latest`。

部署时 `lychee-infra` 总是取 `main`，infra 的改动会在该栈下一次部署时生效。发布 khh-prod 之前，当时的 infra `main` 必须已经在 khh-test 部署过。

## 6. 数据库与租户开通

- 以本机库（与正式同步）重新生成 Liquibase 基线。空库从基线建起；已有库把基线记为已执行，不重跑。
- 空库里带一个不能登录的模板租户，存一套系统配置：菜单、权限、选项、系统角色、编号规则、科目表等。
- 开通函数 `provision_tenant` 从模板复制一套配置给新租户，并建第一个管理员。
- 以后的数据脚本对每个租户生效，不再写 `tenant_id = 1`。

khh-test 从 khh-prod 备份恢复，不需要开通；demo 和以后的共用栈靠开通函数。

## 7. 小租户怎么加、大租户怎么分出去

小租户加入共用栈时，不新开 ECS：

1. 在该栈 Keycloak 新建 realm，client 的回调只登记这个租户的 Host。建第一个管理员用户。
2. 在该栈业务库执行 `provision_tenant`：租户代码 = realm 名，管理员 = 上一步的 Keycloak 用户 ID。
3. DNS 把 `{标签}.lycheetech.com` 指到 `shared-prod`，`{标签}-test.lycheetech.com` 指到 `shared-test`，并放好证书。
4. 两台共用栈的 `TENANT_HOSTS` 各加一行，执行 `render-stack-config.sh`，再 `docker compose up -d backend frontend`，让 CORS 和前端的 Host 表一起更新。

升格为大租户时，新建独享正式栈（以及需要的测试栈），把该租户的 realm、业务数据和 OSS 前缀迁到新栈，再把 `{标签}.lycheetech.com` 的 DNS 改到新机器，并从共用栈的 `TENANT_HOSTS` 删除。issuer 从 `auth.lycheetech.com` 变为该租户自己的 Host，用户需要重新登录。这一步是独立运维操作，本波不写迁移脚本。

判断仍放在共用栈的情形：可以接受与其他小租户同库备份、同一次停机。需要单独的备份恢复窗口、不能与其他客户同库，或长期占满共用栈的 CPU、内存、连接时，改为独享栈。

共用栈的 `env-config.js` 会列出该栈全部租户 Host。若不希望访客看到客户名单，届时改为由 Nginx 按 Host 只返回当前租户。本波没有共用栈，不做。

## 8. 数据边界

| 允许 | 不允许 |
|------|--------|
| khh 测试栈在明确操作下，从 `khh-prod` 的备份恢复业务库，再把 `users.idp_user_id` 改为测试 Keycloak 的用户 | 把 khh 正式库恢复进 `demo` 或任何共用栈 |
| 各栈的 Keycloak 在本栈建立 | 把任何一栈的 keycloak 库恢复到另一栈 |
| 演示栈使用租户 `demo` 的虚构资料 | 演示 realm 使用 `kimhiephoa`，或复用 khh 的用户口令 |
| 各栈备份写到 `backup-postgres/${STACK_ID}/` | 两台正式栈共用一个前缀 |
| 每栈的应用和备份各用一个只能访问本栈 bucket、本栈备份前缀的 AccessKey | 测试栈、演示栈或本机开发持有正式 bucket 的写权限 |
| 运维经 SSH 隧道访问数据库和 Keycloak 管理台 | 从公网直连数据库端口，或从公网打开 Keycloak 管理台 |

keycloak 库里有用户口令哈希和 realm 签名私钥，只留在本栈。khh-test 的测试账号在测试 Keycloak 里建立；刷新业务库后，按映射文件把 `users.idp_user_id` 改成测试账号的用户 ID，没有映射的正式用户在测试栈不能登录。

khh 正式栈现有备份在 `backup-postgres/daily|weekly|monthly/`。切换后新备份写入 `backup-postgres/khh-prod/`。旧前缀留到生命周期过期。恢复脚本只接受本栈的备份；khh-test 加上显式参数时可以取 khh-prod 的业务库备份，包括旧前缀。

本机开发改用 khh 测试栈的 bucket 和只限该 bucket 的 AccessKey。

SLS 已有 Project `lychee-prod` 继续作为 khh 正式栈，不改名。新栈使用 `lychee-khh-test`、`lychee-demo`。

## 9. 页面提示

`LYCHEE_ENV=test` 显示测试条。`LYCHEE_ENV=demo` 显示演示条。`prod` 不显示。提示帮助辨认环境，不代替 Host 和权限。
