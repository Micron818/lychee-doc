## 2. Host 清单与生成脚本

```bash
# khh-prod
TENANT_HOSTS=khh.lycheetech.com=kimhiephoa

# khh-test
TENANT_HOSTS=khh-test.lycheetech.com=kimhiephoa

# demo
TENANT_HOSTS=demo.lycheetech.com=demo
```

约定：

- Host 小写，不含协议、端口和路径，是 `lycheetech.com` 下的一层名字（通配证书只覆盖一层）。同一个 Host 在全局只属于一台栈，在本栈清单里只出现一次。
- `tenantCode` 符合现有 realm 规则：字母或数字开头，后续为字母、数字、`.`、`_`、`-`，最长 50。
- `dedicated`：全部 Host 是同一个 `tenantCode`，`ISSUER_HOST` 是其中之一。
- `shared`：`ISSUER_HOST` 不在 `TENANT_HOSTS` 里。

`deploy/render-stack-config.sh`：部署脚本每次先执行它，人工改 `.env` 后也先执行它。

1. 读 `deploy/.env`，检查 §3 的必填键存在且非空。
2. 按上面的约定校验 `TENANT_HOSTS`、`ISSUER_HOST`、`STACK_PLACEMENT`。
3. 检查证书：`docker/certs/wildcard.lycheetech.com.pem` 与 `.key` 存在，证书覆盖本栈每个 Host，且尚未过期。
4. 先写临时文件，全部通过后再替换：
   - `docker/nginx/conf.d/stack.conf`：用模板 `docker/nginx/stack.conf.template` 生成（§6）
   - `.env.stack`：`APP_CORS_ALLOWED_ORIGINS`，只含租户 Host 的 `https://` 来源
5. 任何一步失败即以非零退出，已有的生成文件保持不变。

`NGINX_SERVER_NAMES` 是 `TENANT_HOSTS` 的全部 Host 加上 `ISSUER_HOST`（去重），空格分隔。

两份生成文件不入库。`stack.conf` 变化后执行 `nginx -t`，通过再 `nginx -s reload`。`.env.stack` 或 `TENANT_HOSTS` 变化后重建 backend 与 frontend。

## 5. 后端配置

`application-prod.yaml` 中随栈变化的值改为占位，不给缺省：

```yaml
aliyun:
  oss:
    endpoint: ${ALIYUN_OSS_ENDPOINT}
    bucket-name: ${ALIYUN_OSS_BUCKET_NAME}
    access-key: ${ALIYUN_OSS_ACCESS_KEY:}
    secret-key: ${ALIYUN_OSS_SECRET_KEY:}
  cdn:
    domain: ${ALIYUN_CDN_DOMAIN}
    auth-key: ${ALIYUN_CDN_AUTH_KEY:}
app.cors.allowed-origins: ${APP_CORS_ALLOWED_ORIGINS}
```

- `@ConfigurationProperties` 遇到解析不了的 `${...}` 会把原文当值绑定进去，不会启动失败。启动时校验 `aliyun.oss.endpoint`、`aliyun.oss.bucket-name`、`aliyun.cdn.domain` 非空且不含 `${`，做法与 `MultiTenantJwtDecoder` 校验 issuer 相同。`app.cors.allowed-origins` 经 `@Value` 注入，缺了会直接启动失败。
- `issuer-base-uris: ${KEYCLOAK_URL}` 保持不变。
- 删除 `spring.liquibase.contexts`（[06 §2](./06-数据库基线与租户开通.md)）。
- 新增 `application-sql-log.yaml`，内容取 `application-local.yaml` 中 datasource-proxy 与 `jdbc.sql` 日志的设置。`DataSourceProxyLoggingConfig` 的 `@Profile("local")` 改为 `@Profile({"local", "sql-log"})`：内联 SQL 的 listener 只在这个配置类里注册，只打开 `decorator.datasource.enabled` 不会有输出。
- 不在 `src/main` 新增 `application-test.yaml`。`src/test/resources` 已有同名文件供集成测试（`@ActiveProfiles("test")`）使用，两者在测试 classpath 上会互相遮蔽。
- `application-local.example.yaml` 的 bucket 与 CDN 改为 khh 测试栈的值。

## 6. Nginx

```text
deploy/docker/nginx/
  stack.conf.template      入库：唯一的一份 server 与 location
  conf.d/stack.conf        由 render-stack-config.sh 生成，不入库
```

现有 `conf.d/default.conf` 从仓库删除。生成时只替换 `${NGINX_SERVER_NAMES}`，Nginx 自己的 `$host` 等变量原样保留。

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;

# 不在清单里的 Host 和直接用 IP 访问：80 断开，443 拒绝握手
server { listen 80 default_server; return 444; }
server { listen 443 ssl default_server; ssl_reject_handshake on; }

server {
    listen 80;
    server_name ${NGINX_SERVER_NAMES};
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name ${NGINX_SERVER_NAMES};
    ssl_certificate     /etc/nginx/certs/wildcard.lycheetech.com.pem;
    ssl_certificate_key /etc/nginx/certs/wildcard.lycheetech.com.key;
    # SSL 协议与加密套件与现网相同

    location / {
        set $lychee_frontend http://frontend:80;
        proxy_pass $lychee_frontend;
        # 转发头与现网相同
    }

    location /api/ {
        set $lychee_backend http://backend:9000;
        proxy_pass $lychee_backend;
        # 转发头、WebSocket 与现网相同
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    location /oidc/ {
        set $lychee_keycloak http://keycloak:8080;
        proxy_pass $lychee_keycloak;
        # 转发头与现网相同
    }

    # 管理台与 master realm 只经 SSH 隧道访问（§8）
    location /oidc/admin/ { return 404; }
    location /oidc/realms/master/ { return 404; }
}
```

- 上游写成变量，配合 `resolver` 在运行时解析容器名。容器重建换 IP 后不用 reload。
- 上游变量不带 URI，请求路径原样转发，与现网的 `http://backend:9000/api/`、`http://keycloak:8080/oidc/`、`http://frontend:80` 效果相同。
- issuer 专用 Host 与用户 Host 走同一份 location，它的首页由前端显示未登记提示。不在清单里的名字（包括切换后的 `lycheetech.com`）在 TLS 握手时被拒。

## 8. Keycloak

每个栈一个 Keycloak，`KC_HOSTNAME` 由 `ISSUER_HOST` 推出。keycloak 库里有用户口令哈希和 realm 签名私钥，只留在本栈，不恢复到别的栈。

每个用户 Host 在其 realm 的 client `lychee-erp-web` 上登记：

- 合法重定向：`https://{host}/auth/callback`
- 登出回跳：`https://{host}`
- Web Origin：`https://{host}`

khh 正式切换后，从 client 删除 `https://lycheetech.com` 的三项。

**khh-test。** 首次开栈时新建 realm `kimhiephoa` 与 client `lychee-erp-web`，只登记 `khh-test.lycheetech.com`。主题、语言等设置可从正式 realm 做「部分导出」后导入，导出不含用户；导入后到 Keys 页确认密钥是本栈新生成的，若带进了正式的密钥就删除重建。测试账号在测试 Keycloak 里建立，口令与正式无关。刷新业务数据时不动 keycloak 库，账号对应关系见 §9。

**demo。** 新建 realm `demo` 与 client `lychee-erp-web`（public client、Standard flow、PKCE S256），只登记 `demo.lycheetech.com`。不从 khh 复制用户。第一个管理员的用户 ID 用于开通（[06 §4](./06-数据库基线与租户开通.md)）。

### 管理入口

数据库和 Keycloak 管理台不对公网开放，各栈相同：

- Compose 的 `5432`、`8080`、`9000`、`8081` 只绑定 `127.0.0.1`（§4）。
- `KC_HOSTNAME_ADMIN=http://127.0.0.1:8080/oidc`；Nginx 对 `/oidc/admin/` 与 `/oidc/realms/master/` 返回 404（§6）。
- 管理员先建隧道 `ssh -L 8080:127.0.0.1:8080 <主机>`，再打开 `http://127.0.0.1:8080/oidc/admin/`。直连数据库同样经隧道。
- 安全组只放行 22、80、443。

原因：

1. Compose 原先把这四个端口发布在主机的所有网卡上。Docker 自己写 iptables 规则，主机防火墙（如 ufw）拦不住它们，能挡住的只有安全组。安全组一旦放行，公网就能直连数据库尝试口令，或绕过 Nginx 访问 Keycloak 和 backend。
2. Nginx 的 `/oidc/` 原先把 Keycloak 整个转出去，包括管理台和 master realm，任何人都能打开管理台登录页。master realm 的管理员可以管理全部 realm 和用户；首次启动建的临时管理员（`KC_BOOTSTRAP_ADMIN_*`）若仍在用且口令弱，从公网就能登录。

khh-prod 在切换前确认没有依赖公网端口的用法（例如经 5432 同步正式库），并确认临时管理员已经换成正式管理员账号（[04 §3.8](./04-实施清单.md)）。

## 9. 数据库初始化、备份与恢复

**初始化。** `docker/postgres/init.sql` 改为 `init.sh`，口令从环境变量取，不再写进仓库：

```bash
psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
     -v app_pw="$LYCHEE_DB_PASSWORD" -v kc_pw="$KEYCLOAK_DB_PASSWORD" <<'SQL'
CREATE ROLE lychee_erp LOGIN PASSWORD :'app_pw';
CREATE DATABASE lychee_erp OWNER lychee_erp;
CREATE ROLE keycloak LOGIN PASSWORD :'kc_pw';
CREATE DATABASE keycloak OWNER keycloak;
\connect lychee_erp
CREATE SCHEMA lychee_erp AUTHORIZATION lychee_erp;
SQL
```

`postgres` 服务传入 `LYCHEE_DB_PASSWORD: ${SPRING_DATASOURCE_PASSWORD}` 与 `KEYCLOAK_DB_PASSWORD: ${KC_DB_PASSWORD}`。初始化脚本只在数据目录为空时执行，对 khh 正式没有影响。现有 `init.sql` 里的口令与 khh 正式相同，已在仓库历史中，建议在 khh 正式轮换。

应用连接 URL 不带 `currentSchema`，依赖 `search_path` 的 `"$user"` 落到 schema `lychee_erp`，所以数据库用户名固定为 `lychee_erp`。

**备份。** `backup_to_oss.sh` 从 `deploy/.env` 读 `STACK_ID`（crontab 不会带入这些变量），为空即退出。上传到 `oss://lycheetech-standard/backup-postgres/${STACK_ID}/daily|weekly|monthly/`。容器名各机仍是 `lychee-postgres`。

**恢复。** `restore_from_oss.sh` 的参数是 `backup-postgres/` 之下的对象键：

```bash
bash restore_from_oss.sh demo/golden/lychee_erp_20261105_020000.sql.gz
# 仅 khh-test：
bash restore_from_oss.sh --from-prod khh-prod/daily/lychee_erp_20261105_020000.sql.gz
bash restore_from_oss.sh --from-prod --idp-map /home/deployer/lychee/idp-map.csv \
  daily/lychee_erp_20261020_020000.sql.gz          # 正式旧前缀
```

- 对象键第一段是栈名。第一段是 `daily`、`weekly`、`monthly` 时，视为 `khh-prod` 的旧前缀。
- 栈名等于本机 `STACK_ID`：允许。
- 栈名是 `khh-prod`，本机 `STACK_ID=khh-test`，并带 `--from-prod`：只允许 `lychee_erp_` 开头的业务库备份。keycloak 库不跨栈恢复。
- 其余一律拒绝，以非零退出，不碰数据库。
- 恢复 `lychee_erp` 前停 backend，恢复 `keycloak` 前停 keycloak，完成后再启动。

脚本是第二道防线。第一道是账号权限（§10）：演示机的备份账号读不到 `khh-prod/`，khh-test 的备份账号也读不到正式的 keycloak 备份。

**khh-test 刷新后的账号对应。** 正式业务库里的 `users.idp_user_id` 是正式 Keycloak 的用户 ID，在测试 Keycloak 里不存在。`--from-prod` 恢复时，脚本：

1. 删库前，把当前测试库 `kimhiephoa` 的 `users` 导出为 `id,username,idp_user_id`，存到 `/home/deployer/lychee/idp-map/<时间>.csv`。
2. 恢复后改写 `users.idp_user_id`。缺省用第 1 步导出的文件，即原测试库的设定；带 `--idp-map <文件>` 时以该文件为准，可在其中改填指定的测试 Keycloak 用户 ID。
3. 映射文件每行按 `id` 匹配；`id` 为空时按 `username` 匹配，同名多于一个则失败。`username` 与 `id` 对不上时提示。`(tenant_id, idp_user_id)` 有唯一约束，同一个测试用户 ID 不能分给两个用户。
4. 输出更新了几个用户、映射里有哪些行在正式数据里找不到、还有几个用户保留正式的 ID。保留正式 ID 的用户在测试栈不能登录。

首次开栈时测试库是空的，没有可导出的设定，要先手工准备映射文件。`LYCHEE_PLATFORM_ADMINS` 同样写测试 Keycloak 的用户 ID。

## 10. OSS、CDN 与 RAM

| 账号 | 用在 | 权限 |
|------|------|------|
| 栈应用账号 | `.env` 的 `ALIYUN_OSS_ACCESS_KEY` | 本栈 bucket 读写 |
| 栈备份账号 | 主机上的 `ossutil` | `lycheetech-standard` 的 `backup-postgres/{STACK_ID}/` 读写 |
| khh-test 刷新时临时追加 | khh-test 备份账号 | 只读 `backup-postgres/khh-prod/` 与旧 `daily|weekly|monthly/` 下 `lychee_erp_` 开头的对象，刷新后撤销 |
| 本机开发 | `application-local.yaml` | khh 测试 bucket 读写 |

正式 bucket 的 key 只出现在 khh 正式机上。

khh-test 需要附件时，由运维账号把正式 bucket 的对象同步到测试 bucket，测试机不持有正式 bucket 的权限。业务库存的是对象键，签名 URL 由后端按本栈 CDN 生成，恢复后不用改库。

每个 CDN 名字配 HTTPS（可用同一张通配证书）和 URL 鉴权（A 方式），鉴权 key 写入该栈的 `ALIYUN_CDN_AUTH_KEY`。

备份生命周期按栈前缀配置：`{STACK_ID}/daily/` 7 天、`{STACK_ID}/weekly/` 30 天、`{STACK_ID}/monthly/` 180 天。`demo/golden/` 不设生命周期。正式旧前缀的规则保留到对象过期。

## 12. CI

| 工作流 | 触发 | GitHub Environment | 行为 |
|--------|------|--------------------|------|
| 构建 | `push` `main` | — | 构建并推送 `<提交号前 8 位>`，不再推 `latest`；成功后部署到 `khh-test` |
| 手动部署 | `workflow_dispatch`，输入栈（`khh-test`、`demo`、`khh-prod`）与标签 | 所选栈 | 只部署，不构建；`khh-prod` 需要审核 |

两条都调用同一个可复用的部署工作流（`workflow_call`）。不要在同一个工作流里用 `needs` 把手动部署挂在构建后面：构建被跳过时，依赖它的部署也会被跳过。

部署步骤：

1. 标签必须匹配 `^[0-9a-f]{8}$`。
2. SSH 到该 Environment 的主机，取部署锁，`git fetch` 后 `git reset --hard origin/main`。
3. 执行 `deploy/deploy-service.sh <backend|frontend> <标签>`。脚本入库，前后端共用：
   1. 执行 `render-stack-config.sh`；失败即退出，运行中的容器不动。
   2. `docker pull` 该标签；失败即退出，`.env` 不改。
   3. 写 `.env` 的 `BACKEND_TAG` 或 `FRONTEND_TAG`，`docker compose up -d --no-deps <服务>`。
   4. `nginx -t` 通过后 `nginx -s reload`，让 infra 带来的新配置生效。
   5. 清理旧镜像。

主机与密钥放在对应 Environment，不放仓库级的单一 `HOST`。现网 SSH 密钥放入 `khh-prod`。

增加共用栈时，新建同名 Environment 并把栈名加入手动部署的选项。`shared-test` 并入构建后的自动部署，`shared-prod` 与 `khh-prod` 一样只接受手动发布。
