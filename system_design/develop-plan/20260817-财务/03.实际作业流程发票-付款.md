
# 发票

应付发票（AP Invoices）的录入和归属，情况如下：

### 1. 哪个部门的人员负责建立（录入） AP 发票？

绝大多数情况下，应付发票的系统录入工作由**财务部门（Finance / Accounting Department）**中专门的**应付会计（AP Accountant）或出纳**来负责。

**为什么是财务部门？**
*   **票据合规性检查**：当发票（如增值税专用发票或普票）从供应商邮寄或电子推送到公司后，第一步必须验证发票的真伪、税率是否正确、抬头是否合规。这是财务的专业领域。
*   **税务抵扣**：对于专票，财务需要拿着这发票去税务系统做进项税认证抵扣。
*   **账务控制**：一旦 AP 发票在系统中审核通过（Approved / Posted），系统会自动抛转生成财务凭证（Journal Entry，借：相关资产/费用，贷：应付账款）。这意味着正式承认了公司的对外负债，这是一项非常严肃的财务动作。

**极少数例外情况：**
在一些管理非常扁平的小型企业，或者使用某些 SaaS 平台时，为了图方便，可能会让采购人员在收到发票时顺手把金额录入系统。但在有内控要求的企业，这种“既负责采购又负责承认债务”的做法是违背职责分离原则的。

### 2. 在 ERP 系统中，AP 发票放在哪个模块作业？

AP 发票通常放在**财务模块（FI - Financial Accounting）**或更细分的**应付账款模块（AP - Accounts Payable）**中作业。它处于供应链和财务的交汇处（即 Procure-to-Pay 流程的尾端）。

在规范的 ERP 菜单结构中，通常是这样布局的：

#### 方案 A：独立作为财务子模块（最常见，如 SAP, Oracle, MS Dynamics）
*   **模块名称**：财务管理 (Financials) -> 应付账款 (Accounts Payable)
*   **功能菜单**：
    *   发票录入 (Invoice Entry / Workbench) -> **在这里建立 `ap_invoices`**
    *   付款申请 (Payment Requests)
    *   付款执行 (Payments / Disbursements)
    *   供应商对账表 (Supplier Aging / Statement)

#### 方案 B：挂在采购与付款流程中（中小型 ERP 或 Odoo 常见）
*   **模块名称**：采购管理 (Purchasing) 或 进销存
*   **功能菜单**：
    *   采购订单 (Purchase Orders)
    *   收货单 (Goods Receipts)
    *   **供应商账单/发票 (Vendor Bills / Invoices) -> 这里建立 `ap_invoices`，但通常权限仅赋予财务角色**

### 3. 实际的 Procure-to-Pay (P2P) 操作流程是怎样的？

为了让您更直观地理解，以下是系统中真实发生的一整套连贯动作：

1.  **采购部**：在采购模块建立【采购订单 PO】。
2.  **仓储部/需求部门**：货品到达后，在库存/收货模块建立【收货单 GR】。
3.  （等待几天或几周...）
4.  **财务部（AP会计）**：收到供应商寄来的纸质或电子发票。
5.  **财务部（AP会计）**：打开 ERP 的**【财务-应付账款-发票录入】**界面。
    *   输入发票号、发票日期。
    *   系统提示：你想根据哪张单据开票？
    *   会计选择对应的【采购订单】或【收货单】。
    *   系统**自动带出**收货的数量和采购的价格（这就是我们之前讨论的三单匹配）。
    *   会计核对纸质发票和系统带出的数据。如果一致，点击保存，生成 `ap_invoices` 记录。
6.  **系统后台**：保存并发票生效后，系统自动生成 `journal_entries`（财务传票）。

**总结：**
`ap_invoices` 是一个**强财务属性**的业务单据。它由**财务人员**在**财务的 AP 子模块**中建立，但它的数据源头必须紧密依赖前端的采购和收货数据。

# 付款

财务建立 `ap_invoices`（应付发票）只是承认了企业的对外负债，距离实际把钱付给供应商，还需要经过一个严谨的审批和执行流程。在规范的 ERP 和企业资金管理中，付款流程（Disbursement Process）通常是这样展开的：

### 1. 发票确认与账期管理（确认该付多少，什么时候付）
*   **账期（Payment Terms）生效**：当 `ap_invoices` 被确认（POSTED）后，系统会根据发票上的 `invoice_date`（发票日期）或收货日期，结合供应商主数据中配置的账期（如：月结30天、货到60天等），自动计算出 `due_date`（到期日）。
*   **应付账款账龄表（AP Aging Report）**：发票进入应付账款池。财务主管可以随时查看账龄表，清楚地知道哪些款项快到期了，哪些已经逾期。这就是我们在前面对话中提到的“下月初汇总付款”的基础数据来源。

### 2. 付款申请（Payment Request）—— 发起付款意愿
*   并不是发票到期了出纳就会自动打款。付款通常需要有人主动发起申请。
*   **谁发起？** 取决于公司制度。有些公司由采购员/业务员发起（因为他们最清楚业务进度），有些公司由应付会计（AP Accountant）定期汇总发起。
*   **在 ERP 中如何操作？** 员工在 ERP 中创建一张【付款申请单】。
    *   他会勾选需要付款的 `ap_invoices`（可以选多张发票，也就是多单汇总付款）。
    *   可以申请全额付款，也可以申请部分付款（例如发票金额 10万，本次只申请付 5万）。
*   **审批流（Workflow）**：付款申请提交后，通常会触发严格的审批流（部门经理 -> 财务总监 -> 甚至总经理/CEO，视金额大小而定）。

### 3. 付款排程与准备（Payment Proposal / Run）—— 出纳接手
*   付款申请全部审批通过后，会流转到**出纳（Cashier / Treasury）**手中。
*   出纳每天或每周（例如您的场景中是“下月初”）会查看所有已审批的待付款项。
*   **资金计划考虑**：出纳会根据公司当前的银行存款余额，决定今天到底付哪几笔款。在大型 ERP 中，这叫做建立付款建议（Payment Proposal）。出纳会指定用哪个银行账号（如：招商银行基本户）来支付这些款项。

### 4. 付款执行（Payment Execution）—— 实际的资金流出
这是流程的最后一步，也是真正动钱的一步。

*   **网银打款**：出纳登录企业网银，将钱转给供应商。更高级的 ERP 可以实现“银企直联（Host-to-Host）”，在 ERP 里点击付款，直接指令银行汇款。
*   **ERP 系统核销（建立 Payment 单据）**：
    *   出纳在 ERP 中录入一笔【付款单】（`ap_payments` 表的记录）。
    *   付款单会记录实际付款金额、付款日期、使用的银行账户等信息。
    *   **关键动作（核销 Allocation / Clearing）**：出纳必须在 ERP 中将这笔付款金额与对应的 `ap_invoices` 进行匹配核销。比如付了 10 万，明确告诉系统这 10 万是用来核销 Invoice A 和 Invoice B 的（这就用到了 `payment_allocations` 表）。
    *   核销完成后，被核销的发票的 `payment_status` 会从 'UNPAID' 变为 'PAID'，`remaining_amount` 会减为 0。

### 5. 生成付款的财务凭证（Journal Entry）
当付款单确认并核销发票后，系统会自动抛转生成付款的财务凭证：
*   **借：** 应付账款（冲减负债）
*   **贷：** 银行存款（资产减少）

---

### 总结：数据流的演进

1.  **收货** -> 2. **建立发票** (`ap_invoices`，生成凭证：借 费用/库存，贷 应付账款) -> 3. **付款申请审批**（可选，部分公司在发票环节审批） -> 4. **建立付款单** (`payments` 记录资金流出) -> 5. **付款核销** (`payment_allocations` 把付款和发票绑在一起) -> 6. **最终凭证**（生成凭证：借 应付账款，贷 银行存款）。
