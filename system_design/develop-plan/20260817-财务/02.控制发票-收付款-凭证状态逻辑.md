单据的状态分为两类：**生命周期状态（Lifecycle Status）** 和 **业务执行状态（Business Status，如收付款状态）**。

以下是对 `ar_invoices`, `ap_invoices`, `payments`, `journal_entries` 四个核心表状态定义的深度剖析和防错设计：

---

### 一、 核心状态定义规范

建议为这四个表制定高度统一的**生命周期状态 (`status` / `invoice_status`)**：
*   **`DRAFT` (草稿)**：初始录入，可任意修改、删除。不产生任何财务影响。
*   **`PENDING_APPROVAL` (待审批)**：提交审核中，锁定修改。
*   **`APPROVED` (已审批)**：业务主管确认无误，准备抛转财务。
*   **`POSTED` (已过账)**：**核心分水岭**。单据已生效，已生成财务凭证（Journal Entry）。**绝对不可修改，绝对不可物理删除**。
*   **`VOIDED` (已作废)**：单据被取消。如果单据在 `POSTED` 之后作废，必须伴随“红字冲销”逻辑。

对于发票表，还需要保留**业务执行状态 (`payment_status` / `receipt_status`)**：
*   **`UNPAID` / `UNRECEIVED` (未收付)**
*   **`PARTIAL` (部分收付)**
*   **`PAID` / `RECEIVED` (已结清)**

---

### 二、 不同单据间的状态逻辑控制（正常流程）

单据之间的流转必须遵循严格的**前置条件依赖**：

#### 1. 发票 (Invoices) -> 凭证 (Journal Entries)
*   **触发点**：当发票状态变为 `POSTED` 时。
*   **动作**：系统自动生成一张 `journal_entries`，且该凭证的状态直接为 `POSTED`（因为业务单据已审批，财务凭证通常自动生效）。
*   **约束**：只有状态为 `APPROVED` 的发票才能执行“过账(Post)”动作。

#### 2. 发票 (Invoices) -> 收付款单 (Payments)
*   **约束**：**只有 `POSTED` 状态的发票，才能被 `payments` 引用和核销**。
    *   *防错说明*：绝不能对一张 `DRAFT` 的发票付款，因为发票金额可能还会改，会导致核销金额对不上。

#### 3. 收付款单 (Payments) -> 凭证 (Journal Entries) & 发票 (Invoices)
*   **触发点**：当 `payments` 状态变为 `POSTED` 时。
*   **动作 A（生成凭证）**：系统自动生成一张付款凭证（借：应付账款，贷：银行存款），状态为 `POSTED`。
*   **动作 B（反写发票状态）**：系统根据 `payment_lines` 中的核销金额，反写对应发票的 `remaining_amount`。
    *   如果 `remaining_amount` == 0，发票的 `payment_status` 自动变为 `PAID`。
    *   如果 `remaining_amount` > 0，发票的 `payment_status` 自动变为 `PARTIAL`。

---

### 三、 开错或特殊原因的异常处理（防错与合理性控制）

这是 ERP 设计中最容易出 Bug 的地方。必须遵循**“后置单据阻断前置单据”**的原则。

#### 场景 1：发票开错了，但还未过账（状态：DRAFT 或 APPROVED）
*   **处理**：直接修改内容，或者将状态改为 `VOIDED`。
*   **合理性**：因为没有生成 `journal_entries`，也没有被 `payments` 引用，随便改，无财务风险。

#### 场景 2：发票开错了，且已经过账（状态：POSTED），但【未付款】
*   **处理**：执行**“发票作废 (Void)”**操作。
*   **系统联动逻辑**：
    1.  发票状态变为 `VOIDED`。
    2.  **严禁物理删除原凭证！** 系统必须自动生成一张**“冲销凭证 (Reversal Journal Entry)”**。
        *   原凭证：借 费用 100，贷 应付 100。
        *   冲销凭证：借 费用 -100，贷 应付 -100（或相反方向）。
    3.  将原凭证的 `status` 更新为 `REVERSED`（已冲销），新凭证状态为 `POSTED`，并将新凭证的 ID 写入原凭证的 `reversal_entry_id`。

#### 场景 3：发票开错了，已经过账（POSTED），且【已经付款】（Payment 也是 POSTED）
*   **防错控制（硬性拦截）**：**系统必须报错，禁止直接作废发票！** 提示：“该发票已有核销记录，请先作废对应的收付款单。”
*   **正确的处理路径**：
    1.  **第一步：作废付款单 (Void Payment)**。
        *   将 `payments` 状态改为 `VOIDED`。
        *   系统生成付款单的“冲销凭证”。
        *   **关键联动**：释放发票额度。系统自动将对应发票的 `remaining_amount` 加回来，并将发票的 `payment_status` 退回为 `UNPAID`。
    2.  **第二步：作废发票 (Void Invoice)**。
        *   此时发票已变成“未付款”状态，回到【场景 2】的逻辑，允许作废发票并生成发票的冲销凭证。

#### 场景 4：手工录入的财务凭证 (Journal Entries) 录错了
*   **约束**：如果是系统自动生成的凭证（`journal_type` = 'AUTO'），**禁止手工修改或作废**。必须通过作废源头业务单据（发票/付款单）来触发冲销。
*   **处理**：如果是手工凭证（`journal_type` = 'MANUAL'）且已 `POSTED`，允许执行“冲销”操作，生成红字凭证，原凭证状态变为 `REVERSED`。

---

### 四、 总结：对当前 SQL 设计的最终调整建议

四张表的状态字段约束：

1.  **`ap_invoices` / `ar_invoices`**:
    *   `invoice_status`: `DRAFT`, `PENDING_APPROVAL`, `APPROVED`, `POSTED`, `VOIDED`
    *   `payment_status`: `UNPAID`, `PARTIAL`, `PAID`
2.  **`payments`**:
    *   `status`: `DRAFT`, `PENDING_APPROVAL`, `APPROVED`, `POSTED`, `VOIDED` (统一使用 VOIDED 代替 CANCELLED)
3.  **`journal_entries`**:
    *   `status`: `DRAFT`, `PENDING_APPROVAL`, `APPROVED`, `POSTED`, `VOIDED`, **`REVERSED`** (REVERSED 专门用于标记被红字冲销过的历史凭证)。
