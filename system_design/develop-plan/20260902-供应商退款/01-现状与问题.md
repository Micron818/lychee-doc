# 01. 供应商退款现状与问题（As-Is）

> 评估对象：已付款 AP 因数量型采购退货产生应付贷项后，供应商把现金退回公司。  
> 当前应付贷项 V1 只处理原票未付剩余；本专题承接其明确排除的“已付部分退款”。

---

## 1. 当前单据链

现网已具备：

```text
采购订单 → 收货 → AP 发票 → 付款
                    │
                    └→ 应付贷项（仅可冲未付 remaining）
                           │
                           └→ 释放占用 → 采购退货
```

当前缺口：

```text
AP 已付款 → 应付贷项涉及已付部分 → 供应商实际退款 → 银行入账并核销
```

采购退货、应付贷项和资金退款是三条不同账：

| 维度 | 单据 | 当前状态 |
|------|------|----------|
| 库存 | `purchase_returns` | 已实现 |
| 采购负债、税与暂估 | `ap_credit_memos` | 已实现，但仅限未付部分 |
| 供应商退回资金 | `payments` 的供应商收款方向 | 尚未形成业务能力 |

---

## 2. 应付贷项 V1 的限制

### 2.1 只能贷原票未付剩余

贷项过账时：

```text
creditMemo.total_amount ≤ apInvoice.remaining_amount
remaining = total_amount − paid_amount − credited_amount
remaining < 0 → 拒绝
```

因此：

```text
AP 100，已付 100，remaining = 0
要贷 40 → 40 > 0 → 过账失败
```

相关实现：

- `ApCreditMemoPostingServiceImpl.postCreditMemo` 锁原 AP 后以 `remaining` 卡住贷项总额。
- `ApInvoiceRemainingSupport.apply` 不允许 remaining 为负。
- `ap_invoices.credited_amount` 当前既表示贷项合计，又直接参与 remaining 公式。

这套模型适合“贷项直接结清尚未支付的 AP”，不能表达“贷项超过未付金额后形成供应商应退余额”。

### 2.2 贷项不是开放项

`ap_credit_memos` 当前只有生命周期状态：

```text
DRAFT → PENDING_APPROVAL → APPROVED → POSTED → VOIDED
```

没有：

- 冲抵原 AP 的金额；
- 由已付部分形成的可退款金额；
- 已收到退款金额；
- 待退款余额；
- 退款结算状态。

贷项 V1 过账即被视为全部应用到原 AP，因此 `payment_lines` 也没有 `ap_credit_memo_id`。

---

## 3. 收付款模型的可复用能力与限制

### 3.1 已有能力

`payments` 已采用“先资金、后核销”模型：

```text
amount = 银行实收/实付
unallocated_amount = amount − Σ(allocated_amount + discount_amount)
```

`PaymentType.RECEIPT` 的现有银行凭证是：

```text
借：公司银行 GL
贷：伙伴 GL
```

若伙伴是供应商且伙伴 GL 为应付账款，该方向正好可以结清应付贷项形成的借方供应商余额。因此以下能力可以复用：

- 收付款头档、银行账户和外部流水号；
- DRAFT / 审批 / 过账 / VOID 工作流；
- `amount` / `unallocated_amount`；
- 先过账资金、后追加核销行；
- 银行凭证与按行调整凭证；
- 一张资金单据多行核销。

### 3.2 当前硬编码

现有实现把资金方向与子账类型固定绑定：

```text
RECEIPT      → CUSTOMER → AR Invoice
DISBURSEMENT → SUPPLIER → AP Invoice
```

具体限制：

- `PaymentAllocationValidator.resolveInvoice`：RECEIPT 只接受 `ar_invoice_id`，DISBURSEMENT 只接受 `ap_invoice_id`。
- `PaymentPostingServiceImpl`：RECEIPT 一律记 `JournalSourceModule.AR`，DISBURSEMENT 一律记 `AP`。
- 前端 `PaymentForm`：RECEIPT 自动固定 `partnerType=CUSTOMER`，DISBURSEMENT 固定 `SUPPLIER`。
- `PaymentAllocationType` 只有 `INVOICE` / `GL_ACCOUNT` / `PREPAYMENT`。
- `payment_lines` 没有应付贷项引用。
- 现有 Payment 创建与过账没有完整复核内部银行账户的公司、币别、启用状态及 GL 归属。

所以不能只在页面上开放“收款选择供应商”；必须同时增加业务用途、子账归属和贷项核销规则。

## 4. 为什么真实退款不能用付款 VOID

付款 VOID 表示原付款错误、被撤销或银行交易没有成立。它会：

1. 冲销原付款银行凭证；
2. 回减 AP `paid_amount`；
3. 恢复原票 `remaining_amount`。

供应商后来实际退回一笔现金，是一笔新的银行流入，原付款仍真实发生，必须保留审计轨迹。

示例：

```text
AP 发票：100
原付款：借 AP 100 / 贷银行 100
应付贷项：借 AP 40 / 贷 GR/IR、费用及税 40
供应商退款：借银行 40 / 贷 AP 40
```

最终采购净额与净现金流均为 60，原付款 100 和后来退款 40 都能与银行流水一一对应。

若用 VOID 原付款再重建净额付款：

- 系统会出现并不存在的银行冲销和新付款；
- 原始 100 的银行流水无法与业务单据保持一致；
- 退款到账流水没有独立来源单据；
- 审计和银行对账失真。

结论：真实退款必须是新 `RECEIPT`；VOID 只用于纠正原付款本身。

## 5. 部分已付场景要求拆分贷项

示例：

```text
AP 总额 100
已付 60
未付 remaining 40
应付贷项 70
```

贷项 70 应拆成：

```text
applied_amount       = 40  // 直接冲完原票未付
refundable_amount    = 30  // 已付款部分形成供应商应退
refund_remaining_amount = 30
```

应付贷项凭证仍按完整 70 过账；拆分只是 AP 子账核销语义，不额外产生总账凭证。

若贷项只有 30：

```text
applied_amount       = 30
refundable_amount    = 0
原票 remaining       = 10
```

现有未付贷项流程应保持不变。

## 6. 外币缺口

贷项汇率冻结为原 AP 汇率，供应商退款发生在后来，应按退款日汇率记录银行资金。

例如同币金额 40：

```text
贷项历史本位币金额 = 40 × creditMemo.exchange_rate
退款本位币金额     = 40 × payment.exchange_rate
汇兑差额           = 退款本位币金额 − 贷项历史本位币金额
```

现有普通收付款核销没有自动已实现汇兑损益。本专题需要新增可复用计算与凭证组件，但本期只接供应商退款，避免把普通 AP/AR 收付款改造混入同一交付。

这意味着退款段可以正确核算“贷项历史汇率 vs 退款日汇率”，但不能修复原 AP 发票与原付款之间已经存在的本位币残余。**普通 AP 付款汇兑正确落地必须作为启用外币供应商退款的上线前置**；未满足前置时只允许本位币退款。

---

## 7. 原付款折扣边界

现有 AP `paid_amount` 会把：

```text
allocated_amount + discount_amount
```

一起视为已结清金额，但供应商实际收到的现金不包含付款折扣。若直接按 `paid_amount` 判断可退款金额，会把折扣误当成供应商应退现金。

同时，现有 Payment 对 `amount / unallocated / discount` 的现金语义需要独立整顿，不适合夹带在退款交付中处理。

本期规则：

```text
若贷项 POST 计算出 refundable_amount > 0
且原 AP 存在有效 payment_line.discount_amount > 0
→ 拒绝过账
```

这里“有效”指 `payments.status=POSTED`、`payment_type=DISBURSEMENT`、该行 `allocation_status=APPLIED` 且 `ap_invoice_id` 指向原 AP。

只冲原票未付部分、`refundable_amount = 0` 的贷项不受此限制。付款折扣比例转回作为后续独立设计。

---

## 8. 并发与锁风险

应付贷项过账会悲观锁：

- `ap_credit_memos`；
- 原 `ap_invoices`；
- 原 AP 行；
- 涉及的收货行。

但现有付款核销 `PaymentInvoiceClearingSupport.applyAp` / `restoreAp` 使用普通 `findById`，`ApInvoice` 也没有 `@Version`。付款核销与贷项过账并发时，存在 `paid_amount`、`credited_amount`、`remaining_amount` 互相覆盖的风险。

供应商退款还会增加“多张收款同时核销同一贷项”的竞争，因此新设计必须统一锁顺序：

```text
Payment → ApCreditMemo（按 id 升序）→ 原 ApInvoice
```

并在过账、追加核销、反向核销、VOID 时重算开放金额。

---

## 9. 测试基线

当前 FI 测试没有覆盖：

- `ApCreditMemoPostingServiceImpl` 过账/VOID；
- `PaymentPostingServiceImpl`；
- `PaymentInvoiceClearingSupport`；
- 付款与贷项并发；
- 贷项与退款的下游作废顺序。

退款会修改 AP remaining 的核心语义。实现前必须先把现有未付贷项场景固化为回归测试，再增加退款与并发测试。

---

## 10. 设计结论

供应商退款适合复用现有 `payments` 资金框架，但不能直接复用现有“RECEIPT 只核 AR 发票”的核销逻辑。

目标方案：

1. 应付贷项成为带退款开放金额的 AP 子账单据；
2. 原 AP 保留“贷项总额”和“已应用贷项金额”两种语义；
3. `payments` 增加 `SUPPLIER_REFUND` 用途；
4. 供应商退款以 `RECEIPT + SUPPLIER` 过账；
5. 退款行核销 `ap_credit_memos`，不修改原付款 `paid_amount`；
6. 逐行处理历史汇率与退款日汇率的已实现汇兑损益；
7. 退款不触碰库存、采购退货或收货开票占用。
