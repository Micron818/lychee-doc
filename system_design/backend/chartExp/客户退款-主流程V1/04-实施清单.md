## 1. 审查结论

| 问题 | 主流程 V1 |
|------|-----------|
| 真实退款是否 VOID 原收款 | **否** |
| 新表 `customer_refunds` | **否**；复用 `payments` |
| 业务组合 | `DISBURSEMENT + CUSTOMER + CUSTOMER_REFUND` |
| 核销对象 | 贷项 `refund_remaining` |

| 一单核多张贷项 | **否** |

| 普通 AP/AR 汇兑 | **不改** |
| 原票折扣 | 待退款 ≤ 剩余实收现金 |
| 核销/冲销换日 | **否** |

## 2. 已锁定决策

1. 名称：**客户退款 / `CUSTOMER_REFUND`**。
2. 只覆盖数量型退货贷项的现金退款。
3. 贷项仍一对一原 AR。退款一对一贷项；一贷项可被多张退款分次退。
4. 退款不改原 AR `received_amount` 与原收款。
5. 过账必须恰好一行 `AR_CREDIT_MEMO` 且 `allocated = amount`。
6. 退款 Journal 模块 `AR`。
7. 有有效退款则禁止 VOID 贷项。
8. 有 `refundable > 0` 则禁止撤原收款。
9. 锁序：Payment → CreditMemo → 原 AR。
10. `AR_CREDIT_MEMO` 禁止走进 `applyAr`。

---

## 3. 实现约定

扩展 `PaymentPurposeSupport`：增加 `isCustomerRefund`、`documentType`、`assertCombination` 第四条合法组合。未识别 purpose 必须抛错。

核销应用抽与供应商退款对称的 `applyArCreditMemo` / `restoreArCreditMemo`，不要复制粘贴后改漏方向。

银行校验仅 `CUSTOMER_REFUND` 强制（对标 `SUPPLIER_REFUND`）。

## 5. 提交顺序

1. Liquibase + 枚举 + 单号
2. 用途矩阵与草稿行校验
3. POST：银行凭证 + 回写贷项 + 汇兑
4. VOID + 贷项/原收款闸
5. 可退款查询 + 前端
6. 文档对齐

3–4 必须同一交付。

## 6. 验收

1. AR 100 已收 100，贷项 40 → `refundable=40`。退款 40 过账：银行贷 40、借 AR 40；贷项 `REFUNDED`；原 AR 仍 `received=100`、原收款仍 `POSTED`。
2. AR 100 已收 60，贷项 70 → `applied=40`、`refundable=30`。退款只能退 30；可先 20 再 10。
3. 贷项 `refundable=0`：无退款入口。
4. 过账必须恰好一行且 `allocated = amount`；交叉货币拒绝。
5. 两张退款抢同一贷项余额：一方成功，另一方失败。
6. VOID 退款后贷项 `refund_remaining` 恢复，可再退。
7. 有有效退款时 VOID 贷项失败；VOID 退款后成功。
8. 有 `refundable>0` 时 VOID / 撤原收款失败。
9. 实收 98、折扣 2：贷项待退款 100 拒绝；待退款 40 通过。
10. 数量记账不影响验退款凭证（资金侧必有银行分录）。
11. STANDARD 收付款行为不变。供应商退款回归仍绿。
