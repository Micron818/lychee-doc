# 产量回馈与倒扣料优化执行计划

## 一、 背景与目标
当前系统在处理“产量回馈及倒扣料”时，存在以下问题：
1. **流程割裂**：用户需要先保存产量，再手动点击生成倒扣料明细，最后再次保存。破坏了事务一致性。
2. **批次生成逻辑错误**：倒扣料属于发料（Issue）动作，当前代码在 `calculateBackflushComponents` 中为倒扣料生成了新的批次号，而实际上应从现有库存中按 FIFO（先进先出）抓取可用批次。
3. **缺少回转（Reverse）机制**：目前 `ProductionReportService` 仅支持过账（Post），不支持回转。一旦过账发现错误，用户无法自行纠正。

**优化目标**：
实现**“同屏联动，一次保存（草稿）”**。前端输入产量后自动带出推荐的倒扣料批次（支持库存不足时的自动拆行），用户确认后一次性保存主子表为草稿，最后手动过账。同时保留接口的自动过账能力，并规划回转（Reverse）功能供用户纠错。

---

## 二、 详细执行计划

### 阶段一：WM 模块扩展（提供库存分配推荐能力）
**目标**：将 WM 模块现有的 `suggestAllocations` 能力通过 `RemoteStockOnHandService` 暴露给 PP 等其他模块，用于倒扣料的智能批次推荐。

1. **扩展公共接口 `RemoteStockOnHandService`**
   - **文件**：`lychee-erp-common/src/main/java/com/lychee/erp/common/service/RemoteStockOnHandService.java`
   - **动作**：新增方法 `List<AllocationSuggestResponse> suggestAllocations(AllocationSuggestRequest request);`
2. **实现接口 `StockOnHandServiceImpl`**
   - **文件**：`lychee-erp-wm/src/main/java/com/lychee/erp/wm/service/impl/StockOnHandServiceImpl.java`
   - **动作**：`implements RemoteStockOnHandService`，直接提供 `getTotalAvailableQuantity` 与 `suggestAllocations` 实现，供跨模块及 WM HTTP 接口调用；`StockOnHandService` 仅保留 WM 模块内部的库存查询能力。

### 阶段二：PP 模块改造（核心逻辑重构）
**目标**：重构倒扣料计算逻辑，支持主子表一次性保存。

1. **扩展 DTO 结构**
   - **文件**：`lychee-erp-pp/src/main/java/com/lychee/erp/pp/dto/request/ProductionReportRequest.java`
   - **动作**：新增字段 `private List<ProductionReportComponentRequest> components;`，用于接收前端传来的倒扣料明细。可新增 `private boolean autoPost = false;` 标志，保留自动过账的接口能力（默认不自动过账）。
2. **重构倒扣料计算逻辑 `calculateBackflushComponents`**
   - **文件**：`lychee-erp-pp/src/main/java/com/lychee/erp/pp/service/impl/ProductionReportServiceImpl.java`
   - **动作**：
     - 移除原有错误的新批次生成逻辑。
     - 根据 BOM 计算出每个组件的应扣总数。
     - 组装 `AllocationSuggestRequest`（含 `issueUnitId`），调用 `remoteStockOnHandService.suggestAllocations`，直接返回 `List<AllocationSuggestResponse>`。
     - `refId` 存放工单组件 ID，便于前端关联。
3. **重构保存逻辑 `createProductionReport` / `updateProductionReport`**
   - **文件**：`lychee-erp-pp/src/main/java/com/lychee/erp/pp/service/impl/ProductionReportServiceImpl.java`
   - **动作**：
     - 在保存主表（ProductionReport）后，检查 `request.getComponents()` 是否有值。
     - 如果有值，遍历设置 `productionReportId`，并调用 `componentRepository.saveAll()` 批量保存明细。
     - 确保整个方法在 `@Transactional` 下运行，保证主子表强事务一致性。
     - 如果 `request.isAutoPost()` 为 true，则在保存后直接调用过账逻辑（保留该能力供特定场景使用）。

### 阶段三：前端交互改造
**目标**：实现同屏联动，提升用户体验。

1. **同屏联动触发**：
   - 用户在页面上半部分输入 `goodQuantity`（良品数）和 `scrapQuantity`（报废数）。
   - 当输入框失去焦点或数值改变时，前端自动调用后端的 `calculateBackflushComponents` 接口。
2. **明细渲染与微调**：
   - 将接口返回的推荐明细直接渲染在页面下半部分的表格中。
   - 用户可以直观看到系统推荐的仓库和批次。如果发现“缺料”（批次为空），可手动干预或等待库存。
3. **一次性提交**：
   - 用户点击页面底部的“保存”按钮。
   - 前端将主表数据和表格中的明细数据组装成一个 JSON，调用 `createProductionReport`（或 update）接口，保存为**草稿（DRAFT）**状态（不触发 auto-post）。
4. **手动过账**：
   - 在列表页或详情页，用户确认草稿无误后，点击“过账”按钮，调用现有的 `postProductionReport` 完成库存扣减。

### 阶段四：实现回转（Reverse）功能
**目标**：提供已过账单据的回转能力，允许用户在发现错误时手动冲销，恢复库存与工单状态。

1. **WM 模块提供回转接口**：
   - 在 `RemoteProductionInventoryService` 中新增 `reverseFinishedGoods` 和 `reverseBackflushMaterials` 方法。
   - 底层调用 `StockOnHandInventoryService.reverseGoodsReceipt` 和 `reverseStockIssue`，实现库存的增加（冲销发料）和减少（冲销收货）。
2. **PP 模块实现回转逻辑**：
   - 在 `ProductionReportService` 中新增 `reverseProductionReport(Long id)` 方法。
   - 校验单据状态必须为 `POSTED`。
   - 调用 WM 模块的回转接口冲销库存。
   - 扣减工单（ProductionOrder）的已完工数量和报废数量，若工单状态为 `FINISHED`，则回退为 `IN_PROGRESS`。
   - 将产量回馈单（ProductionReport）状态更新为 `REVERSED`（或直接退回 `DRAFT` 视业务需求而定）。
3. **前端开放回转操作**：
   - 在已过账的产量回馈单详情页或列表页，提供“回转（Reverse）”按钮。
   - 用户点击后，调用后端的 `reverseProductionReport` 接口，完成单据冲销。

---
**执行优先级**： 阶段一 -> 阶段二 -> 阶段三 -> 阶段四。
