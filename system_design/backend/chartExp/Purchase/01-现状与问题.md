# 01. 原物料采购现状与问题（As-Is）

> 依据当前代码：`lychee-erp-pp` / `lychee-erp-scm` / `lychee-frontend`。

---

## 1. 设计初衷与实际角色

原设计把采购拆成两段：


| 单据      | 角色假设            | 实际原物料作业            |
| ------- | --------------- | ------------------ |
| PR（请购）  | 需求部门提出，采购执行前需审核 | 采购员自己从 MRP 转出、自己审核 |
| PO（采购单） | 采购员对供应商下单       | 同一人再建 PO 主档并汇入 PR  |


FO 确认 + MRP 净算已经表达「要买什么、何时要、买多少」。对原物料，PR 没有再确认需求的业务含义，只增加作业切换。

手工请购（`source_type = MANUAL`）仍需要 PR：无 FO/MRP 的耗材、备件、临时采购。

---

## 2. 现行主流程

```text
Factory Order (CONFIRMED / IN_PROGRESS)
        │
        ▼
   MRP Run（再生式净算）
        │
        ▼
   MrpResult  suggested_action_type = PURCHASE
        │  采购员在 MRP 结果勾选「转采购申请」
        ▼
   Purchase Requisition（按工厂一张 DRAFT 主档）
        │  切换到 PR 作业 → 打开单据 → 审核（仅改状态）
        ▼
   PR APPROVED
        │  切换到 PO 作业
        ▼
   先新增 PO 主档（必须先选供应商）
        │
        ▼
   打开 PO →「汇入 PR 明细」→ 草稿 PO 明细
        │
        ▼
   补单价 / 交期 → 审核 PO → GR → AP
```

生产侧对照（已一键转单）：

```text
MrpResult PRODUCTION → PlannedOrder →「转工单」一次生成 MO
```

采购侧没有对等的「选建议 → 生成执行单」。

## 3. 各步骤在代码中的行为



### 3.1 MRP 转 PR — `MrpConversionServiceImpl.convertToPurchaseRequisitions`

- 仅 `suggestedActionType = PURCHASE` 且 `isConverted = false`
- 已有 `MRP_RESULT → PURCHASE_REQUISITION` pegging 则跳过
- 经 `RemotePurchaseRequisitionService.createFromMrpResults` 建单
- Pegging：`demand = MRP_RESULT`，`supply = PURCHASE_REQUISITION`（**PR 明细 id**）
- `MrpResult.isConverted = true`（按建议行全量转出，**无部分转**；布尔在 As-Is 够用，To-Be 部分转后不够，见 `03-schema设计.md` §5）



### 3.2 建 PR — `RemotePurchaseRequisitionServiceImpl.createFromMrpResults`

- **仅按** `factoryId` **分组**，一批转换、同一工厂 = 一张 PR 主档
- `sourceType = MRP`，`status = DRAFT`，写 `mrpRunId`
- 明细：数量/需求日/最晚下单日来自 MrpResult；单位取物料采购单位（否则基本单位）
- `suggested_supplier_id` **有栏位，转换从不写入**
- MRP 来源的 PR 禁止改主档、禁止增删改明细



### 3.3 审核 PR — `PurchaseRequisitionServiceImpl.approvePurchaseRequisitionBulk`

- `DRAFT → APPROVED`，明细同步
- 无签核流、无预算、无「请购人 ≠ 审批人」校验
- PO 汇入只接受主档 `APPROVED` / `PARTIAL` 且未订满的明细（`getPendingPurchaseRequisitionItems`）



### 3.4 建 PO 再汇入 — `PurchaseOrderGenerationServiceImpl.createPurchaseOrderItemsFromPr`

- PO 必须已存在且 `DRAFT`；`purchase_orders.supplier_id` **NOT NULL**
- 校验：PR 与 PO 工厂一致；转换量 ≤ 未订量
- 单价写死 `0`；写 pegging `PURCHASE_REQUISITION → PURCHASE_ORDER`；回写 PR `orderedQuantity`

前端：`purchase-orders` 新增主档 → 明细 `ImportPRModal` 拉 pending PR。

### 3.5 下次 MRP 对未固化 PR 的清理

`MrpCalculationEngine.cleanupPreviousRunArtifacts`：

- 删除该厂 `source_type = MRP` 且仍为 `DRAFT` 的 PR
- 对应 MrpResult 一并删除（未转或仅转到未确认 PLO 的建议同样清理）

含义：MRP 转出的 DRAFT PR 是**可被下一轮运算抹掉的缓冲**，不是稳定需求单据。已审核 PR 会作为预计入库参与净算（`findOpenPurchaseRequisitions`）。

## 4. 作业摩擦（采购员视角）

同一人完成原物料采购时，最少经过：

1. MRP 结果作业：转 PR
2. PR 作业：打开 + 审核（不能改内容）
3. PO 作业：先想好供应商、建空主档
4. 同一张 PO：再打开汇入窗勾 PR 行

其中 2 不产生业务决策；3 与 4 的顺序与「先看要买什么、再决定卖给谁」相反。

分组粒度也不匹配：


| 单据       | 实际分组键                            |
| -------- | -------------------------------- |
| MRP → PR | 仅 `factoryId`                    |
| PO       | `factoryId` + `supplierId`（对外合约） |


一张 MRP PR 往往要拆成多张 PO，采购员必须在汇入时手工挑选同行供应商的行。

---



## 5. 主数据缺口


| 缺口                             | 影响                   |
| ------------------------------ | -------------------- |
| 无物料–供应商来源清单                    | 无法预填供应商、无法按供应商预拆 PO  |
| `materials` 无默认供应商             | 不能塞进物料主档（同料不同厂、多供应商） |
| `material_factories` 只管仓/倒扣/公差 | 采购来源不应混入该表           |
| PO 汇入单价恒为 0                    | 无末次采购价可带             |


没有来源清单时，即使跳过 PR，采购员仍要逐行指定供应商。简化作业的前提是：**默认供应商可维护，转单时可改。**

---



## 6. 溯源现状

统一模型：

```text
FO item  ←pegging→  MrpResult  ←pegging→  PR item  ←pegging→  PO item
```

`PeggingOrderType` 已含 `PURCHASE_REQUISITION` / `PURCHASE_ORDER`。改造后 MRP 路径改为 `MrpResult → PO item` 即可，不必补直连外键。

---



## 7. 保留与淘汰的边界


| 能力                               | 结论                    |
| -------------------------------- | --------------------- |
| 手工 PR（MANUAL）CRUD、审核、汇入 PO       | **保留**                |
| MRP 结果「转采购申请」作为采购员日常路径           | **淘汰**（见 02）          |
| PR 审核作为原物料需求确认                   | **淘汰**（控制点改到 PO 审核）   |
| `createPurchaseOrderItemsFromPr` | **保留**（仅服务 MANUAL PR） |
| `order_peggings`                 | **保留并作为唯一溯源**         |
