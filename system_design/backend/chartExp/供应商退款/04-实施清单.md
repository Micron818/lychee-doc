> **完整目标清单，本期不要按本文施工。** 开发入口：[../供应商退款-主流程V1/04-实施清单.md](../供应商退款-主流程V1/04-实施清单.md)。

> 必须一次交付“贷项开放金额 + 供应商退款资金 + 核销 + 汇兑 + VOID”；禁止只放开已付贷项而没有退款闭环。

## 1. 审查结论

| 问题 | 结论 |
|------|------|
| 真实供应商退款是否用原付款 VOID | **否**；原付款保留，退款是新银行流入 |
| 是否新增 `supplier_refunds` 表 | **否**；复用 `payments` |
| 退款业务组合 | `RECEIPT + SUPPLIER + SUPPLIER_REFUND` |
| 退款核销对象 | 应付贷项待退款开放金额 |
| 贷项能否超过原票未付 remaining | **可以**，但不得超过原票尚未贷回总额与可贷数量 |
| 超过 remaining 的部分 | 冻结为 `refundable_amount` |
| 资金能否先到账 | **可以**；先成为未分配供应商退款 |
| 一张退款能否核多张贷项 | **可以**；公司、供应商、币别一致 |
| 外币 | 退款日汇率；逐贷项行计算已实现汇兑损益 |
| 普通 AP/AR 汇兑 | 本期不改；只抽可复用组件。外币退款启用以前置完成为准 |
| 库存与收货占用 | 退款不触碰；仍由贷项和采购退货负责 |

## 2. 已锁定决策

1. 正式名称：**供应商退款 / `SUPPLIER_REFUND`**。
2. 本期只覆盖“已付 AP 的数量型退货贷项现金退款”。
3. 不覆盖供应商预付款退回、贷项冲未来 AP、客户退款。
4. 应付贷项仍一对一原 AP；退款 Payment 可以多行核销多张贷项。
5. `credited_amount` 保持贷项总额，新增 `applied_credit_amount` 参与原票 remaining。
6. 贷项 POST 时冻结 `applied_amount` 与 `refundable_amount`。
7. `applied = min(memo.total, invoice.remainingBefore)`。
8. `refundable = memo.total - applied`。
9. `refundRemaining = refundable - refunded`。
10. 退款核销不修改原 AP `paid_amount`，也不修改原付款。
11. 资金先行：供应商退款 Payment 可无线过账，保留 `unallocated_amount`。
12. `payment_purpose` 必须显式存储，不从付款方向临时推导。
13. `SUPPLIER_REFUND` 固定 `RECEIPT + SUPPLIER`，Journal 模块归 `AP`。
14. 退款日汇率冻结在 Payment；贷项历史汇率冻结在贷项。
15. 汇兑差额按每条退款核销行计算并生成 local-only 调整凭证。
16. 汇兑组件可复用，但普通 AP/AR 本期不接入。
17. 有有效退款核销时禁止 VOID 贷项。
18. 有 `refundable_amount > 0` 的贷项时，禁止撤销会改变拆分依据的原付款核销。
19. 完整撤销按“退款 → 退货 → 贷项 → 原付款”。
20. 本期沿用 Payment 权限与页面，不新增第二套退款主档。
21. 资金后补核销增加 `clearing_date`，汇兑凭证按核销日过账，不回开退款到账期间。
22. 核销行使用 `PROPOSED / APPLIED / REVERSED`，反向核销保留审计，不物理删除已应用行。
23. 反向核销和退款 Payment VOID 由用户填写开放期间 `reversal_date`。
24. 原 AP 存在有效付款折扣且将形成 `refundable_amount` 时拒绝；本期不做折扣比例转回。
25. 普通 AP 付款汇兑正确落地是启用外币供应商退款的前置；本期代码只处理退款段汇兑。

## 3. 核心公式

### 3.1 原 AP

```text
credited       = Σ(POSTED、非 VOIDED 贷项 total)
appliedCredit  = Σ(POSTED、非 VOIDED 贷项 applied)
remaining      = total − paid − appliedCredit
```

严禁继续使用：

```text
remaining = total − paid − credited
```

### 3.2 贷项

```text
grossCreditAvailable = invoice.total − invoice.credited
applied               = min(memo.total, invoice.remainingBefore)
refundable            = memo.total − applied
refundRemaining       = refundable − refunded

memoTotalBase          = round(memo.total × memo.exchangeRate, 2)
appliedBase            = 结清原票时取 apRemainingBase；
                         否则 min(round(applied × rate, 2), apRemainingBase)
refundableBase         = memoTotalBase − appliedBase
```

外币 `apRemainingBase` 必须来自普通 AP 付款汇兑前置能力维护的实际开放本位币，不得用交易币余额简单重乘。

### 3.3 退款 Payment

```text
DRAFT / PENDING_APPROVAL / APPROVED:
  unallocated = payment.amount − Σ(PROPOSED counted allocation)
POSTED:
  unallocated = payment.amount − Σ(APPLIED counted allocation)
VOIDED:
  不参与开放金额计算
```

### 3.4 汇兑

```text
sourceCandidate      = round(allocated × memo.exchangeRate, 2)
settlementCandidate  = round(allocated × payment.exchangeRate, 2)
sourceBase / settlementBase 按剩余上限分摊
fxDifference         = settlementBase − sourceBase
```

本位币金额均为 2 位小数。

分次退款使用“候选值 + 剩余上限”：

```text
sourceRemainingBase =
    memo.refundableBaseAmount
    − Σ(该贷项有效行与本事务较早行 sourceBase)
sourceBase =
    min(round(allocated × memo.exchangeRate, 2), sourceRemainingBase)

settlementRemainingBase =
    round(payment.amount × payment.exchangeRate, 2)
    − Σ(该 Payment 有效行与本事务较早行 settlementBase)
settlementBase =
    min(round(allocated × payment.exchangeRate, 2), settlementRemainingBase)
```

结清贷项或用完 Payment 时直接取对应 remaining base。所有分摊必须非负；批量 POST 按 `lineNo / id` 稳定排序并维护事务内合计，不能只查数据库中“Payment 已 POSTED”的有效行。

### 5.2 AP remaining

修改 `ApInvoiceRemainingSupport`：

```text
remaining = total − paid − appliedCredit
```

检查所有调用点：

- `ApInvoicePostingServiceImpl`
- `ApInvoiceServiceImpl.recalculateInvoiceTotals`
- `PaymentInvoiceClearingSupport.applyAp / restoreAp`
- `ApCreditMemoPostingServiceImpl`
- AP VOID / 付款 VOID

迁移后不得残留 `total − paid − credited`。

### 5.3 贷项过账

修改 `ApCreditMemoPostingServiceImpl`：

1. 保留可贷数量与成卡校验。
2. 删除 `memo.total ≤ original.remaining`。
3. 新增 `memo.total ≤ original.total − original.creditedAmount`。
4. 锁内计算 `applied / refundable`。
5. 禁止读取 Journal 反推：本位币用 remaining；外币从普通 AP 付款汇兑前置能力取得原 AP 实际未结本位币金额。结清原票时 `appliedBase` 取完整 AP 开放金额，部分应用时取 `min(round(applied×rate), apRemainingBase)`；`refundableBase = round(memo.total×rate) − appliedBase`。
6. 若 `refundable > 0`，查询原 AP 有效付款行；任一 `discountAmount > 0` 则拒绝。
7. `credited += memo.total`。
8. `appliedCredit += memo.applied`。
9. 用新公式重算 remaining / paymentStatus。
10. 完整 memo total 继续写凭证与回减收货占用。

`refundStatus`：

- `refundable=0` → `NOT_REQUIRED`
- 否则 → `UNREFUNDED`

有效付款折扣定义：

```text
Payment.status = POSTED
AND Payment.paymentType = DISBURSEMENT
AND PaymentLine.apInvoiceId = originalApInvoice.id
AND PaymentLine.allocationType = INVOICE
AND PaymentLine.allocationStatus = APPLIED
AND PaymentLine.discountAmount > 0
```

### 5.4 贷项 VOID

在既有采购退货闸之前或同一校验阶段增加：

```text
Payment.status = POSTED
AND paymentPurpose = SUPPLIER_REFUND
AND allocationType = AP_CREDIT_MEMO
AND allocationStatus = APPLIED
→ 拒绝
```

通过后：

```text
credited       -= memo.total
appliedCredit  -= memo.applied
```

再沿用凭证冲销、占用回加和 AP remaining 重算。

### 5.5 Payment 用途校验

`PaymentServiceImpl` 创建/更新时：

- 从 `BusinessPartner.partnerType` 回填并校验请求 partnerType，禁止伪造；
- 校验 `paymentPurpose + paymentType + partnerType` 组合；
- `SUPPLIER_REFUND` 强制 `isPrepayment=false`；
- `paymentPurpose` 建单后不可修改；
- 校验内部银行账户同公司、同币别、有效，且银行 GL 属于该公司；对方银行账户若填写，须属于同一供应商且有效；
- `SUPPLIER_REFUND` 使用 `DocumentTypeEnum.SUPPLIER_REFUND`；
- 默认 `paymentPurpose=STANDARD` 兼容历史 API。

前端隐藏不是安全边界，后端必须拒绝无效组合。

### 5.6 Payment 过账

修改 `PaymentPostingServiceImpl`：

```text
STANDARD RECEIPT         → JournalSourceModule.AR
STANDARD DISBURSEMENT    → JournalSourceModule.AP
SUPPLIER_REFUND RECEIPT  → JournalSourceModule.AP
```

供应商退款：

```text
sourceDocType = SUPPLIER_REFUND
借银行 / 贷供应商 AP
```

过账无线仍允许；有拟核销行时一次预锁全部目标贷项，按全部 PROPOSED 行聚合校验，应用后转为 APPLIED。此内部路径不能套用“表头必须已 POSTED”的外部 API 校验，也不能按已经预扣的 `unallocated` 再逐行扣一次；最终余额须显式按目标状态 APPLIED 重算，不能依赖动作处理器中暂时仍为 APPROVED 的表头状态。

### 5.7 退款核销

建议新增：

```text
SupplierRefundAllocationSupport
PaymentSettlementFxSupport
```

由 `PaymentInvoiceClearingSupport` 按 allocation type 分派，避免继续扩大单一类中的 AR/AP/预付款/退款条件分支。

必须修改 `PaymentAllocationValidator`：

- `SUPPLIER_REFUND` 只接受 `AP_CREDIT_MEMO`；
- 拒绝 INVOICE / GL_ACCOUNT / PREPAYMENT；
- 拒绝 `isPrepayment=true`；
- 校验目标互斥、重复行、金额与日期。

必须修改 `PaymentInvoiceClearingSupport.applyLine / restoreLine`：

- `AP_CREDIT_MEMO` 只分派到 `SupplierRefundAllocationSupport`；
- 禁止误走 `applyAp / applyAr`，不得修改 AP `paidAmount`；
- 禁止误走现有折扣 / GL_ACCOUNT 调整凭证；
- restore 按核销行原始快照反向，不重新计算历史汇差。

`SupplierRefundAllocationSupport` 负责：

- 锁 Payment、贷项与原 AP；
- 校验用途、状态、公司、供应商、币别；
- 校验 `clearingDate` 不早于 Payment 日期、贷项日期、该 Payment 与贷项历史最大 reversalDate，且期间开放；
- 校验 Payment 未分配余额和贷项待退款余额；
- 更新 `refunded / refundRemaining / refundStatus`；
- `PROPOSED → APPLIED → REVERSED`；
- 应用/反向退款行并保留审计；
- 拒绝超额与重复核销。

`PaymentSettlementFxSupport` 负责：

- 计算并写入核销行汇兑快照；
- 按稳定顺序处理有界剩余本位币分摊，保证非负并吸收双侧尾差；
- 用 `AccountDeterminationService.resolve(EXCHANGE_DIFF)` 取得科目；
- 以 `clearingDate` 生成 local-only AP / 汇兑损益凭证；
- 反向核销时按用户输入的开放期间 `reversalDate` 冲销。

仅当 `exchangeDifferenceAmount != 0` 时要求 `EXCHANGE_DIFF`；缺少科目应拒绝核销，不建议将真实汇兑损益静默落到 `PRICE_VAR`。汇差为 0 时不解析该科目。

发布控制：普通 AP 付款汇兑未正确落地时，外币供应商退款入口必须关闭或后端拒绝；本位币退款可独立启用。

`JournalPostingService` 增加按指定开放期间冲销的能力：

```text
reverseEntry(entryId, reversalDate, reason)
```

新冲销凭证按 `reversalDate` POSTED，原凭证保留原日期并写 reversal 关联。退款行汇兑凭证与退款银行凭证必须在同一事务使用同一冲销日。

新增带日期重载，保留现有 `reverseEntry(entryId, reason)`；本期只有 SUPPLIER_REFUND 强制开放期间冲销日，STANDARD Payment 行为不扩大。

日期下限：

```text
单行 reverse ≥ line.clearingDate
Payment VOID ≥ paymentDate、全部 line.clearingDate、既有 REVERSED line.reversalDate
```

开放期间冲销只扩展退款核销与退款 Payment。后续采购退货和贷项自身若处于关闭期间，仍按各自现网规则处理，可能需要重开期间。

### 5.8 原付款撤销闸

在以下入口增加下游检查：

- `PaymentAllocationServiceImpl.removeAllocation`
- `PaymentPostingServiceImpl.reversePostedPayment`

当被恢复的 AP 存在非 VOIDED 且 `refundableAmount > 0` 的贷项时拒绝。

检查应基于 Payment 行引用的 AP id 集合批量查询，不能逐行 N+1。

`removeAllocation` 对 `SUPPLIER_REFUND + AP_CREDIT_MEMO + APPLIED` 直接拒绝，必须走 reverse API；STANDARD Payment 保留现有恢复后物理删除行为。

## 8. 实施顺序

1. 先补现有贷项、付款 remaining、Payment 拟核销/已核销状态与并发回归测试。
2. Liquibase、实体、枚举、DTO 与历史回填。
3. 切换 `applied_credit_amount` remaining 公式，确保 V1 行为不变。
4. 贷项 POST 拆分 `applied / refundable`，完成 VOID 回滚。
5. Payment purpose、供应商 RECEIPT 过账与后端组合校验。
6. 退款核销、核销行生命周期、开放金额与 VOID 恢复。
7. clearing/reversal 日期、汇兑组件、逐行凭证与双侧尾差。
8. 原付款撤销闸与全链路锁。
9. 前端、API、locale。
10. 文档和 schema_tables 切换为已落地口径。

步骤 3–8 必须同一可发布交付，禁止出现：

- 已付贷项可以过账但没有退款核销；
- 退款可以过账但贷项开放金额不回写；
- 汇兑凭证生成但 VOID 不冲销；
- 前端限制存在而后端没有硬校验。

## 9. 验收

### 9.1 基础金额

1. AP 100 已付 100，贷项 40：`applied=0`、`refundable=40`、原 AP remaining=0。
2. AP 100 已付 60，贷项 70：`applied=40`、`refundable=30`。
3. AP 100 已付 20，贷项 30：`applied=30`、`refundable=0`、remaining=50；外币 appliedBase 使用 AP 实际开放本位币而非简单重乘，V1 交易币行为不变。
4. 累计贷项总额超过原 AP total：拒绝。
5. 贷项数量超过可贷数量：拒绝。
6. AP 全额已付但仍有可贷数量：后端可生成贷项，前端入口可见。
7. 原 AP 存在有效付款折扣，且贷项将形成 refundable：拒绝；纯 applied 贷项仍允许。

### 9.2 资金先行与核销

8. 供应商退款 40 无行过账：借银行/贷 AP 40，`unallocated=40`。
9. 后续核销贷项 30：贷项 refunded=30，Payment unallocated=10。
10. 一张 Payment 核销同供应商两张贷项成功。
11. 跨公司、跨供应商、跨币别核销均拒绝。
12. 超过 Payment unallocated 或贷项 refundRemaining 均拒绝。
13. 同 Payment 重复选择同一贷项拒绝。
14. STANDARD Payment 不能使用 AP_CREDIT_MEMO 行。
15. SUPPLIER_REFUND + `isPrepayment=true` 拒绝。
16. DRAFT `/items` 建立 PROPOSED 行不回写贷项；POST 后一次转 APPLIED 且不重复扣 unallocated。
17. POSTED 后反向原行再新增同贷项核销成功；REVERSED 行不参与任何合计，新 clearingDate 不得早于该 Payment 或贷项历史 reversalDate。
18. 银行账户跨公司、跨币别、无效或 GL 归属错误均拒绝。

### 9.3 汇兑

19. 退款日汇率等于贷项汇率：无汇兑凭证。
20. 退款日汇率较高：local-only 借 AP / 贷汇兑收益。
21. 退款日汇率较低：local-only 借汇兑损失 / 贷 AP。
22. 一张退款核销不同历史汇率的多张贷项：逐行汇差正确。
23. 分次退款含极小金额与反向后重分配：每行 sourceBase 非负，全部结清时累计值等于贷项可退款历史本位币金额。
24. 一张 Payment 分配多张贷项并批量 POST：按事务工作合计计算，每行 settlementBase 非负，全部分配时累计值等于银行凭证本位币金额。
25. 后补核销使用开放的 clearingDate；退款原期间已关闭不影响，clearingDate 期间关闭则拒绝。
26. 普通 AP 付款汇兑前置未启用时，本位币退款允许、外币退款拒绝。
27. 非零汇差缺少 `EXCHANGE_DIFF` 时核销整体回滚；零汇差不要求该科目。

### 9.4 VOID 与依赖

28. 反向退款核销：行转 REVERSED、恢复贷项 refundRemaining，按 reversalDate 冲汇兑凭证。
29. VOID 退款 Payment：恢复全部贷项、行转 REVERSED，按 reversalDate 冲汇兑和银行凭证。
30. 原 clearing/payment 期间已关但 reversalDate 开放：反向/VOID 成功；reversalDate 已关、早于 clearingDate 或早于既有行 reversalDate 均拒绝。
31. 有有效退款核销时 VOID 贷项：拒绝。
32. 先 VOID 退款后、无 POSTED 采购退货且贷项期间满足现网规则：贷项 VOID 成功；上游关闭期间不由退款 reversalDate 绕过。
33. 同时有退款与采购退货：必须按退款 → 退货 → 贷项顺序。
34. 贷项 `refundable>0` 时撤销原付款核销：拒绝。
35. 贷项 `refundable=0` 时撤销后置付款：按新 remaining 公式正确恢复。

### 9.5 并发与回归

36. 两张退款 Payment 并发消费同一贷项最后余额：一笔成功，一笔失败，无超退。
37. 付款与贷项并发更新同一 AP：锁生效，无 paid/credited/applied/remaining 丢更新。
38. 贷项 POST 与原付款 VOID 并发：只能形成一种合法结果。
39. 现有普通 RECEIPT→AR、DISBURSEMENT→AP 账务结果与 DELETE 行为不变；POST/VOID 正确写新增 allocationStatus，STANDARD reversalDate 可空。
40. 现有已过账贷项迁移后 `applied=total`、`refundable=0`、`appliedBase=round(total×rate)`，账面 remaining 不变。

## 10. 权限

沿用：

| 动作 | 权限 |
|------|------|
| 查看退款及可退款贷项 | `/fi/payments:read` + `/fi/ap-credit-memos:read` |
| 建立供应商退款 | `/fi/payments:create` |
| 修改草稿、工作流与核销 | `/fi/payments:update` |
| 删除草稿 | `/fi/payments:delete` |

退款核销查询同时校验 Payment read/update 与贷项 read，不因复用 API 绕过现有权限。

## 11. 明确不做

- 独立供应商退款表；
- 负金额 Payment；
- 付款 VOID 模拟真实退款；
- 供应商预付款退回；
- 贷项冲未来 AP；
- 客户退款；
- 普通 AP/AR 已实现汇兑损益改造；
- 普通 AP 付款汇兑完成前启用外币供应商退款；
- 原 AP 付款折扣的比例转回；
- 纯金额或改单价折让贷项；
- 通用供应商开放项互抵与净额账龄；
- 退款折扣、容差与坏账；
- 银行对账导入；
- 退款自动生成采购退货或再次修改 `invoiced_quantity`。
