# 規範 ERP 的固定資產建立方式，與現有實作的對照

## 一、主流 ERP 的標準做法

規範 ERP（SAP、Oracle、Dynamics）建立固定資產大致有三條路徑：

**路徑 1：直接資本化（貨到票到即轉固）**
AP 發票過帳時直接指定資產卡片（SAP 是 posting key 70 + 交易類型 100，或 PO 用帳戶指派類別 A），分錄一步到位：借固定資產、貸應付帳款。前提是資產主檔（卡片）先建好。

**路徑 2：經過渡科目，事後成卡（最常見）**
- **Oracle 的 Mass Additions**：AP 發票行記到「資產清理科目（Asset Clearing）」，過帳後由 *Create Mass Additions* 程序把發票行推送到 FA 工作台，會計人員在 FA 端審核（Prepare）——指定資產類別、拆分（split）、合併（merge）、指派部門——確認後生成卡片並過帳：借固定資產、貸 Asset Clearing。
- **SAP 的 AuC（在建工程）結算**：先記到 Asset under Construction，完工後用 AIAB/AIBU 結算轉到最終資產。

**路徑 3：手工建卡 + 手工取得過帳**：零星情況用，不經 AP 整合。

實務上路徑 2 是主流，因為採購入帳（AP 會計）和資產成卡（資產會計）通常是兩個人、兩個時點的作業，中間需要一個過渡科目做勾稽。

## 二、現有系統的實作對照

`createFromApInvoiceLines` 的流程是：AP 發票行過帳到 CIP 科目 → 使用者透過來源接口選擇已過帳的 CIP 行 + 指定資產類別 → 每行按 `quantity` 拆成 N 張卡（尾差歸最後一張）→ 可選 `autoCapitalize` 立即轉固（借固定資產、貸 CIP）。

來源接口（降低前端關聯）：
- `GET /api/v1/fi/ap-invoices/{id}/fa-source`
- `GET /api/v1/fi/ap-invoices/fa-eligible-lines?companyId=`

這**基本上就是 Oracle Mass Additions / SAP AuC 結算的模式**，符合實務。做對的關鍵點：

- **AP 不直接借最終固定資產科目**，經 CIP 過渡，避免與 FA 資本化重複入帳（`assertCipLine` 強制驗證行科目必須是 CIP 判定出的科目）。
- **防重複**：`existsByApInvoiceLineId` 防止同一發票行重複成卡，等同於 Mass Additions 的行狀態管控。
- **一行拆多卡**（quantity → split_no），對應 Oracle 的 split 功能；尾差分配也是標準做法。
- **原幣/本位幣雙軌**（`acquisition_amount_txn` + 發票匯率換算 `original_value`），符合多幣別資產取得的慣例。
- **建卡與轉固兩段式**（預設不自動資本化），保留了「先掛 CIP、驗收完成才轉固」的實務彈性。
- 發票必須 POSTED 才能成卡，勾稽基礎正確。

## 三、與規範系統相比的差距

以下幾點是成熟 ERP 有、現有實作沒有的，看業務需要決定是否補：

1. **只能拆、不能併（merge）**。IAS 16 / 會計準則規定取得成本 = 買價 + 運費 + 安裝費等可直接歸屬成本，這些常分散在不同發票行甚至不同發票。Oracle Mass Additions 可以把多行併入一張卡（或作為 cost adjustment 加到既有卡片）；現有實作是嚴格的 1 行 → N 卡，運費、安裝費類的行無法歸集到主資產。

2. **取得日 = 發票日的假設偏簡化**。`acquisitionDate` 固定取 `invoice.getInvoiceDate()`，但會計上資本化日應是「達到可使用狀態日」，兩者可能差好幾個月（尤其真正的在建工程）。目前只有 `startDepreciationDate` 可覆寫，取得日不能。

3. **不支援部分金額成卡**。整行金額必須一次全轉，無法「這行 100 萬先轉 60 萬、剩 40 萬留在 CIP」。真實在建工程分批轉固時會遇到。

4. **成卡後上游沖銷沒有聯動**。發票行成卡後，如果 AP 發票被沖銷或收到貸項憑證，資產原值不會跟著調整；規範系統有 credit memo → cost adjustment 的機制。目前至少應該在發票沖銷時擋掉已成卡的發票（如果還沒有這個校驗，值得補上）。

5. **CIP 兼作清理科目**。嚴格說 Oracle 的 Asset Clearing 和 CIP 是兩個科目（前者是短期過渡、後者是真正在建工程歸集）。現有設計把兩者合一，對中小型系統可接受，但若日後要做真正的工程項目歸集（按項目彙集多期成本再轉固），這個科目會混用。

6. **卡片欄位全部繼承類別預設**（折舊方法、年限、殘值率），成卡時不能逐卡覆寫；Oracle 的 Prepare 環節允許會計在成卡前調整。這點影響不大，因為事後應該還能改卡片。

## 結論

這個設計走的是「AP 記 CIP → 選行成卡 → 轉固沖 CIP」的路徑，與 Oracle Mass Additions、SAP AuC 結算的骨架一致，方向是符合實務的，且防重複、幣別處理、拆卡尾差這些細節都做得正確。主要差距在**多行歸集成本（merge）**、**部分轉固**、**上游沖銷聯動**這三項，屬於功能完整度問題而非模式錯誤——如果客戶場景以「整機採購、一票一卡」為主，現有實作已經夠用；若有大型設備（主機+運費+安裝分行開票）或真正的在建工程，就需要補 merge 和部分轉固。
