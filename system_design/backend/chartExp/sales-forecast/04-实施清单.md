## 3. 实现约定

### 3.1 数量

```text
open_to_allocate = forecast − allocated − consumed
open_to_consume  = forecast − consumed
CHECK allocated + consumed <= forecast
```

全部 `compareTo`。Remote `updateAllocatedQuantities` 的 map 值为 **增量**（可负），对标 SO。落库后若违反 CHECK 或开量为负 → `ValidationException`，不要截断。

接管 / 吃未转：每个 SO 确认循环结束后，统一走 `SalesForecastItemRepository.updateQuantitiesAtomic(...)`（一条原生 SQL 改两列），禁止 `entity.setAllocated` + `setConsumed` 分两次 dirty flush。签名建议：

```java
@Modifying
@Query(value = """
    UPDATE lychee_erp.sales_forecast_items
    SET allocated_quantity = allocated_quantity + :dAlloc,
        consumed_quantity  = consumed_quantity  + :dCons
    WHERE id = :id
      AND allocated_quantity + :dAlloc >= 0
      AND consumed_quantity  + :dCons  >= 0
      AND allocated_quantity + :dAlloc + consumed_quantity + :dCons
            <= forecast_quantity
    """, nativeQuery = true)
int updateQuantitiesAtomic(Long id, BigDecimal dAlloc, BigDecimal dCons);
```

返回 0 → `ValidationException`（并发下开量不够或违反 CHECK）。现网 `SalesOrderServiceImpl` 为类级 `@Transactional`：原生 SQL 之后必须 `detach`/`refresh` 这些预告行（或下一张 SO 重新 `FOR UPDATE` 加载），避免同一 persistence context 读到旧快照。

ISO 周：`required_date.with(DayOfWeek.MONDAY)`（ISO-8601）。月：`withDayOfMonth(1)`。

### 3.2 确认预告

同一事务：

1. 校验 DRAFT、有行
2. 查同 `(company, customer)` 当前 ACTIVE（`FOR UPDATE`）
3. 若有：直接置 `CLOSED`，行跟随（不校验开量/allocated）；本单 `supersedes_id`
4. 本单 `ACTIVE`，行 `ACTIVE`，写 `confirmed_at/by`

两张 DRAFT 抢同一公司+客户：第二张确认命中部分唯一索引，转成业务错误（不要 500）。

### 3.3 转 FO

复制 `addItemsFromSalesOrders`：

- 换 DTO 字段 `forecastItemId`
- `sourceType` 必须 `FORECAST`
- `dueDate = requiredDate`
- pegging demand `SALES_FORECAST`
- 回写 `RemoteSalesForecastService.updateAllocatedQuantities`

删 FO 行：同时处理 `SALES_ORDER` 与 `SALES_FORECAST` 两种 demand。

### 3.4 SO 确认消耗

插在现网改 SO 状态之后、提交之前（同一 TX）。本批按 `order_date, order_no, id` 升序：

1. 无该公司+客户 ACTIVE、且按 `02` §3.3.1 走到的链上 / 当前单已关行上也无 `allocated>0` → 该单跳过消耗
2. 锁 ACTIVE；换版链 `while` 回溯，只锁 `allocated>0` 的 CLOSED 前序（全 0 不锁但仍继续 `supersedes_id`）
3. 按 `item_no` 匹配；单位冲突 → 失败
4. `SalesForecastService.consume`：内存累减同料同桶，写 `FORECAST→SO`，返回各行 `u/t`
5. **该 SO 循环结束**：`updateQuantitiesAtomic` 刷预告账 → detach/refresh
6. `t>0` → `RemoteFactoryOrderService.takeoverFromForecast`（只改 pegging）
7. SD 对每个 SO 行 `allocated += t`

反确认：

- 仅 `FORECAST→SO` 且 SO allocated=0 → `consume` 负向回滚
- allocated 仅来自 FORECAST FO 接管，且那些 FO 仍 DRAFT → `revertTakeover` + 负向 consume，再改 DRAFT
- 存在 `SALES_ORDER` FO 的 allocated → 现网拒绝

### 3.5 Pegging 树

`OrderPeggingServiceImpl`：根为 `SALES_FORECAST` 时按 **demand** 往下展（对标 SO）。  
新增 `SalesForecastPeggingEnricher`（填单号、状态）。

打印：`FORECAST` 来源 FO 允许打印；客户矩阵上游取 pegging 上的预告/SO 行，不要硬拒非 `SALES_ORDER`。V1 若改动面过大：FORECAST FO **禁用**现网 SO 矩阵打印并给明确 i18n，列入验收，避免 500。

### 3.6 命名检查

合并前不得残留：

- Entity 行级 `version` + `status_option_id` 当头
- `status_option_id` 作为预告状态
- 菜单正式名「销售预测」
- MRP 引擎 `seed*Forecast*`

测试 / i18n key：`sales_forecast` / `salesForecast`。

## 6. 验收

1. `DROP` 后旧单表列不存在；新头行可建 DRAFT，`SFO` 单号日重置。
2. 同一公司+客户第二张 ACTIVE 确认：自动关闭第一张并写 `supersedes_id`；旧单仍有 `open_to_allocate>0` 或 `allocated>0` → **新单仍确认成功**，旧未转开量不可再转 FO。
3. 同一公司+客户两个 DRAFT 同一 `version` → 保存/确认被唯一索引拒绝（业务错误）。不同 `company_id` 的同一客户可以各有一张 ACTIVE。
4. 明细：同单同料同桶第二行拒绝；`required_date` 跨周而 `bucket_type=WEEK` 拒绝。
5. ACTIVE 后改数量 API 拒绝；改备注成功。
6. 无行不能确认。DRAFT 可删；ACTIVE 不可删。
7. 预告 ACTIVE 100，转 FO 40：`allocated=40`，pegging `FORECAST→FO`；FO 确认后 MRP 能算到这 40。
8. 再转 61 拒绝；删 DRAFT FO 行后 `allocated` 回 0，可再转。
9. `SALES_ORDER` FO 调 `add-items-from-forecast` 拒绝；反之亦然。
10. 预告 100 未转 FO，SO 确认 60：`consumed=60`，`allocated=0`，pegging `FORECAST→SO`；SO 可再转 FO 60。
11. 预告 100 已转 FO 100，SO 确认 60：`allocated=40`，`consumed=60`，FO 上 60 改为 `SO→FO`，SO.`allocated=60`；SO 再汇入 FO 最多 40（未接管部分仍挂预告，**不要**把已接管 60 再转一次）。
12. 预告 100 已转 30，SO 确认 50：先消耗未转的 70 开量中的 50？**按锁定顺序**：未转 FO 开量 = 70，`c=50` 全部落在未转部分 → `consumed=50`，`allocated=30` 不动，无接管。SO 还可转 FO 50。
13. 预告 100 已转 80，SO 确认 50：未转开量 20 先吃完，再接管 30 → `consumed=50`，`allocated=50`，SO.`allocated=30`。
14. 匹配行单位不同 → SO 确认失败，状态仍 DRAFT，预告账不变。
15. 无 ACTIVE 预告 → SO 确认成功，行为与现网一致。
16. SO 交期为空 → 该行不消耗。
17. 已消耗未转 FO 的 SO 反确认：预告 `consumed` 回滚。已接管且 FO 仍 DRAFT：反确认成功，pegging 改回 `FORECAST→FO`，预告账还原，SO 回 DRAFT。已接管且 FO 已确认：反确认拒绝。存在 `SALES_ORDER` FO allocated：仍拒绝。
18. 交货汇入待交列表不含预告行；DN 不能选预告来源。
19. 菜单 `/sd/sales-forecasts` 可开主从表；FORECAST FO 可汇入预告。
20. 全文无用 `status_option_id` 表示预告状态；MRP 无 Forecast 种子调用。
21. 换版：旧单 100 已转 FO 40、未转 60 → 新单确认成功。随后 SO 确认 50：先接管旧 40，再吃新 ACTIVE 未转 10；**不得**再为这 40 开一张 FO。旧单 `allocated=0`、`consumed=40`；新单对应行 `consumed=10`。
22. 公司 A 的预告不被公司 B 的同客户 SO 消耗。
23. 同一预告行同时存在 `FORECAST→FO` 与 `FORECAST→SO` 且 supply 数值相同：`uk_order_peggings` 不冲突。
24. 同一 SO 两行同料同桶、预告开量 50：行 10 要 40、行 20 要 40 → 只消耗 50，行 20 余 30 不报错、不超额。
25. 批量确认两张同客户 SO 抢同一桶：按 `order_date, order_no, id` 升序分配，结果可复现。
26. ACTIVE 单行关闭后仍有 `allocated`：SO 确认仍接管该行 FO，且不再吃该行未转开量。
27. 换版链 W34 `allocated=40`、W35 `allocated=0`、W36 ACTIVE：SO 确认仍接管 W34 的 40（不得因 W35 全 0 停走）。`supersedes_id` 自环或指回已访问 id：回溯中断，不抛 500，本单只处理已纳入的池。
28. 列表/详情：ACTIVE 行开量 = `forecast − allocated − consumed`；行或头 CLOSED/CANCELLED 时开量显示 0（即使账面公式仍为正）。
29. 同一 TX 连续确认两张 SO 打同一预告行：第一张结束后走 `updateQuantitiesAtomic`；第二张读到的是库内已扣量，不超额、不撞 CHECK。
